
### Что такое **rebase** в Git?

**`git rebase`** — это одна из самых мощных и часто используемых команд в Git, которая позволяет **переместить или изменить базу (основу)** для вашей текущей ветки. В контексте работы с ветками и слияниями (merges), `rebase` позволяет интегрировать изменения из одной ветки в другую, но с тем отличием, что делает это **по-другому**, чем команда **`merge`**.

Когда вы выполняете **rebase**, вы "переносите" все изменения, сделанные в вашей ветке, на **новую базу**. Это может быть полезно, чтобы **переписать историю** или сделать её более линейной, без появления лишних merge-коммитов.

### Как работает `git rebase`?

1. **Слияние истории (merge history)**: При обычном слиянии (`merge`), Git создает новый **merge-коммит**, который объединяет изменения из двух веток. Однако, при **rebase** изменения из одной ветки просто **переносится поверх** изменений другой ветки, не создавая лишнего коммита.
    
2. **Простой пример**:
    
    - Пусть у вас есть две ветки: `master` и `feature`.
    - Если в ветке `feature` вы выполняете `rebase master`, то Git переместит коммиты из ветки `feature` поверх последнего коммита из ветки `master`, как если бы изменения в `feature` были сделаны **после** изменений в `master`.
    
    ```bash
    git checkout feature
    git rebase master
    ```
    
    Это позволяет "сделать историю" более линейной, так как все изменения из ветки `feature` будут казаться сделанными **после** изменений в `master`, без дополнительных merge-коммитов.
    
3. **Конфликты**: Во время ребейза могут возникнуть конфликты, и Git попросит вас разрешить их вручную. После того как вы разрешите конфликты, нужно будет выполнить команду `git rebase --continue`, чтобы продолжить процесс ребейза.
    

### Преимущества `rebase`:

- **Линейная история**: История становится более читаемой и линейной, без множества merge-коммитов. Это полезно для поддержания чистоты истории в репозиториях.
- **Чистая история изменений**: Все изменения будут отображаться в том порядке, в котором они были изначально сделаны, без того, чтобы создавать новые merge-коммиты, что может привести к сложной и нечеткой истории.

### Недостатки `rebase`:

- **Переписывание истории**: Ребейз изменяет историю коммитов, что может быть опасным, если вы работаете в совместной ветке, так как это может привести к потере данных, если другие разработчики уже вытягивали (fetch) ваши коммиты.

### Как `rebase` связан с хешированием?

В Git каждый коммит имеет уникальный **хеш**, который генерируется с использованием **SHA-1** алгоритма. Хеш коммита зависит от:

- Содержимого самого коммита (изменения в файлах).
- Метаданных коммита (например, автор, дата).
- **Хеша родительского коммита** (то есть, коммита, на основе которого был создан текущий).

Когда вы выполняете **rebase**, Git фактически **переписывает историю**: для каждого коммита в ветке `feature` создается новый коммит, который будет иметь новый хеш, так как:

- Изменяется родительский коммит (он теперь другой).
- Могут изменяться некоторые данные, такие как дата или автор.

**Это означает, что при ребейзе все коммиты получают новые хеши.** Поэтому, если кто-то уже работает с вашими старыми коммитами, и вы выполняете `rebase`, они будут иметь новый хеш и будут восприниматься как **новые** коммиты для других участников. Это может создать проблемы, если другие участники репозитория уже синхронизировались с этими коммитами.

### Пример:

Предположим, у вас есть две ветки: `master` и `feature`.

4. Исходная структура:
    
    ```
    A---B---C (master)
         \
          D---E---F (feature)
    ```
    
5. После выполнения `git rebase master` в ветке `feature`:
    
    ```
    A---B---C (master)
             \
              D'---E'---F' (feature)
    ```
    

Обратите внимание, что коммиты `D'`, `E'`, и `F'` — это новые коммиты с новыми хешами, потому что они были **переписаны** поверх `master`.

### Заключение

- **`git rebase`** позволяет переместить коммиты из одной ветки поверх другой, что помогает создавать линейную и чистую историю изменений, не создавая лишних merge-коммитов.
- В процессе **ребейза** происходит переписывание истории, и каждый коммит получает **новый хеш**, что важно учитывать, особенно при совместной работе.

### 🔄 Что делает `git rebase main` из ветки `feature`?

1. **Ветка `main` остаётся без изменений.**  
    Никаких новых коммитов, никакого слияния, ничего — она не трогается вообще.
    
2. **Ветка `feature` меняет свою историю.**
    
    - Git "вытаскивает" твои уникальные коммиты из `feature` (т.е. которые идут после общего предка с `main`).
        
    - Затем ставит их **поверх последнего коммита `main`**, как будто ты их написал позже.
        
    - При этом создаются **новые коммиты с новыми хешами** (`D'`, `E'` и т.д.).
        
    - Старая история (`D`, `E`) как бы "отваливается", но всё ещё доступна через reflog, если что.
        
3. **По итогу это выглядит**, как будто ты **только что создал `feature` от свежей `main`** и сразу сделал в ней свои коммиты.
    

---

### 🔁 Пример:

**До ребейза:**

```
main:    A---B---C
                  \
feature:           D---E
```

**После `git rebase main`:**

```
main:    A---B---C
                      \
feature:               D'--E'
```

- `main` untouched.
    
- `feature` будто бы родилась только что от `C`, и твои коммиты снова "сделаны", но уже в другом месте.
    
- Хеши у `D'` и `E'` другие, чем у оригинальных `D` и `E`.
    

---

### 💡 Итого:

✅ `main` не трогается  
✅ `feature` сохраняется, но с новой историей  
✅ Хеши коммитов меняются  
✅ Выглядит как новая ветка от свежего `main`  
⚠️ Потребуется `git push --force`, если `feature` уже была запушена
