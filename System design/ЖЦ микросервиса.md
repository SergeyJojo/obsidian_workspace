## **1. Жизненный цикл микросервисного приложения**

Разработка, развёртывание и эксплуатация микросервисов требуют тщательного управления жизненным циклом. Глубже рассмотрим каждую стадию:

### **1.1. Разработка**

#### **Модульность и независимость**

1. **Интерфейсы и контракты:**
    
    - Каждый микросервис должен иметь чётко определённый API:
        - REST, gRPC или GraphQL.
    - Контракты можно описывать через OpenAPI (Swagger).
2. **Тестирование контрактов:**
    
    - Используйте инструменты, такие как **Pact**, чтобы убедиться, что клиенты и провайдеры API согласованы:
        - Pact генерирует "мок" серверы для тестирования взаимодействий.

#### **CI/CD в микросервисах**

- Каждое изменение в микросервисе должно проверяться независимо.
- Ветка разработки (например, `feature/add-user-auth`) запускает:
    - Тесты контрактов.
    - Тесты интеграции (проверка совместимости с другими сервисами).
- **ArgoCD** или **Spinnaker** для автоматического развёртывания.

---

### **1.2. Деплой**

#### **Канареечный деплой**

- Развёртывайте новую версию на часть узлов:
    - Пример: 10% трафика направляется на новую версию.
- Используйте **Istio** для маршрутизации трафика:

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
spec:
  http:
  - route:
    - destination:
        host: my-service
        subset: v1
      weight: 90
    - destination:
        host: my-service
        subset: v2
      weight: 10
```

#### **Blue/Green Deployment**

- Развёртывание новой версии в параллельной среде.
- После проверки новая версия заменяет старую.

---

### **1.3. Мониторинг и наблюдаемость**

#### **Трассировка и корреляция запросов**

Когда запрос проходит через множество сервисов, важно понимать, где он "застревает". Используйте **дистрибутед трейсинг**:

- Инструменты: **Jaeger**, **Zipkin**.
- Реализация с OpenTelemetry:

```go
tracer := otel.Tracer("example-service")
ctx, span := tracer.Start(context.Background(), "operation-name")
defer span.End()

// Выполнение бизнес-логики
doWork(ctx)
```

#### **Метрики (Prometheus + Grafana)**

- Сбор ключевых метрик (например, `latency`, `request count`, `error rate`):
    - **RED метрики:**
        - Rate (количество запросов).
        - Errors (количество ошибок).
        - Duration (время обработки).

## **2. Архитектурные паттерны**

### **2.1. Паттерн "Strangler Fig"**

- Постепенная миграция монолита в микросервисы:
    - Старые функции остаются в монолите.
    - Новые функции разрабатываются как микросервисы.
- **API Gateway** перенаправляет запросы на нужный сервис или монолит.

---

### **2.2. Event Sourcing глубже**

#### **Основная идея**

- Вместо хранения текущего состояния объекта сохраняются все события, которые привели к этому состоянию.
- Пример: "Пользователь добавил товар в корзину", "Пользователь удалил товар".

#### **Реализация с Kafka:**

- События записываются в Kafka:

```go
type Event struct {
    ID      string
    Type    string
    Payload interface{}
    Time    time.Time
}
```

- Процессор событий обрабатывает их и обновляет локальную проекцию:

```go
func ProcessEvent(event Event) {
    switch event.Type {
    case "ItemAdded":
        // Обновить локальное хранилище
    case "ItemRemoved":
        // Удалить из локального хранилища
    }
}
```

## **3. Работа с отказами**

### **3.1. Circuit Breaker глубже**

- Circuit Breaker имеет три состояния:
    1. **Closed:** Всё работает нормально.
    2. **Open:** Система блокирует запросы к сервису.
    3. **Half-Open:** Система проверяет, восстановился ли сервис.

#### **Пример использования Hystrix:**

```java
@HystrixCommand(fallbackMethod = "fallback")
public String callExternalService() {
    return restTemplate.getForObject("http://service-endpoint", String.class);
}

public String fallback() {
    return "Fallback response";
}
```

---

### **3.2. Retry и экспоненциальная задержка**

Если сервис временно недоступен, можно повторить запрос с задержкой:

```go
func retryRequest(request func() error, retries int, delay time.Duration) error {
    for i := 0; i < retries; i++ {
        if err := request(); err == nil {
            return nil
        }
        time.Sleep(delay)
        delay *= 2 // Увеличиваем задержку
    }
    return errors.New("request failed")
}
```

## **4. Продвинутые вопросы, которые могут задать на собеседовании**

### **4.1. Как реализовать транзакции в микросервисах?**

#### Ответ:

1. Использование **Saga**:
    
    - Оркестрация или хореография.
2. Использование **двухфазного коммита (2PC):**
    
    - Протокол требует координации между всеми участниками, но это менее масштабируемо.
3. **Outbox паттерн:**
    
    - События записываются в локальную базу данных, а затем реплицируются в брокер сообщений.

---

### **4.2. Как решать проблему согласованности кэша и базы данных?**

#### Ответ:

1. **Write-Through Cache:**
    - Все изменения сначала записываются в кэш, затем в базу данных.
2. **Event-Driven Cache Update:**
    - База данных генерирует события при изменении данных, а кэш обновляется на основе событий.

---

### **4.3. Как справляться с "Split Brain" в распределённых системах?**

#### Ответ:

Используйте алгоритмы консенсуса:

- **Paxos** или **Raft**:
    - Гарантируют, что только одна сторона будет "активной" в случае разделения сети.
