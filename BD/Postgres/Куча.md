
В PostgreSQL термин "куча" (heap) относится к способу организации данных в таблицах на физическом уровне. Это основная структура хранения данных в PostgreSQL, и её понимание важно для работы с базой данных, особенно если вы занимаетесь оптимизацией или администрированием. Давайте разберём, для чего используется куча, как она работает, и основные моменты её использования.

---

Что такое куча в PostgreSQL?

"Куча" — это неупорядоченная структура данных, которая используется для хранения строк (или кортежей, tuples) таблицы. В отличие от индексов, где данные упорядочены по какому-то ключу, куча представляет собой просто набор записей, размещённых на страницах (обычно размером 8 КБ). Каждая строка в куче имеет уникальный идентификатор ctid, который указывает на её физическое местоположение на диске.

Куча — это базовый уровень хранения данных в таблице PostgreSQL, и все операции с данными (вставка, обновление, удаление, чтение) в конечном итоге работают с ней.

---

Для чего используется куча?

1. Хранение данных таблицы: Куча — это место, где физически хранятся все строки таблицы, если не используются дополнительные структуры вроде партиционирования или индексов для специфических задач.
    
2. Поддержка операций CRUD: Все операции создания, чтения, обновления и удаления данных (Create, Read, Update, Delete) происходят в куче.
    
3. Базис для индексов: Индексы в PostgreSQL (например, B-tree, GiST, GIN) ссылаются на строки в куче через ctid. Индексы ускоряют поиск, но сами данные извлекаются из кучи.
    
4. Управление версиями данных (MVCC): PostgreSQL использует механизм многовариантной конкурентности (MVCC), и куча играет ключевую роль в хранении старых и новых версий строк для обеспечения изоляции транзакций.
    

---

Основные моменты использования

1. Физическое расположение строк:
    
    - Строки в куче не упорядочены. Порядок вставки или обновления не гарантирует порядок хранения.
        
    - ctid — это временный указатель на строку (например, (0, 1) — страница 0, строка 1). Он может измениться после операций вроде UPDATE или VACUUM.
        
2. MVCC и "мёртвые кортежи":
    
    - При обновлении строки старая версия остаётся в куче как "мёртвый кортеж" (dead tuple), а новая записывается в другое место.
        
    - Удалённые строки тоже остаются как "мёртвые кортежи" до очистки.
        
    - Это требует периодической уборки с помощью команды VACUUM, чтобы освободить место и обновить статистику.
        
3. Размер страницы:
    
    - По умолчанию данные в куче хранятся в страницах по 8 КБ. Это можно изменить при компиляции PostgreSQL, но редко требуется.
        
    - Если строка не помещается в одну страницу (например, большие текстовые поля или массивы), используется механизм TOAST (см. ниже).
        
4. TOAST:
    
    - Для больших данных (например, длинных строк или BLOB) PostgreSQL использует технику TOAST (The Oversized-Attribute Storage Technique). Такие данные сжимаются или разбиваются на части и хранятся отдельно, но всё равно связаны с кучей.
        
5. Производительность:
    
    - Без индексов доступ к данным в куче требует полного сканирования (sequential scan), что медленно для больших таблиц.
        
    - Индексы ускоряют поиск, но увеличивают накладные расходы на обслуживание (обновление индексов при изменении данных в куче).
        

---

Неочевидные и дополнительные моменты

1. HOT (Heap-Only Tuples):
    
    - Если обновление строки не затрагивает индексированные столбцы и новая версия помещается на той же странице, PostgreSQL использует оптимизацию HOT. Это уменьшает фрагментацию и нагрузку на индексы.
        
2. Фрагментация:
    
    - Частые обновления и удаления приводят к фрагментации кучи — появляются "дыры" от мёртвых кортежей. Команда CLUSTER или VACUUM FULL может перестроить таблицу, упорядочив данные и убрав фрагментацию.
        
3. Ограничения ctid:
    
    - ctid ненадёжен для долгосрочного использования, так как он меняется после операций вроде UPDATE, VACUUM или CLUSTER. Не используйте его как замену первичному ключу.
        
4. Связь с индексами:
    
    - Индексы не содержат данные, а только указывают на строки в куче. Если индекс повреждён, его можно перестроить с помощью REINDEX, но сама куча остаётся основой.
        
5. Администрирование:
    
    - Команда ANALYZE обновляет статистику планировщика запросов, основываясь на данных в куче.
        
    - pgstattuple — расширение, которое позволяет анализировать состояние кучи (например, процент мёртвых кортежей).
        

---

Пример использования

Допустим, у вас есть таблица:

sql

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name TEXT,
    data JSONB
);
```

- При вставке INSERT INTO users (name, data) VALUES ('Alice', '{"key": "value"}'); данные записываются в кучу.
    
- При обновлении UPDATE users SET name = 'Bob' WHERE id = 1; старая строка остаётся в куче как мёртвый кортеж, а новая записывается рядом.
    
- Индекс на id ускоряет поиск, но сами данные извлекаются из кучи.
    

Если таблица активно обновляется, через некоторое время потребуется VACUUM, чтобы очистить мёртвые кортежи:

sql

```sql
VACUUM VERBOSE users;
```

---

Итог

Куча в PostgreSQL — это фундаментальная структура для хранения данных таблицы. Она проста, но требует внимания к управлению (MVCC, фрагментация, TOAST). Основные команды для работы с ней — VACUUM, CLUSTER, ANALYZE. Понимание её работы помогает оптимизировать производительность и избегать проблем вроде раздувания таблиц из-за мёртвых кортежей.
