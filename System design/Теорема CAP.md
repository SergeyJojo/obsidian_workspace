## **1. Расширенные аспекты согласованности**

### **1.1. Теорема CAP: Beyond the Basics**

**CAP-теорема** говорит, что распределённая система может гарантировать только два из трёх свойств:

- **Consistency (Согласованность):** Все узлы возвращают одинаковые данные.
- **Availability (Доступность):** Система отвечает на запросы, даже если некоторые узлы вышли из строя.
- **Partition Tolerance (Устойчивость к разделению):** Система продолжает работать при разрыве сети.

#### **Глубокий взгляд на компромиссы:**

- **CA (Consistency + Availability):**
    - Пример: Реляционные базы данных (SQL), где данные всегда согласованы, но при сетевом разрыве система может стать недоступной.
- **CP (Consistency + Partition Tolerance):**
    - Пример: MongoDB, HBase. Система отказывается от доступности для обеспечения согласованности.
- **AP (Availability + Partition Tolerance):**
    - Пример: DynamoDB, Cassandra. Данные могут быть неактуальными, но система всегда отвечает.

---

### **1.2. PACELC-теорема**

CAP — не вся история. **PACELC** добавляет нюанс:

- При **разделении сети** (Partitioning), система должна выбрать между **доступностью (A)** и **согласованностью (C)**.
- В **нормальных условиях** (Else), система должна выбрать между **задержкой (Latency)** и **согласованностью (Consistency)**.

Пример: DynamoDB при разделении сети выбирает **AP**, а в нормальных условиях — балансирует между низкой задержкой и согласованностью.

## **2. CRDT: Conflict-Free Replicated Data Types**

**CRDT** — это структуры данных, которые позволяют реплицировать данные между узлами без конфликтов. Это основа для построения **eventual consistency**.

### **2.1. Типы CRDT**

1. **Grow-Only Set (G-Set):**
    
    - Поддерживает только добавление элементов.
    - Используется для подсчёта уникальных событий.
2. **Last-Write-Wins Register (LWW-Register):**
    
    - Каждый узел пишет данные с временной меткой. Данные с большей меткой "побеждают".
3. **PN-Counter:**
    
    - Подсчёт с поддержкой увеличения и уменьшения.
    - Используется для подсчёта элементов в распределённых системах.

## **3. Алгоритмы построения масштабируемых очередей**

Очереди сообщений — это ядро асинхронных систем. Рассмотрим углублённые аспекты их построения.

### **3.1. Алгоритм распределённой очереди Kafka**

1. Kafka использует **partitioning** для разделения данных.
2. Каждый раздел (partition) обрабатывается только одним "лидером".
3. Консистентность в Kafka достигается через **ISR (In-Sync Replicas)**:
    - Лидер записывает данные.
    - Реплики подтверждают, что данные записаны.

---

### **3.2. Flow Control в очередях**

Чтобы система не перегружалась, используются механизмы:

1. **Ack/Nack:**
    - Сообщение помечается как "обработанное" (Ack) или "отклонённое" (Nack).
2. **Dead Letter Queue (DLQ):**
    - Если сообщение не обработано после нескольких попыток, оно отправляется в специальную очередь.

## **4. Теория управления нагрузкой**

### **4.1. Моделирование нагрузки через M/M/1**

Используй теорию очередей для расчёта времени отклика:

- **M/M/1** — одна очередь, один сервер, экспоненциальное распределение времени обработки.
- Среднее время ответа:
    
    ```plaintext
    W = 1 / (μ - λ)
    ```
    
    Где:
    - `λ`: Скорость поступления запросов.
    - `μ`: Скорость обработки запросов.

---

### **4.2. Механизм Graceful Degradation**

Когда система перегружена:

1. Отключи низкоприоритетные функции (например, рекомендации).
2. Возвращай предварительно кэшированные данные.

## **5. Реализация алгоритмов с нуля**

### **5.1. Алгоритм Raft: реализация базовых принципов**

Raft — это упрощённая альтернатива Paxos для достижения консенсуса.

#### **Основные этапы:**

1. Узлы выбирают лидера.
2. Лидер отвечает за запись данных.
3. Данные реплицируются на фолловеры.

#### **Пример кода:**

```go
type RaftNode struct {
    state       string // "follower", "candidate", "leader"
    currentTerm int
    votes       int
}

func (node *RaftNode) StartElection() {
    node.state = "candidate"
    node.currentTerm++
    node.votes = 1 // голосует за себя
    // Отправка запросов голосов другим узлам...
}
```

---

### **5.2. Consistent Hashing: добавление виртуальных узлов**

Улучшение равномерного распределения:

1. Каждый физический узел добавляется как несколько виртуальных узлов.
2. Виртуальные узлы равномерно распределяются по кольцу.

## **6. Реальные кейсы из индустрии**

### **6.1. Как спроектировать систему рекомендаций, устойчивую к нагрузкам?**

1. Используй **batch processing** для расчёта рекомендаций:
    - Spark или Hadoop для обработки данных.
2. Кэшируй предварительно рассчитанные рекомендации в Redis.

---

### **6.2. Как справляться с резким ростом трафика?**

1. Масштабирование через **autoscaling**:
    - Пример: Kubernetes автоматически добавляет поды при увеличении нагрузки.
2. Используй CDN для разгрузки серверов.
