
Давайте разберем, как происходит итерация по sync.Map в Go. sync.Map — это потокобезопасная реализация словаря из пакета sync, предназначенная для использования в конкурентных средах. В отличие от обычной карты (map), она не имеет встроенной операции range в языке, но предоставляет метод Range, который позволяет итерироваться по ключам и значениям. Я объясню, как это работает на уровне интерфейса и внутренней реализации.

---

Интерфейс sync.Map.Range

Метод Range определен следующим образом (из документации sync.Map):

go

```go
func (m *Map) Range(f func(key, value interface{}) bool)
```

- Аргумент f: Функция обратного вызова (callback), которая вызывается для каждой пары ключ-значение.
    
- Возвращаемое значение f:
    
    - Если f возвращает true, итерация продолжается.
        
    - Если f возвращает false, итерация прерывается.
        
- Потокобезопасность: Метод безопасен для вызова из нескольких горутин одновременно.
    

Пример использования:

go

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    m := &sync.Map{}
    m.Store("one", 1)
    m.Store("two", 2)
    m.Store("three", 3)

    m.Range(func(key, value interface{}) bool {
        fmt.Printf("key: %v, value: %v\n", key, value)
        return true // продолжаем итерацию
    })
}
```

Вывод (порядок не гарантирован):

```text
key: one, value: 1
key: two, value: 2
key: three, value: 3
```

Внутреннее устройство sync.Map

Чтобы понять, как работает итерация, нужно заглянуть во внутреннюю структуру sync.Map. Хотя исходный код находится в стандартной библиотеке (src/sync/map.go), я опишу ключевые моменты без прямого копирования закрытого кода, а на основе анализа и открытых данных.

Структура sync.Map

go

```go
type Map struct {
    mu     sync.Mutex      // Блокировка для "грязных" данных
    read   atomic.Value    // Атомарное хранилище "чистых" данных (тип readOnly)
    dirty  map[interface{}]*entry // "Грязная" карта с новыми/измененными данными
    misses int             // Счетчик промахов при чтении из read
}
```

- read: Атомарно хранит структуру readOnly, которая содержит карту "чистых" данных (map[interface{}]interface{}) и флаг amended, указывающий, есть ли измененные данные в dirty.
    
- dirty: Обычная карта Go, которая хранит новые или измененные записи. Используется, когда данные в read устарели.
    
- mu: Мьютекс для синхронизации доступа к dirty.
    
- entry: Внутренняя структура для значения, содержащая атомарный указатель (atomic.Value) и флаг удаления.
    

Двойное состояние

sync.Map использует два уровня данных:

1. read: Оптимизирован для быстрого чтения без блокировок (через atomic.Value).
    
2. dirty: Хранит изменения и требует мьютекса для записи или синхронизации с read.
    

---

Как работает Range?

Метод Range итерируется по всем парам ключ-значение, находящимся в sync.Map, объединяя данные из read и dirty. Вот пошаговый процесс:

1. Захват начального состояния

- Range начинает с чтения текущего значения read через m.read.Load().(readOnly).
    
- Это атомарная операция, не требующая блокировок, что делает начальную точку итерации безопасной в конкурентной среде.
    

2. Итерация по read

- Range проходит по карте, хранящейся в read.m (тип map[interface{}]*entry).
    
- Для каждого ключа:
    
    - Проверяется значение в entry.p (указатель на interface{}):
        
        - Если p == nil, запись считается удаленной (игнорируется).
            
        - Если p == expunged (специальный маркер), запись была "вытеснена" и требует проверки в dirty.
            
        - Если p содержит значение, оно передается в функцию f.
            

3. Проверка dirty

- Если read.amended == true, это означает, что в dirty есть дополнительные данные, отсутствующие в read.
    
- Range захватывает m.mu (блокировку) и проверяет dirty:
    
    - Если dirty == nil (например, после очистки), создается новая карта на основе read.
        
    - Затем итерируется по dirty, добавляя только те ключи, которые не были обработаны в read.
        

4. Вызов функции f

- Для каждой пары ключ-значение вызывается f(key, value):
    
    - Если f возвращает false, итерация немедленно прерывается.
        
    - Если true, продолжается до конца.
        

5. Обработка конкурентности

- Во время итерации другие горутины могут изменять sync.Map (добавлять, удалять или обновлять записи).
    
- Range работает с "снимком" данных на момент начала итерации:
    
    - Изменения в dirty после захвата read могут не отразиться.
        
    - Это означает, что итерация не гарантирует полную консистентность с текущим состоянием карты.
        

---

Пример внутренней логики (псевдокод)

go

```go
func (m *Map) Range(f func(key, value interface{}) bool) {
    ro := m.read.Load().(readOnly) // Атомарное чтение read

    // Итерация по read
    for k, e := range ro.m {
        v, ok := e.tryLoad() // Проверка значения в entry
        if ok && !e.isDeleted() { // Пропускаем удаленные
            if !f(k, v) {
                return
            }
        }
    }

    // Если есть dirty, проверяем его
    if ro.amended {
        m.mu.Lock()
        defer m.mu.Unlock()

        if m.dirty != nil { // Проверка после блокировки
            for k, e := range m.dirty {
                if _, exists := ro.m[k]; !exists { // Пропускаем уже обработанные
                    v, ok := e.tryLoad()
                    if ok && !e.isDeleted() {
                        if !f(k, v) {
                            return
                        }
                    }
                }
            }
        }
    }
}
```

- Примечание: Это упрощенный псевдокод, реальная реализация сложнее из-за обработки expunged записей и оптимизаций.
    

---

Особенности и ограничения

1. Нет гарантии порядка:
    
    - Как и у обычной карты Go, порядок итерации по sync.Map не определен.
        
2. Снимок данных:
    
    - Range видит состояние read на момент вызова. Изменения в dirty после этого могут быть пропущены.
        
3. Потокобезопасность:
    
    - Итерация безопасна для параллельного вызова, но не блокирует запись в карту другими горутинами.
        
4. Прерывание:
    
    - Возврат false из f немедленно останавливает итерацию, что полезно для поиска или частичной обработки.
        

---

Итог

Итерация по sync.Map через Range:

- Работает с двумя уровнями данных: read (быстрое чтение) и dirty (изменения под блокировкой).
    
- Выполняет атомарное чтение read и, при необходимости, блокирует mu для доступа к dirty.
    
- Передает пары ключ-значение в функцию f, пропуская удаленные или вытесненные записи.
    
- Не гарантирует полную консистентность с текущим состоянием из-за конкурентных изменений.
    

Структура sync.Map в Go — это потокобезопасная реализация хеш-таблицы (map), предназначенная для использования в конкурентных приложениях. Она была введена в Go 1.9 как часть пакета sync, чтобы предоставить альтернативу стандартной map с встроенной синхронизацией, которая не требует внешних мьютексов. Давайте разберём её внутреннюю структуру и принцип работы "по полочкам", основываясь на исходном коде Go (runtime) и её логике.

---

Общая идея sync.Map

- sync.Map оптимизирована для сценариев, где много чтений и мало записей, чтобы минимизировать блокировки.
    
- Она использует комбинацию атомарных операций и мьютексов для обеспечения безопасности в конкурентной среде.
    
- В отличие от обычной map с sync.Mutex, sync.Map разделяет данные на "только для чтения" и "грязные" (dirty), что ускоряет операции чтения.
    

---

Структура sync.Map (из исходного кода)

Вот как она определена в пакете sync (на момент Go 1.21):

go

```go
type Map struct {
    mu     sync.Mutex       // Мьютекс для защиты операций записи
    read   atomic.Value     // Атомарное хранилище для "только чтение" данных (тип readOnly)
    dirty  map[interface{}]interface{} // "Грязная" карта для новых или изменённых записей
    misses int              // Счётчик промахов при чтении из read
}
```

А структура readOnly, которая хранится в read:

go

```go
type readOnly struct {
    m       map[interface{}]interface{} // Карта "только чтение"
    amended bool                     // Флаг, указывающий, есть ли данные в dirty, отсутствующие в m
}
```

---

Разбор структуры "по полочкам"

1. mu sync.Mutex
    
    - Назначение: Мьютекс для синхронизации операций записи и обновления структуры.
        
    - Когда используется:
        
        - При записи нового значения (Store).
            
        - При удалении (Delete).
            
        - При обновлении dirty карты, когда промахов (misses) становится слишком много.
            
    - Особенность: Защищает только "медленные" операции, чтение обычно обходится без него.
        
2. read atomic.Value
    
    - Назначение: Атомарное хранилище для структуры readOnly, которая содержит данные, доступные только для чтения.
        
    - Тип данных: Хранит readOnly, которая включает:
        
        - m map[interface{}]interface{} — карта с данными, которые считаются "чистыми" (неизменяемыми на момент чтения).
            
        - amended bool — флаг, показывающий, есть ли данные в dirty, которых нет в read.m.
            
    - Когда используется:
        
        - При операциях чтения (Load, Range).
            
        - Обновляется атомарно через atomic.Store при необходимости синхронизации с dirty.
            
    - Особенность: Благодаря atomic.Value чтение из read не требует мьютекса, что делает его быстрым и конкурентным.
        
3. dirty map[interface{}]interface{}
    
    - Назначение: Хранит "грязные" данные — новые записи или изменённые значения, которые ещё не синхронизированы с read.
        
    - Когда используется:
        
        - При добавлении новых ключей через Store.
            
        - При удалении ключей, если они были в dirty.
            
        - При "промахе" (miss) в read, когда ключ ищется в dirty.
            
    - Особенность: Может быть nil, если все данные уже синхронизированы с read. Когда dirty становится достаточно большим, он "поднимается" в read.
        
4. misses int
    
    - Назначение: Счётчик промахов — сколько раз чтение из read не нашло ключ, и пришлось обращаться к dirty.
        
    - Когда используется:
        
        - Увеличивается при каждом обращении к dirty в Load.
            
        - Если misses достигает порога (например, длины dirty), dirty копируется в read, а dirty очищается.
            
    - Особенность: Помогает балансировать производительность, избегая частого копирования dirty в read.
        

---

Как это работает вместе

Чтение (Load):

1. Сначала проверяется read через atomic.Load.
    
    - Если ключ есть в read.m и запись не помечена как удалённая (entry не expunged), возвращается значение.
        
    - Если amended == true, значит, есть данные в dirty, которых нет в read.
        
2. Если ключа нет в read или amended == true:
    
    - Блокируется mu.
        
    - Проверяется dirty, возвращается значение, если найдено.
        
    - Увеличивается misses.
        
3. Если misses превышает порог, dirty копируется в новый readOnly, обновляется read атомарно, а dirty становится nil.
    

Запись (Store):

1. Блокируется mu.
    
2. Если dirty == nil, создаётся новый dirty как копия read.m с удалёнными помеченными записями (expunged).
    
3. Добавляется или обновляется значение в dirty.
    
4. Обновляется read.amended = true, если ключ новый.
    

Удаление (Delete):

1. Блокируется mu.
    
2. Удаляется ключ из dirty (если он там был).
    
3. В read значение помечается как expunged (специальный указатель), если оно ещё не в dirty.
    

---

Внутренняя структура записи (entry)

Каждая запись в read.m и dirty представлена как указатель на структуру entry:

go

```go
type entry struct {
    p unsafe.Pointer // Указатель на значение или специальные состояния
}
```

- Состояния p:
    
    - nil — ключ удалён, но ещё не вычищен из read.
        
    - expunged — специальное значение, показывающее, что ключ был удалён и не должен использоваться.
        
    - Указатель на interface{} — актуальное значение.
        
- Особенность: Использование unsafe.Pointer и атомарных операций (atomic.LoadPointer, atomic.StorePointer) позволяет обновлять значения без мьютекса в некоторых случаях.
    

---

Пример работы

go

```go
var m sync.Map
m.Store("key1", 1) // mu.Lock(), dirty["key1"] = 1, read.amended = true
m.Store("key2", 2) // mu.Lock(), dirty["key2"] = 2
val, ok := m.Load("key1") // atomic.Load(read), затем mu.Lock(), dirty["key1"]
m.Delete("key1") // mu.Lock(), удаление из dirty, пометка в read как expunged
```

---

Итог структуры sync.Map:

1. mu: Защищает запись и синхронизацию dirty с read.
    
2. read: Быстрый доступ к "чистым" данным через atomic.Value.
    
3. dirty: Хранит новые/изменённые данные, синхронизируется с read при необходимости.
    
4. misses: Балансирует частоту обновления read из dirty.
    
5. entry: Внутренние указатели для значений с состояниями (nil, expunged, данные).
    

Внутренняя структура entry в sync.Map — это ключевой элемент, который используется для хранения значений в хеш-таблице sync.Map. Она не экспортируется (является частью внутренней реализации пакета sync), но её устройство можно понять из исходного кода Go и логики работы sync.Map. Давайте разберём её устройство "по полочкам", основываясь на том, как она определена и используется.

---

Определение entry

В исходном коде sync/map.go структура entry выглядит так:

go

```go
type entry struct {
    p unsafe.Pointer // Указатель на значение или специальное состояние
}
```

- Это простая структура с единственным полем p, которое представляет собой указатель типа unsafe.Pointer.
    
- unsafe.Pointer — это универсальный указатель в Go, который позволяет обходить строгую типизацию и работать с памятью напрямую.
    

---

Назначение entry

- entry используется как обёртка для каждого значения, хранящегося в read.m (карта "только чтение") и dirty (грязная карта) внутри sync.Map.
    
- Она позволяет:
    
    1. Хранить само значение (через указатель на interface{}).
        
    2. Отмечать состояние записи (например, "удалено" или "вычищено").
        
    3. Обеспечивать атомарное обновление значений без блокировки мьютекса в некоторых случаях.
        

---

Разбор устройства entry "по полочкам"

1. Поле p (unsafe.Pointer)
    
    - Тип: unsafe.Pointer — указатель, который может указывать на любой тип данных или специальные значения.
        
    - Назначение: Хранит либо само значение (в виде указателя на interface{}), либо одно из двух специальных состояний:
        
        - nil — ключ присутствует в карте, но значение было удалено.
            
        - expunged — специальный маркер, указывающий, что ключ был окончательно вычищен из read и теперь существует только в dirty (или удалён полностью).
            
    - Особенность: Использование unsafe.Pointer позволяет применять атомарные операции (atomic.LoadPointer, atomic.StorePointer, atomic.CompareAndSwapPointer) для конкурентного доступа.
        
2. Состояния entry.p
    
    - p == nil:
        
        - Что значит: Значение было удалено через Delete, но ключ ещё присутствует в read.m или dirty.
            
        - Когда появляется: После вызова m.Delete(key), если ключ был только в read, он помечается как nil до полной очистки.
            
        - Пример: m.Store("key", 1); m.Delete("key) → entry.p = nil.
            
    - p == expunged:
        
        - Что значит: Специальное значение, показывающее, что ключ был "вычищен" (expunged) из read и теперь либо существует в dirty, либо удалён окончательно.
            
        - Когда появляется: При синхронизации read с dirty, если ключ удалён и не нужен в read. expunged — это глобальная константа в runtime:
            
            go
            
            ```go
            var expunged = unsafe.Pointer(new(interface{}))
            ```
            
        - Пример: После многократных промахов (misses) dirty становится новым read, а старые удалённые записи получают expunged.
            
    - p указывает на значение (interface{}):
        
        - Что значит: Указатель на актуальное значение, хранящееся в куче (heap).
            
        - Когда появляется: После m.Store(key, value) или при копировании из dirty в read.
            
        - Пример: m.Store("key", 42) → entry.p указывает на interface{} с значением 42.
            
3. Атомарность
    
    - Как работает: Поле p обновляется с помощью атомарных операций:
        
        - atomic.LoadPointer(&e.p) — безопасное чтение значения.
            
        - atomic.StorePointer(&e.p, ptr) — запись нового значения.
            
        - atomic.CompareAndSwapPointer(&e.p, old, new) — условное обновление (CAS).
            
    - Зачем: Это позволяет конкурентно читать и обновлять значения в read.m без блокировки мьютекса mu, что ускоряет операции Load.
        
4. Жизненный цикл entry
    
    - Создание: При добавлении ключа через Store создаётся новая entry с p, указывающим на значение.
        
    - Обновление: Значение может быть изменено через CAS, если ключ уже существует в read.
        
    - Удаление: p устанавливается в nil через Delete, затем может стать expunged при синхронизации.
        
    - Очистка: Когда dirty становится новым read, старые entry с expunged вычищаются.
        

---

Как entry используется в sync.Map

Чтение (Load):

go

```go
func (m *Map) Load(key interface{}) (value interface{}, ok bool) {
    read, _ := m.read.Load().(readOnly)
    e, ok := read.m[key]
    if !ok && read.amended {
        m.mu.Lock()
        e, ok = m.dirty[key]
        m.mu.Unlock()
    }
    if !ok {
        return nil, false
    }
    return e.load()
}

func (e *entry) load() (value interface{}, ok bool) {
    p := atomic.LoadPointer(&e.p)
    if p == nil || p == expunged {
        return nil, false
    }
    return *(*interface{})(p), true
}
```

- Проверяется read.m[key]. Если entry найдена, вызывается e.load().
    
- Если p == nil или p == expunged, возвращается nil, false.
    
- Иначе p преобразуется в interface{} и возвращается значение.
    

Запись (Store):

go

```go
func (m *Map) Store(key, value interface{}) {
    m.mu.Lock()
    if m.dirty == nil {
        m.dirty = make(map[interface{}]interface{})
        // Копирование из read в dirty
    }
    m.dirty[key] = value
    m.mu.Unlock()
}
```

- Новая entry создаётся в dirty с p, указывающим на value.
    

Удаление (Delete):

go

```go
func (m *Map) Delete(key interface{}) {
    m.mu.Lock()
    delete(m.dirty, key)
    if e, ok := m.read.m[key]; ok {
        e.delete()
    }
    m.mu.Unlock()
}

func (e *entry) delete() {
    atomic.StorePointer(&e.p, nil)
}
```

- В dirty ключ удаляется.
    
- В read p устанавливается в nil.
    

---

Пример жизненного цикла entry

1. m.Store("key", 1):
    
    - dirty["key"] = &entry{p: &1}.
        
2. m.Load("key"):
    
    - После промахов read.m["key"] = &entry{p: &1}.
        
3. m.Delete("key"):
    
    - read.m["key"].p = nil.
        
4. Синхронизация dirty → read:
    
    - read.m["key"].p = expunged, если ключа нет в dirty.
        

---

Итог устройства entry

- p unsafe.Pointer: Хранит значение или состояние (nil, expunged).
    
- Атомарность: Обеспечивает конкурентное чтение/обновление через atomic.
    
- Состояния:
    
    - nil — удалено, но ещё в карте.
        
    - expunged — вычищено из read.
        
    - Указатель на interface{} — актуальное значение.
        
- Роль: Оптимизирует работу sync.Map, разделяя быстрые операции чтения и медленные операции записи.
- 
В sync.Map запись из read не "вытесняется" и не заменяется напрямую записью из dirty в традиционном смысле (как перезапись конкретной записи). Вместо этого происходит процесс синхронизации, когда вся карта dirty становится новым содержимым read, а старые записи в read, помеченные как удалённые или устаревшие, могут быть вытеснены (точнее, очищены или заменены актуальными данными из dirty). Этот процесс связан с механизмом "поднятия" (promotion) карты dirty в read. Давайте разберём, в каком случае это происходит и как влияет на записи.

---

Условие "вытеснения" записи из read

Запись из read может быть фактически заменена или вытеснена в следующих случаях:

1. Превышение количества промахов (misses) при чтении
    
    - Когда происходит:
        
        - Каждый раз, когда операция Load не находит ключ в read.m (или находит запись с entry.p == nil/expunged), но находит его в dirty, счётчик misses увеличивается.
            
        - Если misses достигает порога, равного длине dirty (len(m.dirty)), планировщик sync.Map решает синхронизировать dirty с read.
            
    - Что происходит:
        
        - dirty полностью копируется в новую структуру readOnly.
            
        - Все записи из старого read.m, которые были помечены как expunged или отсутствуют в dirty, вытесняются (их больше нет в новом read).
            
        - Актуальные записи из dirty становятся частью нового read.m.
            
        - После этого dirty устанавливается в nil, а misses сбрасывается.
            
    - Условие:
        
        - m.misses >= len(m.dirty) && len(m.dirty) > 0.
            
2. Удаление ключа с последующей записью нового значения
    
    - Когда происходит:
        
        - Если ключ был удалён через Delete (в read запись становится entry.p = nil), а затем добавлено новое значение через Store (оно попадает в dirty), то при следующей синхронизации старое состояние (nil или expunged) в read будет заменено новым значением из dirty.
            
    - Что происходит:
        
        - При синхронизации dirty → read запись в read.m обновляется до актуального значения из dirty.
            
    - Условие:
        
        - Ключ присутствует в dirty с новым значением, а в read он либо отсутствует, либо имеет состояние nil/expunged.
            

---

Механизм синхронизации dirty → read

Этот процесс описан в методе missLocked() внутри sync.Map:

go

```go
func (m *Map) missLocked() {
    m.misses++
    if m.misses < len(m.dirty) {
        return
    }
    m.read.Store(readOnly{m: m.dirty})
    m.dirty = nil
    m.misses = 0
}
```

- Шаги:
    
    1. Увеличивается m.misses.
        
    2. Если m.misses меньше длины dirty, ничего не происходит (ранний выход).
        
    3. Если m.misses >= len(m.dirty):
        
        - dirty становится новым read.m через атомарную операцию atomic.Store.
            
        - dirty очищается (nil).
            
        - misses сбрасывается в 0.
            
- Результат:
    
    - Все записи из старого read, которые были помечены как expunged или отсутствуют в dirty, исчезают из нового read.
        
    - Записи из dirty (включая новые или обновлённые) полностью заменяют старое содержимое read.
        

---

Пример сценария

Исходное состояние:

go

```go
var m sync.Map
m.Store("key1", 1) // dirty["key1"] = 1
m.Store("key2", 2) // dirty["key2"] = 2
m.Delete("key1")   // dirty["key1"] удалён, read["key1"].p = nil
```

- read: {"key1": entry{p: nil}, "key2": entry{p: &2}} (после синхронизации).
    
- dirty: {"key2": 2}.
    

Добавление нового значения:

go

```go
m.Store("key1", 10) // dirty["key1"] = 10
```

- dirty: {"key1": 10, "key2": 2}.
    
- read: {"key1": entry{p: nil}, "key2": entry{p: &2}}.
    
- misses увеличивается при каждом Load("key1"), так как ключ ищется в dirty.
    

Превышение промахов:

- После нескольких m.Load("key1") (например, misses >= 2):
    
    - dirty становится новым read: read.m = {"key1": entry{p: &10}, "key2": entry{p: &2}}.
        
    - Старое значение read["key1"].p = nil вытесняется новым значением 10 из dirty.
        
    - dirty = nil, misses = 0.
        

---

В каком случае запись из read вытесняется?

Запись из read вытесняется и заменяется записью из dirty в следующих условиях:

1. Ключ удалён в read (p = nil) и добавлен заново в dirty:
    
    - При синхронизации старое состояние (nil) заменяется новым значением из dirty.
        
2. Ключ помечен как expunged в read:
    
    - Если ключ отсутствует в dirty или обновлён, при синхронизации он либо исчезает, либо заменяется актуальным значением.
        
3. Промахи превышают порог:
    
    - Когда misses >= len(dirty), вся dirty становится новым read, и старые записи (nil, expunged) вытесняются актуальными данными из dirty.
        

---

Итог

- "Вытеснение" записи из read происходит не по одной записи, а в процессе полной замены read.m на dirty при синхронизации.
    
- Условие: misses >= len(dirty), вызванное частыми обращениями к данным, которые есть только в dirty.
    
- Старые состояния (nil, expunged) в read заменяются новыми значениями из dirty или исчезают, если ключей больше нет в dirty.
### **Как устроена `sync.Map` в Go (простое объяснение)**

`sync.Map` — это потокобезопасная мапа, оптимизированная для двух сценариев:  
1) **Частое чтение** (без блокировок)  
2) **Редкая запись** (с минимальными блокировками)  

Она использует **две мапы** и **хитрые флаги**, чтобы избежать глобальных блокировок.  

---

## **1. Две мапы внутри `sync.Map`**
```go
type Map struct {
    mu     sync.Mutex      // Блокировка только для dirty-мапы
    read   atomic.Value    // Горячая мапа (только для чтения)
    dirty  map[any]*entry  // "Грязная" мапа (для записи)
    misses int             // Счетчик промахов в read
}
```

- **`read`** (readonly):  
  - Быстрая, работает без блокировок через `atomic`.  
  - Может устаревать (не всегда актуальна).  

- **`dirty`** (грязная):  
  - Полная актуальная версия данных.  
  - Требует блокировки `mu` для доступа.  

---

## **2. Как работает `sync.Map`**  

### **Чтение (`Load`)**
1. Сначала ищем ключ в **`read`** (без блокировки).  
2. Если не нашли:  
   - Блокируем `mu`.  
   - Ищем ключ в **`dirty`**.  
   - Увеличиваем `misses`.  
3. Если `misses > len(dirty)`:  
   - **`dirty` копируется в `read`** (теперь `read` снова актуальна).  
   - `dirty` становится `nil` (пока не понадобится новая запись).  

> 💡 **Почему `misses > len(dirty)`?**  
> Это порог, после которого `read` становится слишком устаревшей, и её нужно обновить.  

---

### **Запись (`Store`)**
1. Если ключ есть в `read`:  
   - Пытаемся обновить его **атомарно** (без блокировки).  
2. Если ключа нет:  
   - Блокируем `mu`.  
   - Если `dirty == nil`:  
     - Копируем все **неудалённые** ключи из `read` в `dirty`.  
   - Добавляем/обновляем ключ в `dirty`.  

---

### **Удаление (`Delete`)**
1. Если ключ есть в `read`:  
   - Помечаем его как **`nil`** (логическое удаление).  
2. Если ключ есть в `dirty`:  
   - Удаляем его физически.  

---

## **3. Что за флаги `nil` и `expunged`?**  
Каждое значение в мапе хранится как `*entry`:  
```go
type entry struct {
    p unsafe.Pointer  // Может быть: значением, `nil` или `expunged`
}
```

| Флаг           | Что означает?                                                          |
| -------------- | ---------------------------------------------------------------------- |
| **`nil`**      | Ключ удалён, но **ещё есть в `dirty`** (можно переиспользовать entry). |
| **`expunged`** | Ключ удалён и **нет в `dirty`** (значит, он полностью исчез из мапы).  |
| **`amended`**  | В `read` есть не все ключи (значит, часть данных только в `dirty`).    |

### **Зачем это нужно?**
- **`nil`**:  
  - Говорит, что ключ удалён, но его `entry` можно переиспользовать при следующей записи.  

- **`expunged`**:  
  - Нужен, чтобы при копировании из `read` в `dirty` не переносить удалённые ключи.  

- **`amended`**:  
  - Оптимизация: если `amended=false`, значит `read` содержит все ключи, и `dirty` можно не проверять.  

---

## **4. Пример работы `sync.Map`**
```go
m := sync.Map{}

// Запись
m.Store("key1", 100)  // Попадет в dirty (так как read пустая)

// Чтение
val, ok := m.Load("key1")  // Сначала в read (нет), потом в dirty (есть)

// Удаление
m.Delete("key1")  // В read помечается как nil, в dirty удаляется

// Повторная запись
m.Store("key1", 200)  // Если entry в read == nil, переиспользуется
```

---

## **5. Итог: как запомнить?**
- `read` — быстрая, но может устаревать.  
- `dirty` — полная, но требует блокировки.  
- `misses` — счётчик промахов, если их много — `dirty` копируется в `read`.  
- `nil` — "ключ удалён, но структура осталась".  
- `expunged` — "ключ удалён навсегда".  
- `amended` — "в `read` не все ключи, смотри ещё в `dirty`".  

`sync.Map` — это **оптимизация для редких записей**, а не для частых. Если у вас много записей, лучше использовать `map + RWMutex`.
