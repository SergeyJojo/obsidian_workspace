
### **Sidecar Pattern (Паттерн "Боковой контейнер")**  
**Назначение**: Разделение функциональности основного приложения и вспомогательных задач (логирование, мониторинг, аутентификация) путём выноса их в отдельный процесс/контейнер.  

#### **Как работает?**  
- Основное приложение (например, микросервис Twitch для чата) работает в одном контейнере.  
- Рядом с ним запускается **"боковой" контейнер** (Sidecar), который выполняет сопутствующие задачи:  
  - **Логирование** (сбор и отправка логов в ELK или Grafana).  
  - **Мониторинг** (метрики для Prometheus).  
  - **Сетевые задачи** (TLS-шифрование, балансировка).  
  - **Кеширование** (например, Redis для временных данных).  

#### **Пример в Twitch**  
- Для микросервиса **трансляции видео** Sidecar может:  
  - Анализировать сетевые задержки и переключать протоколы (HLS → LL-HLS).  
  - Собирать метрики качества стрима (битрейт, потери пакетов).  

#### **Плюсы и минусы**  
| ✅ Преимущества | ❌ Недостатки |  
|----------------|---------------|  
| Изоляция основного кода от вспомогательной логики | Усложнение деплоя (2+ контейнера на сервис) |  
| Гибкость (можно менять Sidecar без перезапуска основного сервиса) | Нагрузка на ресурсы (CPU/RAM) |  
| Поддержка разных языков (Sidecar может быть на Go, основной сервис — на Java) |

### **Split-Brain Pattern (Паттерн "Разделённый мозг")**  
**Назначение**: Обеспечение отказоустойчивости распределённых систем при сетевых сбоях, когда кластер разделяется на изолированные части ("мозги").  

#### **Как работает?**  
1. **Сценарий**: Сеть между узлами кластера рвётся, образуя два независимых подкластера.  
2. **Проблема**: Обе части могут считать себя "главными" и вносить противоречивые изменения (например, в базу данных).  
3. **Решение**:  
   - **Quorum (Кворум)**: Система требует согласия большинства узлов для записи (например, 3 из 5).  
   - **Fencing**: Блокировка "меньшинства" до восстановления связи.  
   - **Автоматическое восстановление**: После устранения сбоя данные синхронизируются.  

#### **Пример в Twitch**  
- Если **чат-серверы** в AWS разделяются из-за сбоя:  
  - Часть зрителей видит чат A, часть — чат B.  
  - Система использует **Quorum**, чтобы определить, какая сторона может принимать сообщения.  
  - После восстановления сообщения из "отставшей" части сливаются в основную.  

#### **Плюсы и минусы**  
| ✅ Преимущества | ❌ Недостатки |  
|----------------|---------------|  
| Предотвращение потери данных | Сложная реализация (например, в распределённых БД) |  
| Минимизация downtime | Риск временной недоступности сервиса |  
| Поддержка консистентности | Требует чёткого определения "кворума" |  

---

### **Сравнение паттернов**  
| Характеристика       | Sidecar                          | Split-Brain                     |  
|----------------------|----------------------------------|---------------------------------|  
| **Цель**            | Модульность и расширяемость      | Отказоустойчивость при сбоях    |  
| **Использование**   | Микросервисы, Kubernetes         | Распределённые БД, кластеры     |  
| **Примеры**         | Envoy (прокси), Fluentd (логи)   | Cassandra, Elasticsearch        |  

**Вывод**:  
- **Sidecar** — для улучшения архитектуры сервисов (например, в Twitch для мониторинга стримов).  
- **Split-Brain** — критичен для систем, где важен consensus (чаты, транзакции).
