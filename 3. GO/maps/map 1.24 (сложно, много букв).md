🌻 Мапа со швейцарской таблицей

В Go 1.24 map реализован с использованием швейцарской таблицы (Swiss Table). Разберёмся, что это значит для разработчиков и как это влияет на производительность.

➖ Что такое швейцарская таблица

Швейцарская таблица – это продвинутый алгоритм хеш-таблиц, разработанный Google для библиотеки Abseil. Она отличается высокой плотностью хранения данных и уменьшенной нагрузкой на кеш процессора.

➖ Главные фишки:

• Компактное представление — хранит метаданные ключей рядом с хешами, что сокращает использование памяти.

• Эффективное разрешение коллизий — используется пробирование с SIMD: процессор обрабатывает сразу несколько элементов одновременно.

• Быстрое сканирование — поиск ключей стал намного быстрее за счёт оптимизированных операций.

Мапа в Go теперь занимает на 15-25% меньше памяти, а производительность ускорилась на 5-15%. Если в вашем коде активно используется map, он автоматически станет быстрее, потому что внешне ничего не поменялось.


Этот пакет содержит реализацию встроенного типа карты в Go.

Дизайн карты основан на "Swiss Table" (швейцарская таблица) от Abseil ([https://abseil.io/about/design/swisstables](https://abseil.io/about/design/swisstables)), с дополнительными модификациями, чтобы учесть дополнительные требования Go, которые обсуждаются ниже.

### Терминология:

- **Слот:** Местоположение для хранения одной пары ключ/элемент.
- **Группа:** Группа из 8 слотов `abi.SwissMapGroupSlots` плюс управляющее слово.
- **Управляющее слово:** 8-байтное слово, которое указывает, является ли слот пустым, удаленным или использованным. Если слот используется, то его управляющий байт также содержит нижние 7 бит хэша (H2).
- **H1:** Верхние 57 бит хэша.
- **H2:** Нижние 7 бит хэша.
- **Таблица:** Полная хэш-таблица "Swiss Table". Таблица состоит из одной или нескольких групп для хранения, а также метаданных для обработки операций и определения момента роста.
- **Карта:** Тип верхнего уровня `Map` состоит из нуля или более таблиц для хранения. Верхние биты хэша выбирают, к какой таблице принадлежит ключ.
- **Директория:** Массив таблиц, используемых картой.

В своей основе дизайн таблицы похож на традиционную хэш-таблицу с открытым адресованием. Хранение данных состоит из массива групп, что эффективно означает массив слотов ключ/элемент с вкраплениями управляющих слов. Поиск использует хэш для определения начальной группы для проверки. Если в этой группе, из-за коллизий, нет совпадений, последовательность пробежки выбирает следующую группу для проверки (см. ниже подробности о последовательности пробежки).

### Основное отличие заключается в группе:

В стандартной хэш-таблице с открытым адресованием и линейным поиском мы проверяем каждый слот поочередно, чтобы найти совпадение. Швейцарская таблица использует дополнительное управляющее слово для проверки всех 8 слотов параллельно.

Каждый байт в управляющем слове соответствует одному из слотов в группе. В каждом байте 1 бит указывает, используется ли слот, или он пустой/удаленный. Остальные 7 бит содержат нижние 7 бит хэша для ключа в этом слоте.

Во время поиска мы используем хитрые битовые манипуляции для параллельной проверки всех 8 7-битных хэшей с входным хэшем (см. `ctrlGroup.matchH2`). Таким образом, фактически мы выполняем 8 шагов пробежки за одну операцию. С использованием SIMD инструкций это может быть расширено до 16 слотов с 16-байтным управляющим словом.

Поскольку мы используем только 7 бит из 64-битного хэша, существует вероятность ложных срабатываний около 0,7% на каждый слот, но это нормально: мы всегда проверяем совпадение с помощью стандартного сравнения ключей.

### Пробежка (Probing)

Пробежка выполняется с использованием верхних 57 бит (H1) хэша как индекса в массив групп. Пробежка идет по группам с использованием квадратичной пробежки, пока не найдет группу с совпадением или с пустым слотом. См. `probeSeq` для подробностей о последовательности пробежки. Обратите внимание на инварианты пробежки: количество групп должно быть степенью двойки, и конец последовательности пробежки должен быть группой с пустым слотом (таблица не может быть полностью заполнена).

### Удаление

Пробежка прекращается, когда находит группу с пустым слотом. Это влияет на удаление: при удалении из полностью заполненной группы мы не должны помечать слот как пустой, поскольку позже в последовательности пробежки могут быть использованы другие слоты, и это удаление приведет к преждевременному завершению пробежки. Вместо этого мы помечаем такие слоты как "удаленные" с помощью могилы. Если группа все еще имеет пустой слот, мы не нуждаемся в могиле и сразу помечаем слот как пустой. Вставка отдает предпочтение повторному использованию могил перед заполнением пустых слотов. В противном случае могилы очищаются только при росте, так как очистка на месте усложняет итерацию.

### Рост

Последовательность пробежки зависит от количества групп. Поэтому при увеличении количества групп все слоты должны быть перераспределены, чтобы соответствовать новой последовательности пробежки. Другими словами, вся таблица должна увеличиться одновременно.

Для поддержания инкрементального роста карта разделяет свои содержимое на несколько таблиц. Каждая таблица по-прежнему является полноценной хэш-таблицей, но отдельная таблица обслуживает только подмножество хэш-пространства. Рост происходит по отдельным таблицам, поэтому хотя вся таблица должна расти одновременно, каждый из этих ростов — это лишь небольшая часть карты. Максимальный размер одного роста ограничен максимальным размером таблицы, прежде чем она будет разделена на несколько таблиц.

Карта начинает с одной таблицы. До [maxTableCapacity] рост просто заменяет эту таблицу на таблицу с удвоенной вместимостью. После этого роста таблица делится на две.

Карта использует "расширяемое хэширование" для выбора таблицы. В расширяемом хэшировании мы используем верхние биты хэша как индекс в массив таблиц (называемый "директорией"). Количество используемых бит увеличивается по мере увеличения количества таблиц. Например, когда есть только 1 таблица, мы используем 0 бит (выбор не требуется). Когда их 2, мы используем 1 бит для выбора между 0-й и 1-й таблицей. [Map.globalDepth] — это количество бит, используемых в данный момент для выбора таблицы, и, соответственно (1 << globalDepth) — размер директории.

Обратите внимание, что каждая таблица имеет свой собственный коэффициент загрузки и растет независимо. Если первый бакет растет, он разделяется. Нам нужно 2 бита для выбора таблиц, хотя у нас будет 3 таблицы вместо 4. Мы поддерживаем это, позволяя нескольким индексам указывать на одну и ту же таблицу.

### Итерация

Итерация — это самая сложная часть карты из-за щедрых семантик итерации Go. Сводка семантик из спецификации:

1. Добавление и/или удаление записей во время итерации НЕ должно приводить к возвращению одной и той же записи более одного раза.
2. Записи, добавленные во время итерации, МОГУТ быть возвращены итерацией.
3. Записи, измененные во время итерации, ДОЛЖНЫ возвращать их последнюю версию.
4. Записи, удаленные во время итерации, НЕ должны быть возвращены итерацией.
5. Порядок итерации не определен. В реализации он явно случайным.

Если карта не растет, эти семантики просты: просто итерируйте по каждой таблице в директории и каждой группе и слоту в каждой таблице.

Если карта растет во время итерации, ситуация усложняется. Прежде всего, нам нужно отслеживать, какие записи мы уже вернули, чтобы удовлетворить (1). Существует три типа роста: а. Таблица заменена одной большей таблицей. б. Таблица разделена на две заменяющие таблицы. в. Рост директории (происходит как часть (б), если это необходимо).

Для всех этих случаев заменяющие таблицы будут иметь различную последовательность пробежки, поэтому просто отслеживание текущего индекса группы и слота недостаточно.

Мы решаем (а) и (б) тем, что итератор сохраняет ссылку на таблицу, по которой он в данный момент итерирует, даже после замены таблицы. Мы продолжаем итерацию по исходной таблице, чтобы сохранить порядок итерации и избежать нарушения (1). Все новые записи, добавленные только в заменяющие таблицы, будут пропущены (что разрешено (2)). Чтобы избежать нарушения (3) или (4), хотя мы используем исходную таблицу для выбора ключей, мы должны снова искать их в новых таблицах, чтобы проверить, были ли они изменены или удалены.

---

Общая идея

Тип map в Go — это хэш-таблица, которая обеспечивает быструю вставку, поиск и удаление элементов по ключу. Реализация основана на "Swiss Table" — современном подходе к открытой адресации (open addressing), оптимизированном для скорости за счет параллельной обработки слотов в группах и использования битовых операций. Однако Go добавляет свои особенности, такие как поддержка итерации с определенными семантиками и постепенного роста (incremental growth).

---

Терминология

1. Slot (слот):
    
    - Место хранения одной пары ключ/значение.
        
2. Group (группа):
    
    - Набор из 8 слотов (константа abi.SwissMapGroupSlots) плюс 8-байтовое контрольное слово.
        
3. Control word (контрольное слово):
    
    - 8-байтовое значение, где каждый байт соответствует одному слоту в группе:
        
        - 1 бит: Статус слота (пустой, удаленный, занят).
            
        - 7 бит: Младшие 7 бит хэша ключа (H2).
            
4. H1: Старшие 57 бит хэша (используются для выбора группы).
    
5. H2: Младшие 7 бит хэша (хранятся в контрольном слове для быстрого сравнения).
    
6. Table (таблица):
    
    - Полная хэш-таблица Swiss Table, состоящая из групп и метаданных для операций и роста.
        
7. Map:
    
    - Верхнеуровневый тип, содержащий ноль или более таблиц.
        
8. Directory (директория):
    
    - Массив указателей на таблицы, выбираемых по верхним битам хэша.
        

---

Основной принцип работы

Базовая структура

- map состоит из одной или нескольких таблиц (tables).
    
- Каждая таблица — это массив групп, где каждая группа содержит 8 слотов и контрольное слово.
    
- Поиск начинается с вычисления хэша ключа. H1 определяет начальную группу, а H2 используется для быстрого сравнения внутри группы.
    

Поиск (lookup)

1. Выбор группы: H1 (57 бит) используется как индекс в массиве групп с квадратичным пробированием (quadratic probing).
    
2. Параллельное сравнение: Внутри группы контрольное слово позволяет одновременно сравнить H2 искомого ключа с H2 всех 8 слотов с помощью битовых операций (см. ctrlGroup.matchH2).
    
3. Проверка: Если есть совпадения по H2 (вероятность ложного срабатывания ~0.7% из-за 7 бит), выполняется полное сравнение ключей.
    

Пробирование (probing)

- Используется квадратичное пробирование на основе H1 для выбора следующей группы, если текущая не содержит совпадения или пустой слот.
    
- Требование: количество групп — степень двойки, и пробирование заканчивается на группе с пустым слотом (таблица не может быть полностью заполнена).
    

---

Уникальные особенности

Удаление (deletion)

- Если слот удаляется в полностью заполненной группе, он помечается как "удаленный" (tombstone), а не пустой, чтобы не прерывать цепочку пробирования.
    
- Если в группе есть пустой слот, удаленный слот сразу становится пустым.
    
- При вставке приоритет отдается переиспользованию "удаленных" слотов.
    

Рост (growth)

- Рост одной таблицы требует полной перестройки из-за изменения последовательности пробирования.
    
- Чтобы поддерживать постепенный рост, map делит содержимое на несколько таблиц:
    
    - Каждая таблица обслуживает часть хэш-пространства.
        
    - Рост происходит по одной таблице за раз.
        
- Extendible hashing:
    
    - Верхние биты хэша (количество зависит от globalDepth) выбирают таблицу из директории.
        
    - При превышении maxTableCapacity таблица делится на две, и директория растет, если нужно.
        

Пример директории:

```text
globalDepth = 2 (4 записи):
[00] -> table1 (localDepth=1)
[01] -> table1 (localDepth=1)
[10] -> table2 (localDepth=2)
[11] -> table3 (localDepth=2)
```

---

Итерация

Итерация в Go сложна из-за строгих семантик (см. спецификацию):

1. Нельзя возвращать один элемент дважды.
    
2. Новые элементы могут быть пропущены.
    
3. Измененные элементы должны возвращать актуальное значение.
    
4. Удаленные элементы не возвращаются.
    
5. Порядок случайный.
    

Проблемы роста при итерации:

- Замена таблицы: Одна таблица заменяется большей.
    
- Разделение таблицы: Одна таблица делится на две.
    
- Рост директории: Увеличивается globalDepth.
    

Решение:

- Итератор фиксирует текущую таблицу и продолжает итерироваться по ней, даже если она заменена.
    
- Для актуальности данных (изменения/удаления) ключи перепроверяются в новых таблицах.
    
- При разделении пропускается вторая новая таблица в директории, чтобы избежать дублирования.

Реализация на Go (примерный набросок)

go

```go
type Map struct {
    directory []*table // Массив таблиц
    globalDepth int    // Количество бит для выбора таблицы
}

type table struct {
    groups []group   // Массив групп
    localDepth int    // Глубина таблицы
    loadFactor float32 // Фактор загрузки
}

type group struct {
    control [8]byte      // Контрольное слово
    slots   [8]slot      // 8 слотов
}

type slot struct {
    key   interface{}
    value interface{}
}

// Псевдокод поиска
func (m *Map) Get(key interface{}) interface{} {
    hash := hashKey(key)
    h1 := hash >> 7         // Старшие 57 бит
    h2 := byte(hash & 0x7F) // Младшие 7 бит
    tableIdx := h1 >> (64 - m.globalDepth)
    t := m.directory[tableIdx]
    
    for seq := probeSeq(h1, len(t.groups)); ; seq = seq.next() {
        g := &t.groups[seq.index]
        matches := matchH2(g.control, h2)
        for _, i := range matches {
            if equal(g.slots[i].key, key) {
                return g.slots[i].value
            }
        }
        if hasEmptySlot(g.control) {
            return nil // Не найдено
        }
    }
}
```

---

Почему Swiss Table?

1. Скорость: Параллельная проверка 8 слотов за одну операцию (с потенциалом для SIMD).
    
2. Эффективность памяти: Контрольное слово минимизирует накладные расходы.
    
3. Гибкость: Поддержка постепенного роста через директорию.
    

---

Итог

- map в Go — это многоуровневая Swiss Table с директорией таблиц.
    
- Поиск: H1 для пробирования, H2 для быстрого сравнения в группе.
    
- Рост: Постепенный через разделение таблиц и рост директории.
    
- Итерация: Сложная из-за семантик, решается фиксацией таблиц и перепроверкой.

---

Что сказано в комментарии?

В разделе "Probing" комментария явно указано:

Probing is done using the upper 57 bits (H1) of the hash as an index into the groups array. Probing walks through the groups using quadratic probing until it finds a group with a match or a group with an empty slot.

Здесь прямо говорится, что в реализации Go map используется квадратичное пробирование (quadratic probing) для выбора следующей группы в случае коллизии. Линейное пробирование (linear probing) в этом контексте не упоминается.

---

Разница между линейным и квадратичным пробированием

1. Линейное пробирование:
    
    - При коллизии проверяется следующий слот/группа с шагом +1: index + 1, index + 2, index + 3, ....
        
    - Простое, но приводит к кластеризации (primary clustering), когда занятые слоты образуют большие непрерывные блоки, ухудшая производительность.
        
2. Квадратичное пробирование:
    
    - Шаг увеличивается квадратично: index + 1², index + 2², index + 3², ... (или вариации, например, index + i² с учетом модуля).
        
    - Уменьшает кластеризацию, распределяя пробы более равномерно, но требует, чтобы размер таблицы был степенью двойки для корректной работы.
        

---

Почему в Go используется квадратичное пробирование?

1. Особенности Swiss Table:
    
    - Swiss Table — это открытая адресация (open addressing), где вместо цепочек (chaining) используется пробирование для разрешения коллизий.
        
    - В оригинальном дизайне Abseil Swiss Table действительно используется квадратичное пробирование, так как оно лучше распределяет элементы по таблице и снижает кластеризацию по сравнению с линейным пробированием.
        
    - Комментарий подтверждает, что Go следует этому подходу: "Probing walks through the groups using quadratic probing".
        
2. Инвариант размера:
    
    - Комментарий упоминает: "the number of groups must be a power of two". Это требование типично для квадратичного пробирования, так как оно гарантирует, что последовательность проб покрывает все группы без зацикливания (при условии, что таблица не полностью заполнена).
        
3. Отсутствие линейного пробирования в группах:
    
    - Внутри группы (8 слотов) пробирование не используется вовсе — все слоты проверяются параллельно с помощью контрольного слова и битовых операций (ctrlGroup.matchH2). Это устраняет необходимость линейного пробирования на уровне слотов.
        

---

Используется ли линейное пробирование где-то в map?

На основании комментария и типичного дизайна Swiss Table:

- На уровне групп: Нет, используется только квадратичное пробирование для выбора следующей группы в последовательности проб (probeSeq).
    
- На уровне слотов внутри группы: Здесь пробирование вообще не применяется, так как все 8 слотов проверяются одновременно через контрольное слово. Это ключевая фича Swiss Table, отличающая ее от классических хэш-таблиц с линейным пробированием.
    

Таким образом, в текущей реализации Go map линейное пробирование не используется. Вместо этого:

- Квадратичное пробирование применяется для перехода между группами.
    
- Параллельная проверка слотов внутри группы заменяет традиционное последовательное (линейное) сканирование.
    

---

Почему не линейное пробирование?

1. Кластеризация:
    
    - Линейное пробирование приводит к образованию больших кластеров занятых слотов, что увеличивает среднее количество проб для поиска свободного места или ключа.
        
2. Производительность:
    
    - Квадратичное пробирование лучше распределяет элементы, особенно в таблицах с высокой загрузкой, что важно для Swiss Table, где пробирование должно быть эффективным.
        
3. Совместимость с дизайном:
    
    - Swiss Table оптимизирована для работы с группами и параллельной проверки. Квадратичное пробирование лучше вписывается в эту модель, так как минимизирует количество групп, которые нужно проверять.

Реальный код (взгляд под капот)

В исходниках Go (например, runtime/map.go) нет прямого упоминания probeSeq, так как это часть внутренней логики Swiss Table, реализованной на низком уровне. Однако в файле runtime/hashmap.go (в старых версиях) или в текущей реализации можно найти следы квадратичного пробирования в логике работы с хэш-таблицами. Например, функция probeSeq могла бы выглядеть так (псевдокод):

go

```go
type probeSeq struct {
    index int
    step  int
}

func probeSeq(h1 uint64, size int) probeSeq {
    return probeSeq{index: int(h1 % uint64(size)), step: 1}
}

func (seq *probeSeq) next() probeSeq {
    seq.index = (seq.index + seq.step*seq.step) % size
    seq.step++
    return *seq
}
```

Это примерная реализация квадратичного пробирования, где шаг растет как квадрат числа итераций.

Итог

- В Go map используется только квадратичное пробирование на уровне выбора групп.
    
- Линейное пробирование не применяется ни на уровне групп, ни внутри групп (где используется параллельная проверка).
    
- Это соответствует дизайну Swiss Table и оптимизировано для производительности и равномерного распределения.
