## **1. Глубокая декомпозиция и выбор границ сервисов**

На сложных системах определение границ микросервисов становится критически важным. Неправильно выбранные границы могут привести к проблемам:

- **Чрезмерная связность (tight coupling):** Сервисы начинают зависеть друг от друга, теряя независимость.
- **Чрезмерная декомпозиция:** Слишком мелкие сервисы приводят к накладным расходам на коммуникацию.

#### **Продвинутые подходы к декомпозиции:**

1. **Design by Use Case:**
    
    - Определяйте микросервисы по конкретным сценариям использования.
    - Пример:
        - В интернет-магазине: обработка заказов, управление складом, обработка платежей.
2. **Event Storming (глубже):**
    
    - Включите всех заинтересованных лиц: аналитиков, разработчиков, владельцев продукта.
    - Разбейте процесс на события (например, `OrderCreated`, `PaymentProcessed`).
    - Группируйте события в домены:
        - Например, "оплата" → микросервис платежей.
        - "обработка заказов" → микросервис заказов.
3. **Contract-First Design:**
    
    - Определите, как сервисы будут взаимодействовать, до реализации:
        - Пример: JSON Schema или OpenAPI для описания контрактов.

## **2. Модели взаимодействия между сервисами**

### **Гибридная модель (синхронное + асинхронное взаимодействие):**

В сложных системах синхронное взаимодействие (например, REST) часто комбинируется с асинхронным (например, Kafka).

#### **Когда использовать что?**

1. **Синхронное взаимодействие:**
    
    - Используется, когда требуется немедленный ответ.
    - Пример: запрос состояния пользователя (`GET /user`).
2. **Асинхронное взаимодействие:**
    
    - Подходит для долгих операций и событий.
    - Пример: `OrderCreated` → обработка оплаты через очередь сообщений.

---

### **Асинхронные паттерны глубже:**

#### **Паттерн "Outbox":**

- Проблема: Гарантированная доставка сообщений в асинхронной архитектуре.
- Решение:
    - Вместо того чтобы сразу отправлять событие, сохраните его в локальной таблице (outbox).
    - Фоновый процесс читает из этой таблицы и публикует события.

Пример реализации:

```go
// Сохранение события в Outbox
func SaveOrder(order Order) error {
    tx := db.Begin()
    defer tx.Rollback()

    // Сохранение заказа
    if err := tx.Save(&order).Error; err != nil {
        return err
    }

    // Сохранение события в Outbox
    event := Event{Type: "OrderCreated", Payload: order}
    if err := tx.Save(&event).Error; err != nil {
        return err
    }

    return tx.Commit().Error
}
```

## **3. Управление согласованностью**

В микросервисах часто приходится жертвовать сильной согласованностью ради высокой доступности. Рассмотрим глубже паттерны согласованности:

### **1. Eventual Consistency через репликацию:**

- Пример: Сервис A записывает данные, а сервис B реплицирует их через поток событий.
- Используется, например, в системах, построенных на основе Kafka.

---

### **2. Чёткий и нечёткий консенсус:**

- Пример: Система распределённой базы данных (например, **Raft**, **Paxos**).
- Если несколько узлов системы не могут согласовать результат:
    - **Чёткий консенсус:** Операция блокируется.
    - **Нечёткий консенсус:** Возвращается "лучший возможный" результат.

---

### **3. Strong Consistency через двухфазные транзакции (2PC):**

- Используется, если требуется строгая согласованность:
    - Пример: Перевод денег между банками.

## **4. Масштабирование и отказоустойчивость**

### **1. Горизонтальное масштабирование (Deep Dive):**

- Распределение нагрузки через Load Balancer.
- Для минимизации состояния используйте:
    - Redis (кэш).
    - Базы данных для хранения длинных состояний.

---

### **2. Anti-Patterns масштабирования:**

1. **"Chatty" микросервисы:**
    
    - Проблема: Сервисы постоянно обмениваются большим количеством мелких запросов.
    - Решение: Агрегация данных в API Gateway.
2. **Централизация:**
    
    - Проблема: Один сервис становится "узким местом" системы.
    - Решение: Разделите логику и данные.

---

### **3. Репликация базы данных:**

Используйте Primary-Replica архитектуру:

- **Primary**: Обработка записи.
- **Replica**: Только чтение.

## **5. Расширенные паттерны отказоустойчивости**

### **1. Circuit Breaker глубже:**

Когда один сервис выходит из строя, важно защитить другие.

Пример реализации:

```go
type CircuitBreaker struct {
    failureCount int
    threshold    int
    timeout      time.Duration
    state        string
}

func (cb *CircuitBreaker) Call(request func() error) error {
    if cb.state == "open" {
        return errors.New("circuit is open")
    }

    err := request()
    if err != nil {
        cb.failureCount++
        if cb.failureCount >= cb.threshold {
            cb.state = "open"
            go cb.resetAfterTimeout()
        }
        return err
    }

    cb.failureCount = 0
    return nil
}

func (cb *CircuitBreaker) resetAfterTimeout() {
    time.Sleep(cb.timeout)
    cb.state = "half-open"
}
```

---

### **2. Load Shedding (Сбрасывание нагрузки):**

- Когда система перегружена, отбрасывайте "менее важные" запросы.
- Пример: API сервиса новостей может отказаться отдавать комментарии, если основная система перегружена.
