## **1. Ультрамасштабируемые системы**

На больших масштабах микросервисы сталкиваются с проблемами, которые обычные проекты даже не видят. Разберёмся, как проектировать системы, которые выдерживают **десятки миллионов запросов в секунду**.

---

### **1.1. Дизайн глобальных распределённых систем**

Когда ты проектируешь систему для глобального использования, нужно учитывать:

1. **Географическое распределение пользователей.**
    
    - Используй **Anycast DNS**, чтобы направлять запросы в ближайший дата-центр.
    - Разделяй данные между регионами:
        - Пример: Пользователи из Европы обслуживаются в европейском дата-центре.
2. **Консистентность между регионами:**
    
    - Используй **CRDT (Conflict-Free Replicated Data Types)**:
        - Это структуры данных, которые автоматически разрешают конфликты при репликации.
        - Пример: Google Drive использует CRDT для синхронизации документов.
3. **Гибридное хранилище данных:**
    
    - Разделение данных на **горячие** (часто используемые) и **холодные** (редко используемые).
    - Пример:
        - Redis (горячие данные).
        - S3 (холодные данные).

---

### **1.2. Многослойное кэширование**

Кэширование — основа масштабируемости. Рассмотрим несколько слоёв:

1. **Локальный кэш (In-memory):**
    
    - Каждый экземпляр сервиса хранит кэш в оперативной памяти.
    - Пример: Использование **LRU-кэша**:
        
        ```go
        type LRUCache struct {
            data map[string]string
            max  int
        }
        ```
        
2. **Глобальный кэш (Redis/Memcached):**
    
    - Централизованное кэширование, чтобы данные могли использоваться всеми сервисами.
3. **CDN (Content Delivery Network):**
    
    - Распространение статического контента (например, изображения) через сеть CDN.
    - Пример: Cloudflare, Akamai.

---

### **1.3. Архитектура "Hot-Sharding"**

Когда данные распределяются по шардам, не все шардированные данные загружены одинаково. **Hot-Sharding** помогает решать проблемы перегрузки отдельных шардов.

#### Пример решения:

1. Измеряй нагрузку на каждый шард.
2. Автоматически переназначай горячие ключи на отдельные шарды:
    - Используй **consistent hashing with virtual nodes**.

## **2. Высокая доступность (High Availability)**

### **2.1. Архитектура Active-Active**

- Все дата-центры работают одновременно и обрабатывают запросы. Но возникает проблема консистентности.
- Решение:
    - Используй **DynamoDB-like архитектуру**:
        - Данные реплицируются между узлами.
        - Конфликты разрешаются через **vector clocks**.

---

### **2.2. Система, устойчивая к отказам**

1. **Redundancy (Избыточность):**
    
    - Убедись, что у тебя есть минимум два экземпляра каждого сервиса в разных дата-центрах.
2. **Chaos Engineering:**
    
    - Практикуй отключение частей системы (например, отключи один из дата-центров).
    - Инструменты: **Netflix Chaos Monkey**.

---

## **3. Управление сложностью в микросервисах**

### **3.1. Сервисная сетка (Service Mesh): продвинутые аспекты**

1. **Политики безопасности:**
    
    - Ограничивай, кто может общаться с кем.
    - Пример: "Сервис аутентификации может общаться только с базой данных пользователей".
2. **Трассировка данных:**
    
    - Включи детальную трассировку, чтобы видеть весь путь запроса через десятки сервисов.

---

### **3.2. Отложенные задачи и очереди сообщений**

1. Используй **очереди с дедлайнами**:
    
    - RabbitMQ или Kafka.
    - Пример: Если задача не обработана в течение X секунд, она отправляется в Dead Letter Queue.
2. **Компенсации через Workflow Orchestration:**
    
    - Используй **Temporal.io** для создания сложных оркестраций.

---

## **4. Алгоритмы и структуры данных для больших нагрузок**

### **4.1. Алгоритмы маршрутизации запросов**

1. **Weighted Round Robin:**
    - Запросы направляются к сервисам с учётом их веса (мощности).
2. **Least Connections:**
    - Направляй запросы к сервису с наименьшим количеством активных соединений.

---

### **4.2. Эффективные структуры данных**

1. **Bloom Filters:**
    
    - Структура данных для проверки существования элемента.
    - Пример: Используй в кэше для определения, нужно ли запрашивать данные из базы.
2. **HyperLogLog:**
    
    - Для подсчёта уникальных значений в больших наборах данных.
    - Пример: "Сколько уникальных пользователей посетило сайт за день?"

---

## **5. Подготовка к самым сложным вопросам**

### **5.1. Как бы ты справился с "сплит-брейном" в системе?**

1. **Проблема:**
    - Когда сеть разделена, два узла могут считать себя "мастерами".
2. **Решение:**
    - Используй алгоритмы консенсуса, такие как Raft или Paxos.

---

### **5.2. Как ты будешь балансировать нагрузку в глобальной системе?**

1. **Ответ:**
    - Используй **Global Load Balancer** (например, AWS Global Accelerator).
    - Настрой географический приоритет.

---

### **5.3. Что делать, если Kafka перегружена?**

1. **Ответ:**
    - Включи **Backpressure**.
    - Используй разделение тем на основе приоритетов.
