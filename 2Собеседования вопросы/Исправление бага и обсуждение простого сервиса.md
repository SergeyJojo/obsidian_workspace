
### Задача: Исправление бага и обсуждение простого сервиса

Давайте разберём код и обсудим, как исправить баг, связанный с **data race** и предложим улучшения для синхронизации.

#### Проблемы в исходном коде:

1. **Data Race**: В горутине обновления курсов (`go func()`), которая работает асинхронно, и в хэндлере HTTP-запросов происходит доступ к переменной `rates`. Это может привести к **data race**, так как горутина записывает в эту переменную, а HTTP-хэндлер может одновременно её читать.
2. **Проблема с обновлением переменной `rates` при ошибке**: Если функция `readConversionRates()` вернёт ошибку, переменная `rates` будет обновлена на `nil`, что может привести к неверному состоянию данных. В случае ошибки нужно оставить старое значение переменной `rates`.

### Решение:

#### 1. **Исправление data race**

Чтобы решить проблему с **data race**, нужно синхронизировать доступ к переменной `rates` с помощью мьютекса. Это обеспечит, что только одна горутина будет одновременно изменять или читать значение из `rates`.

- Мы можем использовать **`sync.Mutex`** для синхронизации, либо **`sync.RWMutex`** для более тонкой настройки (чтение в нескольких горутинах, запись — в одной).
- Важно, чтобы мы блокировали только доступ к самой переменной `rates`, а не всю работу с функцией `readConversionRates()`.

#### 2. **Оставляем старое значение в случае ошибки**

Чтобы не потерять старое значение в случае ошибки при обновлении курсов, лучше сначала читать данные в промежуточную переменную и только затем обновлять `rates`, если не было ошибок.

### Исправленный код:

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"sync"
	"time"
)

// Client struct to hold conversion rates
type Client struct {
	rates       map[string]float64
	mu          sync.RWMutex
}

// readConversionRates reads rates from a file or an external service (relatively long-running function).
func readConversionRates() (map[string]float64, error) {
	// Here we simulate a network request or long-running task
	time.Sleep(100 * time.Millisecond)

	return map[string]float64{
		"USD": 1.0,
		"RUB": 70.0,
	}, nil
}

func (c *Client) startUpdatingRates() {
	go func() {
		for {
			// periodically update conversion rates
			time.Sleep(time.Minute)

			// Read rates in a temporary variable
			tmpRates, err := readConversionRates()
			if err != nil {
				log.Printf("ERR: update conversion rates: %s", err)
				continue
			}

			// Lock and update rates atomically
			c.mu.Lock()
			c.rates = tmpRates
			c.mu.Unlock()
		}
	}()
}

func (c *Client) handleConversion(w http.ResponseWriter, r *http.Request) {
	// Parse 'from' and 'value' from query params
	from := "RUB"
	val := 140.0

	// Lock for reading the rates safely
	c.mu.RLock()
	rate, ok := c.rates[from]
	c.mu.RUnlock()

	if !ok {
		http.NotFound(w, r)
		return
	}

	convVal := val / rate

	// Respond with the converted value
	fmt.Fprint(w, convVal)
}

func main() {
	// Initialize the client
	client := &Client{}
	client.rates = map[string]float64{
		"USD": 1.0,
		"RUB": 70.0,
	}

	// Start background task to periodically update rates
	client.startUpdatingRates()

	http.HandleFunc("/", client.handleConversion)

	if err := http.ListenAndServe(":8080", nil); err != http.ErrServerClosed {
		log.Fatal(err)
	}
}
```

### Разбор изменений:

1. **Синхронизация с мьютексом**:
    
    - Мы добавили **`sync.RWMutex`** в структуру `Client`, чтобы можно было безопасно читать и записывать данные в `rates`.
    - В методе `startUpdatingRates` используется `Lock` для записи в `rates` и `RLock` для безопасного чтения данных в хэндлере `handleConversion`.
2. **Промежуточная переменная для обновления курсов**:
    
    - В горутине для обновления курсов мы сначала загружаем новые курсы в промежуточную переменную `tmpRates`. Только если чтение прошло успешно, мы записываем в `rates`, защищённое мьютексом.
3. **Исправление проблем с ошибками**:
    
    - Теперь при ошибке в обновлении курсов старое значение `rates` остаётся неизменным. Мы продолжаем с предыдущими курсами, если новая загрузка не удалась.

### Дополнительные улучшения:

1. **Graceful shutdown**: Чтобы корректно завершать работу сервиса при остановке, можно добавить обработку сигналов с помощью `context` или стандартного `signal.Notify` для закрытия HTTP-сервера и завершения горутин.
    
2. **Нагрузочное тестирование**: Хорошая практика — провести нагрузочное тестирование, например, с использованием `ab`, `wrk` или `hey`, чтобы убедиться в том, что приложение работает корректно при высоких нагрузках и на больших объемах данных.
    
3. **Использование трассировки**: Если система работает в распределенной среде, можно добавить поддержку распределённой трассировки, передавая информацию в контексте (`ctx`), чтобы отслеживать выполнение запросов.
    
4. **`-race` флаг**: Для обнаружения **data race** можно использовать флаг `-race`, который поможет выявить гонки данных при компиляции или выполнении программы:
    
    ```bash
    go run -race main.go
    ```

### Ответы на дополнительные вопросы:

1. **Сколько горутин в этом приложении?**
    
    - Есть одна горутина, которая обновляет курсы каждую минуту, и основная горутина, которая обслуживает HTTP-запросы. Всего — 2 горутины.
2. **Что такое graceful shutdown?**
    
    - Это процесс корректного завершения работы приложения, включая закрытие всех активных соединений и завершение горутин, до того как процесс завершится.
3. **Как искать data race баги в Go?**
    
    - Используйте флаг `-race` при компиляции или запуске программы, чтобы Go-рантайм проверил наличие гонок данных.
4. **Разница между `Mutex` и `RWMutex`?**
    
    - **Mutex** позволяет одному процессу захватывать блокировку, тогда как **RWMutex** позволяет нескольким горутинам читать одновременно, но блокирует запись, когда один процесс записывает данные.
