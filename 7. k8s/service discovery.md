
**Service discovery** (обнаружение сервисов) — это механизм, который позволяет **сервисам находить друг друга** в распределённой системе (например, в Kubernetes или микросервисной архитектуре) **автоматически**, без ручной настройки IP-адресов или портов.

---

## 📌 Зачем нужен service discovery?

В микросервисной архитектуре:

- У тебя десятки и сотни сервисов.
    
- Они могут масштабироваться (менять количество реплик).
    
- Их IP-адреса динамичны (меняются при перезапуске).
    

→ жёстко прописать IP-адреса невозможно и небезопасно.

**Service discovery решает эту проблему** — сервисы находят друг друга по **именам**, как по DNS.

---

## 🔧 Как устроен Service Discovery?

### 🔹 Основные компоненты:

|Компонент|Назначение|
|---|---|
|**Service Registry**|Хранилище информации о доступных сервисах (их адреса, порты, статусы)|
|**Service Provider**|Сервис, который регистрирует себя в реестре|
|**Service Consumer**|Сервис, который ищет другого и получает его адрес|

---

## 📦 Пример на Kubernetes

### 📍 В Kubernetes discovery встроен "из коробки".

- Ты создаёшь `Service` — и Kubernetes автоматически:
    
    - Создаёт DNS-имя (например, `my-backend.default.svc.cluster.local`)
        
    - Проксирует на все Pod'ы, которые соответствуют селектору
        

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-backend
spec:
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8080
```

Теперь любой другой pod может обратиться к `http://my-backend` — и Kubernetes сам найдёт IP-адрес нужного Pod'а и сделает балансировку.

## ⚙️ Виды Service Discovery

|Тип|Пример|Описание|
|---|---|---|
|**Client-side**|Consul, Eureka|Клиент сам запрашивает список доступных инстансов и выбирает нужный|
|**Server-side**|Kubernetes|Клиент обращается к DNS или виртуальному IP, а маршрутизация идёт на уровне платформы|
|**DNS-based**|Kubernetes DNS, AWS Route 53|Используется DNS для получения IP по имени|
|**API-based**|Consul API, etcd API|Клиенты получают данные о сервисах через HTTP API|

---

## 💬 Пример: Service Discovery с Consul

### 🔹 Сервис А регистрируется:

```bash
consul agent -register \
  -name=my-api \
  -address=10.0.1.25 \
  -port=8080
```

### 🔹 Сервис B делает запрос:

```bash
GET http://localhost:8500/v1/catalog/service/my-api
```

→ Получает список живых инстансов `my-api`.

---

## 📶 Как определяется, что сервис "живой"?

Service discovery часто интегрирован с **health checks**:

- В Kubernetes: через `readinessProbe`, `livenessProbe`
    
- В Consul: `check_http`, `check_script`
    
- В Eureka: периодический "пинг"
    

Если сервис не отвечает → его исключают из списка доступных.

## 💡 Use-cases

- Балансировка между репликами микросервиса
    
- A/B-тестирование (направление трафика на разные версии)
    
- Смена окружения без изменения клиента (staging/prod)
    
- Автоматическое подключение к базам, очередям и пр.
    

---

## 🆚 Сравнение инструментов

|Инструмент|Тип|Особенности|
|---|---|---|
|**Kubernetes**|Server-side + DNS|Встроенный, автоматический, подходит для k8s|
|**Consul**|Client-side + API|Гибкий, работает вне Kubernetes|
|**Eureka (Spring)**|Client-side|Используется в Spring экосистеме|
|**etcd**|Low-level KV|Используется как база, но не как discovery из коробки|
|**Zookeeper**|API-based|Надёжный, но сложный, чаще для Kafka/Hadoop|

---

## 📍 Вывод

Service Discovery — **краеугольный камень микросервисов**. Без него:

- нельзя масштабировать сервисы
    
- нельзя изменять инфраструктуру без даунтайма
    
- нельзя обеспечить надёжность и отказоустойчивость
