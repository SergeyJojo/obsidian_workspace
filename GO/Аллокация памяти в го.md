В Go память управляется специальным аллокатором, который является частью **Go runtime**. Этот аллокатор — это сложная система, которая разбивает память на несколько структур и использует различные подходы для управления памятью, чтобы эффективно обрабатывать как маленькие, так и большие выделения. В Go это особенно важно, так как Go активно работает с многопоточностью и использует собственную систему сборки мусора. Аллокатор памяти Go делит память на несколько уровней: **страницы**, **арены**, **спаны** и **кучу**.

### Основные структуры в Go Memory Allocator:

1. **Страницы (Pages)**: Страницы — это наименьшая единица памяти, которая управляется Go. Каждая страница имеет фиксированный размер (обычно 8192 байта или 8 КБ). Страницы являются атомарными единицами управления памяти, и они не делятся на более мелкие части. Это позволяет быстро и эффективно управлять памятью и ускорить процессы выделения.
    
    Страницы Go предназначены для работы с **маленькими объектами** и для оптимизации работы с **кучей**. Каждая страница может быть помечена как **свободная** или **занятая** в зависимости от того, используется ли она в данный момент или нет.
    
2. **Спаны (Spans)**: Спаны — это блоки памяти, состоящие из нескольких страниц. Это структура, которую Go использует для эффективного управления небольшими объектами, которые занимают немного памяти, но требуют большого количества операций выделения. Спаны содержат несколько страниц, и каждый спан обычно выделяется для хранения объектов одного размера.
    
    Когда Go выделяет память для объектов, оно сначала ищет подходящий **спан**, который имеет подходящий размер для объекта. Если подходящий спан не найден, он пытается выделить новый спан или использовать свободные страницы, если таковые имеются.
    
3. **Арены (Arenas)**: Арена — это более высокоуровневая структура, состоящая из нескольких спанов. Она управляет несколькими спанами и представляет собой некоторую область памяти, из которой могут выделяться блоки для нужд программы. Это также служит как контейнер для страницы памяти, который позволяет эффективно управлять большим количеством объектов.
    
    Арены используются для упрощения и ускорения поиска памяти. На низком уровне Go работает с отдельными страницами, но когда нужно выделить несколько объектов, то идет работа с аренами.
    
4. **Куча (Heap)**: Куча — это область памяти, из которой Go выделяет память для объектов, у которых время жизни больше, чем у обычных локальных переменных. Например, объекты, выделенные с помощью `new()` или `make()`, или объекты, которые передаются между горутинами, будут выделяться на куче. Это требует тщательного управления памятью, так как объекты на куче могут быть намного большими, чем обычные локальные переменные.
    

### Как происходит процесс выделения памяти:

Когда Go-программа запрашивает память (например, когда выполняется вызов `new()` или `make()`), это процесс проходит через несколько уровней:

1. **Выделение страниц**:
    
    - Go runtime начинает с того, что запрашивает страницы памяти у операционной системы. Это может быть как одна страница, так и несколько сразу, если ожидается, что память будет использоваться в большом количестве.
        
    - Страницы обычно выделяются через системные вызовы, такие как `mmap()` в Linux или `VirtualAlloc()` в Windows.
        
2. **Использование арены и спана**:
    
    - Когда выделяется память для объектов одного размера, она будет идти в **спан**.
        
    - Если память выделяется для объектов разного размера, то будет использоваться **арена**.
        
    - Каждый спан или арена управляется с учётом стратегии выделения памяти и оптимизаций для многопоточности.
        
3. **Разделение на объекты**:
    
    - После того как выделены страницы и/или спаны, Go приступает к выделению **объектов**. Когда требуется выделить несколько объектов одного размера, они будут распределяться по страницам.
        
    - Каждый объект имеет свой собственный **метаданные** в памяти, которые могут включать информацию о его размере, ссылках на другие объекты и другие параметры.
        
4. **Управление памятью в многозадачности**:
    
    - Go использует **многозадачность** и управляет кучей с учётом горутин. Это может требовать выделения памяти для разных потоков. Поэтому Go имеет продвинутое управление локальными кэшами для потоков, чтобы минимизировать конкуренцию за память и ускорить операции.
        
5. **Гарbage Collection (GC)**:
    
    - Go имеет сборщик мусора, который занимается очисткой неиспользуемых объектов. Сборщик мусора отслеживает объекты, которые больше не используются, и освобождает память, что предотвращает утечки памяти.
        
    - Память на куче может быть освобождена сборщиком мусора, который помечает объекты как неиспользуемые и очищает их.
        

### Этапы аллокации в Go (по шагам):

1. **Запрос памяти**: Когда Go-программа запрашивает выделение памяти, операционная система выделяет несколько страниц (в зависимости от размера запроса).
    
2. **Создание спана**: Для объектов одного размера создаётся спан, в котором будет храниться память.
    
3. **Создание арены**: Для более сложных объектов, которые требуют множества спанов, создаётся арена.
    
4. **Использование памяти**: После выделения памяти объекты могут быть распределены по страницам, а в случае многозадачности — также кэшированы в локальных потоках.
    
5. **Сборка мусора**: Через определённые интервалы времени запускается сборщик мусора, который очищает неиспользуемую память.
    

### Пример:

Предположим, что вы выделяете память для объекта типа `struct`. Go runtime сначала проверяет, существует ли подходящий спан для хранения этих объектов. Если спан найден, память выделяется из этого спана. Если спан отсутствует, то Go выделяет новую страницу или арены для хранения объектов.

### Заключение:

Аллокатор памяти Go использует несколько уровней абстракции (страницы, спаны, арены, куча), чтобы эффективно управлять памятью. Это обеспечивает высокую производительность при выделении и освобождении памяти, а также оптимизацию для многозадачности. Аллокатор памяти Go имеет большое значение для оптимизации работы приложений, так как позволяет эффективно управлять памятью, минимизируя накладные расходы на выделение и освобождение памяти.
