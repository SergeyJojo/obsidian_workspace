
В Go работа с файлами и сетевыми соединениями строится на единой абстракции — **интерфейсах `io.Reader` и `io.Writer`**, но под капотом есть ключевые различия в работе рантайма и планировщика. Разберём детали.

---

## **1. Работа с файлами в Go**
### **Основные особенности**
- Используются **блокирующие системные вызовы** (если не включён `O_NONBLOCK`).
- **Нет автоматического асинхронного I/O** (как в `io_uring` или `epoll` для сетевых операций).
- **Планировщик Go не вмешивается** в файловые операции (горутина блокируется на время syscall).

### **Пример чтения файла**
```go
file, err := os.Open("data.txt")  // syscall: open()
if err != nil { ... }

buf := make([]byte, 1024)
n, err := file.Read(buf)  // Блокирующий read()
if err != nil { ... }
```
**Что происходит:**
1. Вызов `file.Read()` приводит к системному вызову `read()`.
2. Горутина блокируется **на уровне ядра**, пока данные не будут готовы.
3. Планировщик Go не может вытеснить эту горутину — она освободит поток (`M`) только после завершения syscall.

### **Проблемы**
- **Блокировка потока**: Каждая горутина, работающая с файлом, удерживает системный поток (`M`).
- **Низкая производительность** при множестве файловых операций (нет асинхронности по умолчанию).

**Обходные пути:**
1. Использовать **отдельные потоки** через `goroutine` + `runtime.LockOSThread()`.
2. Применять **асинхронные интерфейсы** вручную (например, через `syscall.SetNonblock` + `epoll`).
3. Использовать **пакет `aio`** (если поддерживается ОС).

## **2. Работа с сетевыми соединениями в Go**
### **Основные особенности**
- Используется **неблокирующий I/O** + **event-loop на основе `epoll`/`kqueue`**.
- **Интеграция с планировщиком**: Горутины блокируются на уровне Go, а не ядра.
- **Высокий уровень абстракции** (`net.Conn`, `http.Server`).

### **Пример чтения из сети**
```go
conn, err := net.Dial("tcp", "example.com:80")
if err != nil { ... }

buf := make([]byte, 1024)
n, err := conn.Read(buf)  // Неблокирующий read() + epoll
if err != nil { ... }
```
**Что происходит:**
1. Вызов `conn.Read()` регистрирует FD сокета в **netpoller** (обёртка вокруг `epoll`/`kqueue`).
2. Если данных нет, горутина **пакуется в `gopark`** и освобождает поток (`M`).
3. Когда данные приходят, netpoller будит горутину, и она продолжает работу.

### **Архитектура netpoller**
1. **Отдельный системный поток** (`runtime/netpoll.go`) ждёт событий через `epoll_wait`.
2. При получении события (например, `EPOLLIN`):
   - Находит связанную горутину.
   - Ставит её в очередь на выполнение.
3. **Планировщик Go** запускает разблокированную горутину на свободном потоке (`M`).

### **Почему это эффективно?**
- **1 поток (`M`) может обслуживать 10k+ соединений**.
- **Горутины блокируются без блокировки потоков**.
- **Нет накладных расходов** на переключение контекста ядра.

---

## **3. Ключевые различия**
| **Критерий**         | **Файлы**                          | **Сетевые соединения**            |
|----------------------|-----------------------------------|----------------------------------|
| **Блокировка**       | Блокирует системный поток (`M`)    | Блокирует только горутину        |
| **Механизм I/O**     | Блокирующие syscall (`read`/`write`) | Неблокирующий I/O + `epoll`      |
| **Планировщик Go**   | Не участвует                      | Интегрирован с netpoller         |
| **Масштабируемость** | Низкая (1 поток на операцию)      | Высокая (1 поток на 1000+ conn)  |
| **Асинхронность**    | Только вручную (`O_NONBLOCK` + `epoll`) | Встроенная (netpoller)          |

## **4. Как улучшить работу с файлами?**
### **Вариант 1: Использовать `os.File` с `O_NONBLOCK` + `epoll`**
```go
fd, _ := syscall.Open("file.txt", syscall.O_RDONLY|syscall.O_NONBLOCK, 0)
// Вручную добавляем в epoll (как в netpoller)
```
**Минусы**: Сложно, нет готовых решений в stdlib.

### **Вариант 2: Вынести файловый I/O в отдельные потоки**
```go
go func() {
    runtime.LockOSThread()  // Фиксируем поток
    data, _ := os.ReadFile("largefile.bin")
    ch <- data
}()
```
**Плюсы**: Просто, изолирует блокирующие вызовы.

### **Вариант 3: Использовать `io_uring` (экспериментально)**
```go
// Через сторонние библиотеки (например, `liburing` или `go-uring`)
```
**Плюсы**: Максимальная производительность (асинхронный I/O).

---

## **Вывод**
- **Сетевые операции** в Go оптимизированы через `netpoller` и работают асинхронно.
- **Файловый I/O** по умолчанию блокирующий, но можно адаптировать под асинхронность.
- Для высоконагруженных файловых операций стоит рассмотреть **отдельные потоки** или **`io_uring`**.

Если нужна максимальная производительность с файлами, можно заимствовать подход из `netpoller`, но в стандартной библиотеке этого нет — приходится использовать костыли или сторонние решения.
