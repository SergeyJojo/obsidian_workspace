Ты хочешь понять, **как в Go-аллокаторе работают аллокации больших объёмов памяти**, например:
- От 32KB
- От 1MB и выше

Это отличный вопрос — он касается **внутреннего устройства рантайма Go**, особенно как работает **`runtime.mallocgc()`**.

---

# 🧠 Как устроен аллокатор Go?

Go использует **разные стратегии для объектов разного размера**:
- **Маленькие (< 16B)** → `tinyAlloc`
- **Средние (до 32KB)** → через size classes
- **Большие (> 32KB)** → напрямую через `mheap.alloc_m`
- **Очень большие (> 1MB)** → через `largeAlloc`

---

## 🔁 Классификация по размеру:

| Размер | Используется |
|--------|--------------|
| < 16B  | `tinyAlloc` |
| 16B–32KB | `sizeclass pool` |
| > 32KB | `largeAlloc`, прямая работа с `mheap` |
| > 1MB | `persistentalloc` или `sysAlloc` |

---

# ✅ Подробнее: аллокация от 32KB и выше

## 1. Объекты > 32KB

Для них Go **не использует `mcache` или `mcentral`**, а сразу обращается к глобальному пулу `mheap`.

### Что происходит:

```go
if size >= _MaxSmallSize {
    // _MaxSmallSize == 32KB
    return largeAlloc(size, typ, needzero)
}
```

### a) Вызывается `largeAlloc()`
- Он вызывает `mheap.alloc_m(npages)`
- Где `npages = size / pageSize` (pageSize = 8KB)

👉 То есть, если ты запрашиваешь 34KB → это будет 5 страниц (`34 / 8 ≈ 4.25 → округление вверх до 5 → 40KB`)

---

## 2. Пример: выделение 34KB

```go
data := make([]byte, 34<<10) // 34KB
```

Происходит:
- Проверка размера: больше `_MaxSmallSize` (32KB)
- Перейти в `largeAlloc`
- Вызвать `mheap.alloc_m(npages)` (5 страниц)
- Получить указатель на 40KB блок
- Вернуть его как `[]byte` длиной 34KB

---

## 3. Объекты > 1MB

> Для таких объектов Go использует **`persistentalloc`** или **`sysAlloc`**

Если ты делаешь:

```go
bigData := make([]byte, 1<<20) // 1MB
```

→ Это уже "большой" объект.

Внутри Go:
- Не добавляет его в `mcache` или `mspan`
- Выделяет через `sysAlloc` (вызов `mmap` на Linux)
- Может использовать `huge page`, если система поддерживает

---

## 📦 Что такое `sysAlloc`?

- Это низкоуровневый вызов
- Возвращает чистую память из системы
- Без фрагментации
- Страницами по 8KB (или больше при использовании huge pages)

```text
+---------------------+
| sysAlloc            |
|                     |
| mmap(size)          |
| mprotect            |
+----------↓----------+
           ↓
+---------------------+
| runtime.largeAlloc  |
|                     |
| npages = size >> 13 |
| span := alloc_m(...) |
+----------↓----------+
           ↓
+---------------------+
| runtime.mallocgc    |
| возвращает unsafe.Pointer |
+---------------------+
```

---

## 🔄 Чем отличаются аллокации:

| Размер | Механизм | Производительность | GC |
|--------|----------|--------------------|----|
| < 16B  | tinyAlloc | ✅ Очень быстро     | ❌ Мало метаданных |
| 16B–32KB | small object pool | ✅ Быстро        | ✅ Тренируется |
| > 32KB | `largeAlloc` + `mheap` | ⬇️ Медленнее   | ✅ Да |
| > 1MB | `sysAlloc` / `mmap` | ❗ Зависит от системы | ✅ Да |
| > 10MB | `persistentalloc` | ✅ Работает напрямую с системой | ✅ Да |

---

## 🛠 Как проверить поведение аллокатора?

Используй `pprof`:

```go
import _ "net/http/pprof"
_ = http.ListenAndServe(":6060", nil)
```

Затем:

```bash
go tool pprof http://localhost:6060/debug/pprof/heap
```

---

## 🧱 Как влияет на производительность?

| Размер | GC давление | Аллокации | Фрагментация |
|-------|--------------|------------|---------------|
| 32KB | ⬆️ Умеренное | ❗ Медленная аллокация |
| 1MB  | ❗ Высокое    | ❗ Вызывает `mmap` |
| 10MB | ❗ Очень высокое | ⬆️ Нужны lock'и |
| 100MB| ❌ Неэффективно | ❌ Лучше не делать так |

---

## 📊 Когда что использовать?

| Размер | Рекомендация |
|--------|---------------|
| < 16B  | ✅ Использовать `sync.Pool` |
| 16B–32KB | ✅ Использовать `make([]T, ...)` |
| > 32KB | ⚠️ Использовать аккуратно |
| > 1MB | ❌ Избегать частых аллокаций |
| > 10MB | ❌ Только если нет выбора |

---

## 🧪 Пример: аллокация 1MB

```go
func main() {
	data := make([]byte, 1<<20) // 1MB
	_ = data[0]               // чтобы компилятор не оптимизировал
}
```

При этом:
- Выделяется 129 страниц (`1MB / 8KB = 128 → 129`)
- Берётся мьютекс `mheap`
- Выделяется через `mmap` (на Linux)

---

## 📌 Какие структуры задействованы?

| Структура | Описание |
|-----------|-----------|
| `mspan` | Описывает выделенный блок памяти |
| `mheap` | Глобальный менеджер памяти |
| `mcentral` | Хранится в каждом P |
| `mcache` | Локальный кэш для маленьких объектов |
| `arena` | Большой регион памяти, используется рантаймом |
| `heapArena` | Управление областями heap'а |

---

## 🧰 Советы по работе с большими объектами

| Что делать | Почему |
|------------|--------|
| Используй `sync.Pool` | Для повторного использования |
| Не делай много аллокаций > 1MB | Они замедляют GC |
| Используй `unsafe.Pointer` аккуратно | Можно сломать GC |
| Используй `mmap` напрямую | Для контроля над памятью |
| Избегай множественных `make([]byte, 1<<20)` | Лучше один большой буфер |
| Используй `GODEBUG=malloc=1` | Для диагностики аллокаций |
| Используй `GOGC=off` только для тестов | Чтобы понять, сколько выделяется |
