## **1. Индексы: абсолютный контроль**

---

### **1.1. Индексы с примерами реальной пользы**

1. **Индексы для многоколоночных запросов**
    
    - Если вы часто фильтруете или сортируете по нескольким колонкам одновременно:
        
        ```sql
        CREATE INDEX idx_multicolumn ON table_name (column1, column2);
        ```
        
    - Пример использования:
        
        ```sql
        SELECT * FROM table_name WHERE column1 = 'value1' AND column2 = 'value2';
        ```
        
    
    **ВАЖНО**: Порядок колонок в индексе имеет значение! В запросе условия должны совпадать с порядком в индексе.
    

---

2. **GIN для полнотекстового поиска**
    - Когда работаете с текстовыми данными:
        
        ```sql
        CREATE INDEX idx_gin_fulltext ON table_name USING gin(to_tsvector('english', column_name));
        ```
        
    - Пример поиска:
        
        ```sql
        SELECT * FROM table_name
        WHERE to_tsvector('english', column_name) @@ to_tsquery('postgres & optimization');
        ```
        

---

3. **BRIN для огромных таблиц**
    - Если данные в таблице идут в порядке времени, как в логах:
        
        ```sql
        CREATE INDEX idx_brin_date ON logs USING brin(log_date);
        ```
        
    - BRIN использует диапазоны блоков, что делает его идеальным для больших таблиц.

---

4. **Покрывающие индексы (INCLUDE)**:
    
    - Если в запросе есть колонки, которые не участвуют в фильтрации, но используются в `SELECT`:
        
        ```sql
        CREATE INDEX idx_covering ON table_name (column1) INCLUDE (column2, column3);
        ```
        
    
    Пример:
    
    ```sql
    SELECT column1, column2 FROM table_name WHERE column1 = 'value';
    ```
    

---

### **1.2. Кейс: когда индексы вредят**

1. **Частые `INSERT` и `UPDATE`**:
    
    - Индексы требуют обновления при каждой записи.
2. **Индексы на низкокардинальные колонки**:
    
    - Пример: `gender`, где всего два значения. PostgreSQL просто игнорирует индекс.
3. **Неиспользуемые индексы**:
    
    - Если индекс больше не используется, он только занимает место.
    
    ```sql
    DROP INDEX idx_unused;
    ```
    
4. **Где лучше Seq Scan**:
    
    - Если запрос возвращает >10% строк таблицы, PostgreSQL выбирает последовательное сканирование.

## **2.2. Как избежать "перегрева" запросов**

### 1. **Не используйте подзапросы, если можно обойтись JOIN'ами**

- **Плохо:**
    
    ```sql
    SELECT * FROM table1 WHERE column1 IN (SELECT column2 FROM table2);
    ```
    
- **Хорошо:**
    
    ```sql
    SELECT t1.* FROM table1 t1
    JOIN table2 t2 ON t1.column1 = t2.column2;
    ```
    

### 2. **Используйте фильтрацию на ранних этапах**

- **Вместо:**
    
    ```sql
    SELECT * FROM table1 WHERE LOWER(column1) = 'value';
    ```
    
- **Создайте индекс на `LOWER(column1)`:**
    
    ```sql
    CREATE INDEX idx_lower ON table1 (LOWER(column1));
    ```
    

### 3. **Отдавайте запросы в нужном формате**

- **Вместо:**
    
    ```sql
    SELECT * FROM table1 WHERE column1 > 1000;
    ```
    
- **Используйте:**
    
    ```sql
    SELECT column1, column2 FROM table1 WHERE column1 > 1000;
    ```

## **3. JSONB и сложные данные**

### **3.1. Работа с JSONB**

#### 1. **Создание индекса для JSONB**

- Для доступа к вложенным ключам:
    
    ```sql
    CREATE INDEX idx_jsonb_key ON table_name USING gin (jsonb_column jsonb_path_ops);
    ```
    

#### 2. **Поиск по ключу**

```sql
SELECT * FROM table_name
WHERE jsonb_column ->> 'key' = 'value';
```

#### 3. **Поиск в массиве JSONB**

```sql
SELECT * FROM table_name
WHERE jsonb_column @> '{"key": ["value1", "value2"]}';
```

---

### **3.2. Агрегации JSONB**

#### 1. **Группировка по JSONB**

```sql
SELECT jsonb_column ->> 'key', COUNT(*)
FROM table_name
GROUP BY jsonb_column ->> 'key';
```

#### 2. **Агрегирование данных**

```sql
SELECT JSON_AGG(jsonb_column)
FROM table_name
WHERE column1 = 'value';
```

## **4. Партицирование больших таблиц**

### **4.1. Когда нужно партицирование**

#### 1. **Лог-файлы** или **временные данные**

- Если часто обращаетесь к последним данным:
    
    ```sql
    CREATE TABLE logs (
        id SERIAL,
        log_date DATE,
        log_message TEXT
    ) PARTITION BY RANGE (log_date);
    
    CREATE TABLE logs_2023 PARTITION OF logs FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
    ```
    

#### 2. **Удаление старых данных**

- Партицирование облегчает удаление:
    
    ```sql
    DROP TABLE logs_2021;
    ```
    

---

### **4.2. Листовые партиции**

1. Используйте **HASH** партицирование для равномерного распределения данных:
    
    ```sql
    CREATE TABLE my_table (
        id SERIAL,
        data TEXT
    ) PARTITION BY HASH (id);
    
    CREATE TABLE my_table_0 PARTITION OF my_table FOR VALUES WITH (MODULUS 4, REMAINDER 0);
    ```

## **Индексы в PostgreSQL, оптимизация запросов, агрегации и группировки**

### **1. Индексы: Как, Когда и Зачем**

Индексы — это мощный инструмент для ускорения запросов, но неправильное использование может превратить их в обузу.

---

#### **1.1. Какие бывают индексы?**

2. **B-Tree (по умолчанию)**
    
    - Идеален для точных запросов (`=`) и диапазонов (`<`, `>`, `BETWEEN`).
    
    ```sql
    CREATE INDEX idx_column1 ON table_name(column1);
    ```
    
3. **GIN (Generalized Inverted Index)**
    
    - Используется для массивов, JSONB, полнотекстового поиска.
    
    ```sql
    CREATE INDEX idx_gin_column ON table_name USING gin(column_name);
    ```
    
4. **GiST (Generalized Search Tree)**
    
    - Для поиска по расстоянию, географических данных.
    
    ```sql
    CREATE INDEX idx_gist ON table_name USING gist(geom);
    ```
    
5. **BRIN (Block Range Index)**
    
    - Подходит для огромных таблиц с последовательными данными (например, логов).
    
    ```sql
    CREATE INDEX idx_brin ON table_name USING brin(date_column);
    ```
    
6. **Hash Index**
    
    - Для точных запросов (`=`). Редко используется, так как обычно B-Tree лучше.
    
    ```sql
    CREATE INDEX idx_hash ON table_name USING hash(column_name);
    ```
    

---

### **1.2. Когда индексы полезны?**

7. **Частые выборки по WHERE или JOIN**
    
    - Если часто используете колонку в `WHERE`, создайте индекс:
    
    ```sql
    CREATE INDEX idx_column1 ON table_name(column1);
    ```
    
8. **Группировки и сортировки**
    
    - Ускоряют `GROUP BY` и `ORDER BY`:
    
    ```sql
    CREATE INDEX idx_order ON table_name(column1, column2);
    ```
    
9. **Поиск по массивам и JSONB**
    
    ```sql
    CREATE INDEX idx_gin_json ON table_name USING gin(jsonb_column);
    ```
    

---

### **1.3. Когда индексы вредят?**

10. **Маленькие таблицы**
    
    - На таблицах с десятками или сотнями строк индекс не даст прироста, так как последовательное сканирование (Seq Scan) быстрее.
11. **Частые вставки/обновления**
    
    - Каждый индекс увеличивает накладные расходы на `INSERT` и `UPDATE`.
12. **Индексы на колонки с низкой кардинальностью**
    
    - Если в колонке только 2-3 уникальных значения (например, `gender`), индекс малоэффективен:
    
    ```sql
    CREATE INDEX idx_gender ON table_name(gender);
    ```
    
    В таких случаях PostgreSQL всё равно сделает Seq Scan.
    

---

### **1.4. Как

найти неэффективные индексы**

Используйте `pg_stat_user_indexes`:

```sql
SELECT * 
FROM pg_stat_user_indexes 
WHERE idx_scan = 0; -- Индексы, которые не используются
```

#### **Оптимизация запросов:**

13. Используйте **индексы** для ускорения:

### **2.2. INSERT: Эффективное добавление данных**

17. **Добавление одной записи**:
    
    ```sql
    INSERT INTO table_name (column1, column2) VALUES ('value1', 'value2');
    ```
    
18. **Массовое добавление**:
    
    ```sql
    INSERT INTO table_name (column1, column2)
    VALUES
        ('value1', 'value2'),
        ('value3', 'value4');
    ```
    
19. **Upsert (INSERT ON CONFLICT):**
    
    - Вставить запись, если её нет, иначе обновить:
    
    ```sql
    INSERT INTO table_name (id, value)
    VALUES (1, 'new_value')
    ON CONFLICT (id)
    DO UPDATE SET value = EXCLUDED.value;
    ```
    

---

### **2.3. JOIN: Магия объединения**

#### **Типы JOIN:**

20. **INNER JOIN**:
    
    - Возвращает только совпадающие строки.
    
    ```sql
    SELECT a.*, b.*
    FROM table1 a
    INNER JOIN table2 b ON a.id = b.id;
    ```
    
21. **LEFT JOIN**:
    
    - Возвращает все строки из левой таблицы, даже если в правой таблице нет совпадений.
    
    ```sql
    SELECT a.*, b.*
    FROM table1 a
    LEFT JOIN table2 b ON a.id = b.id;
    ```
    
22. **FULL OUTER JOIN**:
    
    - Возвращает строки из обеих таблиц, включая несопоставимые.
    
    ```sql
    SELECT a.*, b.*
    FROM table1 a
    FULL OUTER JOIN table2 b ON a.id = b.id;
    ```
    

#### **Оптимизация JOIN:**

- Убедитесь, что на ключах `JOIN` есть индексы.
- Избегайте ненужных `JOIN`, если можно использовать подзапросы.

## **3. Индексы и оптимизация запросов**

---

### **3.1. Типы индексов**

23. **B-Tree (по умолчанию):**
    
    - Идеально для операций `=` и `<`, `>`, `BETWEEN`.
24. **GIN (Generalized Inverted Index):**
    
    - Для полнотекстового поиска и массивов.
    
    ```sql
    CREATE INDEX idx_gin ON table_name USING gin(column_name);
    ```
    
25. **GiST (Generalized Search Tree):**
    
    - Для географических данных и поиска по расстоянию.
26. **BRIN (Block Range Index):**
    
    - Для больших таблиц с последовательными данными.

---

### **3.2. Профилирование запросов**

Используйте `EXPLAIN` и `EXPLAIN ANALYZE` для анализа плана выполнения запроса:

```sql
EXPLAIN ANALYZE
SELECT * FROM table_name WHERE column1 = 'value';
```

Пример вывода:

- **Seq Scan**: Последовательное сканирование таблицы.
- **Index Scan**: Использование индекса.
- **Nested Loop**: Выполнение `JOIN` через вложенные циклы.

---

### **3.3. Оптимизация VACUUM**

27. PostgreSQL не удаляет сразу "мёртвые" строки.
    
28. Используйте `VACUUM` для очистки:
    
    ```bash
    VACUUM ANALYZE;
    ```
    
29. Автоматизация через Autovacuum:
    
    - Настройка в `postgresql.conf`:
        
        ```ini
        autovacuum = on
        autovacuum_vacuum_threshold = 50
        ```

## **4. Транзакции и изоляция**

---

### **4.1. Уровни изоляции**

30. **Read Uncommitted**: Видит незавершённые изменения (почти не используется в PostgreSQL).
31. **Read Committed**: Видит только завершённые транзакции (по умолчанию).
32. **Repeatable Read**: Фиксирует snapshot на время транзакции.
33. **Serializable**: Самый строгий уровень (дорого в вычислениях).

Пример:

```sql
BEGIN;
SELECT * FROM table_name WHERE id = 1 FOR UPDATE;
COMMIT;
```

---

### **4.2. Использование WAL (Write Ahead Log)**

WAL гарантирует, что данные будут записаны даже при сбоях.

- **Настройка WAL**:
    
    ```ini
    wal_level = replica
    max_wal_size = 1GB
    ```
    
- **Бэкапы через WAL**: Используйте `pg_basebackup` для репликации.

### **5.2. Репликация**

PostgreSQL поддерживает несколько видов репликации:

34. **Синхронная**:
    
    - Гарантирует, что запись попадает на реплику перед подтверждением.
    
    ```ini
    synchronous_standby_names = 'node2'
    ```
    
35. **Асинхронная**:
    
    - Реплика получает данные с задержкой, но быстрее.
