
Да, из-за неправильно применённых миграций данные в базе данных (например, PostgreSQL) действительно можно потерять. Это одна из самых критичных проблем при работе с миграциями, и она возникает, если миграции недостаточно продуманы или плохо протестированы. Давайте разберём, как это может случиться, и как избежать потери данных.

---

Как можно потерять данные из-за миграций?

Вот типичные сценарии, где данные могут быть утеряны из-за ошибок в миграциях:

1. Удаление таблицы или столбца без сохранения данных:
    
    - Пример: Миграция удаляет столбец email из таблицы users:
        
        sql
        
        ```sql
        ALTER TABLE users DROP COLUMN email;
        ```
        
    - Результат: Все данные в столбце email теряются безвозвратно, если их не сохранили заранее.
        
2. Изменение типа данных с потерей информации:
    
    - Пример: Преобразование VARCHAR(100) в INTEGER без обработки нечисловых значений:
        
        sql
        
        ```sql
        ALTER TABLE users ALTER COLUMN age TYPE INTEGER USING age::INTEGER;
        ```
        
    - Результат: Если в age были строки вроде "twenty", они вызовут ошибку или будут обнулены (в зависимости от USING).
        
3. Пересоздание таблицы (DROP + CREATE):
    
    - Пример:
        
        sql
        
        ```sql
        DROP TABLE users;
        CREATE TABLE users (id SERIAL PRIMARY KEY, name VARCHAR(100));
        ```
        
    - Результат: Все существующие записи в таблице users удаляются.
        
4. Ошибки в логике миграции:
    
    - Пример: Обновление данных с некорректным условием:
        
        sql
        
        ```sql
        UPDATE users SET name = 'unknown' WHERE id > 0;
        ```
        
    - Результат: Все имена пользователей перезаписываются на 'unknown'.
        
5. Откат миграции (Down Migration):
    
    - Пример: Миграция добавляет столбец email, а откат (down.sql) его удаляет:
        
        sql
        
        ```sql
        -- up.sql
        ALTER TABLE users ADD COLUMN email VARCHAR(100);
        -- down.sql
        ALTER TABLE users DROP COLUMN email;
        ```
        
    - Результат: При откате данные в email теряются, если их не сохранили.
        
6. Конфликты или пропуск миграций:
    
    - Если миграции применяются непоследовательно (например, пропущена одна из них), это может привести к несогласованности данных или их потере.
        

---

Как избежать потери данных?

Чтобы миграции были безопасными, нужно следовать лучшим практикам и предусмотреть возможные риски. Вот основные рекомендации:

1. Тестирование миграций

- Тестовая база: Применяйте миграции сначала на копии продакшен-базы.
    
    - Пример: Сделайте дамп базы:
        
        bash
        
        ```bash
        pg_dump -h localhost -U user dbname > backup.sql
        ```
        
        Затем протестируйте миграции на локальной копии:
        
        bash
        
        ```bash
        psql -U user test_db < backup.sql
        migrate -path migrations -database "postgres://..." up
        ```
        
- Автоматические тесты: Пишите тесты для проверки данных до и после миграции.
    

2. Резервное копирование

- Перед применением: Всегда делайте бэкап продакшен-базы:
    
    bash
    
    ```bash
    pg_dump -h prod_host -U user dbname > prod_backup_2025-03-13.sql
    ```
    
- Восстановление: Если что-то пошло не так, восстановите данные:
    
    bash
    
    ```bash
    psql -U user dbname < prod_backup_2025-03-13.sql
    ```
    

3. Минимизация деструктивных операций

- Не удаляйте сразу:
    
    - Вместо DROP COLUMN сначала пометьте столбец как устаревший и перенесите данные:
        
        sql
        
        ```sql
        ALTER TABLE users ADD COLUMN email_new VARCHAR(100);
        UPDATE users SET email_new = email;
        -- Позже, после проверки:
        ALTER TABLE users DROP COLUMN email;
        ```
        
- Используйте временные таблицы:
    
    - Пример: Пересоздание таблицы с сохранением данных:
        
        sql
        
        ```sql
        CREATE TABLE users_new (id SERIAL PRIMARY KEY, name VARCHAR(50));
        INSERT INTO users_new (id, name) SELECT id, name FROM users;
        DROP TABLE users;
        ALTER TABLE users_new RENAME TO users;
        ```
        

4. Корректное изменение типов данных

- Проверяйте совместимость:
    
    - Пример: Преобразование VARCHAR в INTEGER с обработкой:
        
        sql
        
        ```sql
        ALTER TABLE users ADD COLUMN age_int INTEGER;
        UPDATE users SET age_int = CASE WHEN age ~ '^[0-9]+$' THEN age::INTEGER ELSE NULL END;
        ALTER TABLE users DROP COLUMN age;
        ALTER TABLE users RENAME COLUMN age_int TO age;
        ```
        
- Избегайте потерь: Убедитесь, что данные не обрезаются (например, VARCHAR(100) → VARCHAR(50)).
    

5. Тщательное планирование откатов (Down Migration)

- Сохраняйте данные:
    
    - Если up.sql добавляет столбец, down.sql не должен просто удалять его без сохранения:
        
        sql
        
        ```sql
        -- up.sql
        ALTER TABLE users ADD COLUMN email VARCHAR(100);
        -- down.sql
        CREATE TABLE users_email_backup AS SELECT id, email FROM users;
        ALTER TABLE users DROP COLUMN email;
        ```
        
- Ограничьте использование откатов: В продакшене откаты редко применяются, лучше двигаться только вперёд.
    

6. Последовательное применение

- Уникальные имена: Используйте нумерацию миграций (например, 0001_create_users.sql), чтобы избежать пропусков.
    
- Проверка состояния: Перед применением проверяйте, какие миграции уже выполнены:
    
    bash
    
    ```bash
    migrate -path migrations -database "postgres://..." version
    ```
    

7. Использование транзакций

- Атомарность: Оборачивайте миграции в транзакции, чтобы при ошибке изменения откатились:
    
    sql
    
    ```sql
    BEGIN;
    ALTER TABLE users ADD COLUMN email VARCHAR(100);
    UPDATE users SET email = 'default@example.com' WHERE email IS NULL;
    COMMIT;
    ```
    
- Ограничение: Некоторые операции (например, CREATE INDEX CONCURRENTLY) нельзя обернуть в транзакцию.
    

8. Документация и валидация

- Документируйте: Указывайте в миграциях, что они делают, и какие данные затрагивают.
    
- Проверяйте: После миграции убедитесь, что данные остались:
    
    sql
    
    ```sql
    SELECT COUNT(*) FROM users WHERE email IS NOT NULL;
    ```
    

9. Постепенные изменения

- Разделяйте шаги: Вместо одной большой миграции делайте маленькие:
    
    1. Добавьте новый столбец.
        
    2. Перенесите данные.
        
    3. Удалите старый столбец (через несколько релизов).
        

---

Пример безопасной миграции

Проблема

Хотим заменить VARCHAR на JSONB для столбца data в таблице users.

Ошибочный подход (потеря данных)

sql

```sql
ALTER TABLE users ALTER COLUMN data TYPE JSONB;
```

- Если в data были строки вроде "hello", они вызовут ошибку без правильного преобразования.
    

Безопасный подход

sql

```sql
-- 1. Добавляем новый столбец
ALTER TABLE users ADD COLUMN data_jsonb JSONB;

-- 2. Переносим данные с обработкой
UPDATE users SET data_jsonb = CASE 
    WHEN data IS NULL THEN NULL 
    ELSE data::JSONB 
    END;

-- 3. Проверяем
SELECT * FROM users WHERE data_jsonb IS NULL AND data IS NOT NULL; -- Должно быть пусто

-- 4. Удаляем старый столбец (после проверки)
ALTER TABLE users DROP COLUMN data;
ALTER TABLE users RENAME COLUMN data_jsonb TO data;
```

Итог

- Можно ли потерять данные? Да, из-за удаления, изменения типов или ошибок в миграциях.
    
- Как избежать? Тестируйте на копии, делайте бэкапы, минимизируйте деструктивные операции, сохраняйте данные перед удалением, проверяйте откаты.
