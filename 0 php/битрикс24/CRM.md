В Битрикс работа с сущностями CRM (Лиды, Сделки, Контакты) через API должна быть оптимизированной, чтобы избежать проблем с производительностью, таких как проблема N+1. Для этого используются разные подходы в старом процедурном API и в современном D7 (ORM).

Ниже приведена сравнительная таблица, которая показывает ключевые различия в структуре запросов между двумя подходами.

| Аспект | **Старый процедурный API (Legacy)** | **Современное ядро D7 (ORM)** |
| :--- | :--- | :--- |
| **Основной принцип** | Функции-обертки, возвращающие ресурс для выборки. | Объектно-ориентированный подход через классы-сущности (`DataManager`). |
| **Синтаксис запроса** | `CAllCrmLead::GetList($arOrder, $arFilter, $arGroupBy, $arNavStartParams, $arSelectFields)` | `LeadTable::getList(['select' => [...], 'filter' => [...], 'order' => [...]])` |
| **Безопасность** | Требует ручного экранирования значений в фильтрах. | **Автоматическое экранирование** параметров, встроенная защита от SQL-инъекций. |
| **Кеширование** | Ручное, через `CPHPCache` или глобальный менеджер кеша. | Встроенное на уровне ORM через параметр `cache` в `getList()`. |
| **Получение данных** | Цикл с `$res->Fetch()` или `GetNext()`. | Методы `fetch()`, `fetchAll()`, или работа с коллекциями объектов (`fetchCollection()`). |
| **Решение N+1** | **Проблематично.** Требует ручной пакетной загрузки и агрегации данных. | **Встроенная поддержка.** Оптимизация через **JOIN** в одном запросе или автоматическая декомпозиция сложных выборок. |
| **Пример для N+1** | Для каждого лида в цикле делать отдельный запрос за связанными контактами. | Одним запросом с `'select' => ['ID', 'TITLE', 'CONTACT.NAME']` получить все данные с JOIN. |

### 💡 Как решить проблему N+1 в CRM с помощью D7 ORM
Проблема N+1 возникает, когда вы сначала получаете список основных сущностей (например, сделок), а затем в цикле для каждой из них делаете отдельный запрос за связанными данными (например, контактами). В D7 ORM есть два основных способа избежать этого:

1.  **Оптимизация с помощью JOIN в одном запросе**: Вы можете сразу выбрать поля связанной сущности в основном запросе. ORM построит оптимальный SQL-запрос с `JOIN`.
    ```php
    // Пример: Получить сделки с именами связанных контактов одним запросом
    $deals = \Bitrix\Crm\DealTable::getList([
        'select' => ['ID', 'TITLE', 'STAGE_ID', 'CONTACT.NAME', 'CONTACT.LAST_NAME'],
        'filter' => ['=STAGE_ID' => 'NEW'],
        'order' => ['ID' => 'DESC'],
    ])->fetchAll();
    ```
2.  **Использование `QueryHelper::decompose()` для сложных связей**: Если в выборке много связей "один-ко-многим" (1:N), например, несколько мультисписковых свойств, прямое использование JOIN может привести к **декартову произведению** и огромному количеству строк в результате. Метод `decompose()` автоматически разобьет один тяжелый запрос на несколько оптимальных.
    ```php
    // Пример: Безопасная выборка с несколькими множественными свойствами
    use \Bitrix\Main\ORM\Query\QueryHelper;
    $query = \Bitrix\Crm\LeadTable::query()
        ->addSelect('*')
        ->addSelect('MY_MULTI_FIELD_1')
        ->addSelect('MY_MULTI_FIELD_2');
    // Автоматически предотвращает проблему декартова произведения
    $collection = QueryHelper::decompose($query);
    ```

### 💎 Практические рекомендации
*   **Для новых проектов всегда используйте D7 ORM.** Это современный, безопасный и производительный стандарт.
*   **Избегайте `GetByID` в циклах.** Этот метод загружает все поля и свойства сущности, что почти всегда избыточно и медленно. Вместо этого используйте `GetList` (в старом API) или `*Table::getList()` (в D7) с явным указанием нужных полей.
*   **Применяйте кеширование.** В D7 это делается просто добавлением параметра `'cache' => ['ttl' => 3600]` в массив `getList()`.

Если у вас есть конкретный сценарий выборки данных из CRM, с которым возникли сложности, опишите его — помогу подобрать наиболее эффективный способ реализации.
