## **1. Архитектурные решения для ультранагруженных систем**

### **1.1. Архитектура "Lambda" и "Kappa"**

#### **Lambda Architecture**

- Делит обработку данных на два слоя:
    1. **Batch Layer (Пакетный слой):**
        - Обрабатывает данные периодически большими блоками.
        - Пример: Hadoop или Apache Spark.
    2. **Speed Layer (Реальное время):**
        - Обрабатывает данные "на лету".
        - Пример: Apache Storm или Flink.
    3. **Serving Layer:**
        - Объединяет данные из двух слоёв.

**Пример использования:**

- Обработка аналитики: Batch Layer обрабатывает исторические данные, Speed Layer — последние события.

#### **Kappa Architecture**

- Фокусируется на **обработке событий в реальном времени**:
    - Все данные представляют собой поток событий.
    - Нет разделения на исторические и текущие данные.
    - Используется Kafka как основной компонент.

---

### **1.2. Динамическая репликация данных**

1. **Географическая репликация:**
    
    - Используй **active-active репликацию** для глобальных систем (например, Cassandra, DynamoDB).
    - Проблема консистентности: Разрешай конфликты с помощью **vector clocks**.
2. **Частичная репликация:**
    
    - Реплицируй только "горячие" данные в несколько дата-центров.

---

### **1.3. Zero-Downtime Deployment**

1. **Blue/Green Deployment:**
    
    - Новая версия развёртывается параллельно со старой.
    - Переключение трафика осуществляется через Load Balancer.
2. **Canary Deployment:**
    
    - Новая версия получает только часть трафика (например, 5%).

#### **Углубление: Shadow Traffic**

- Запуск новой версии параллельно с текущей, но без воздействия на реальных пользователей:
    - Трафик дублируется для тестирования.

## **2. Консенсус и блокировки: на атомарном уровне**

### **2.1. Продвинутый Raft**

**Raft** не только выбирает лидера, но и гарантирует, что данные консистентны на всех узлах.

#### **Сложные случаи:**

1. **Split Brain (Разделённый мозг):**
    
    - Если сеть разделилась, два узла могут считать себя лидерами.
    - Решение: Установить **quorum** (например, 3 из 5 узлов должны согласиться).
2. **Долгоживущие конфликты:**
    
    - Пример: Реплики на разных узлах имеют противоречивые данные.
    - Решение: Используй **Conflict-Free Data Types** (CRDT).

---

### **2.2. Алгоритм Paxos на пальцах**

1. **Фазы:**
    
    - **Prepare:** Узел предлагает значение.
    - **Accept:** Большинство узлов соглашаются с предложением.
    - **Commit:** Значение фиксируется.
2. **Почему Paxos сложен:**
    
    - Требует больше сообщений (network round-trips).
    - Сложно реализовать на практике (поэтому Raft популярен).

## **3. Криптография и безопасность в микросервисах**

### **3.1. TLS для каждого запроса**

1. Все запросы между сервисами должны быть шифрованы.
2. Используй **mTLS (mutual TLS)**:
    - Сертификаты используются для аутентификации и шифрования.

---

### **3.2. OAuth 2.0 для авторизации**

- При доступе к данным из микросервисов:
    - Клиенты получают **access token** через **Authorization Server**.
    - Access Token используется для проверки прав доступа.

---

### **3.3. Защита от атак**

1. **Rate Limiting:**
    
    - Ограничивай количество запросов от одного клиента.
    - Пример: 100 запросов в минуту.
2. **JWT (JSON Web Token):**
    
    - Используй для передачи данных о пользователе между микросервисами.
    - Пример структуры:
        
        ```json
        {
            "sub": "1234567890",
            "name": "John Doe",
            "iat": 1516239022
        }
        ```

## **4. Big Data: обработка огромных объёмов данных**

### **4.1. MapReduce**

- Распределённая обработка данных:
    1. **Map Phase:** Данные разбиваются на части и обрабатываются параллельно.
    2. **Reduce Phase:** Результаты объединяются.

---

### **4.2. Потоковая обработка данных**

1. **Flink vs Spark Streaming:**
    
    - Flink: Низкая задержка, состояние сохраняется.
    - Spark Streaming: Пакетная обработка с микропакетами.
2. **Kafka Streams:**
    
    - Позволяет обрабатывать потоки событий напрямую внутри Kafka.

## **5. Теория игр и распределённые системы**

Да, теория игр применяется в системах! Например:

1. **Алгоритм лидерства (Election Algorithm):**
    
    - Узлы решают, кто станет лидером.
    - Пример: "Меньший ID выигрывает".
2. **Nash Equilibrium в распределённых системах:**
    
    - Пример: Каждый узел действует так, чтобы минимизировать свои задержки, приводя систему к равновесию.

## **6. Самые сложные вопросы на собеседованиях**

### **6.1. Как проектировать систему, устойчивую к массовым сбоям?**

1. Используй **Multi-Region Deployment:**
    - Данные реплицируются между регионами.
2. Разделяй на независимые части:
    - Пример: Каждая функция работает автономно.

---

### **6.2. Как справляться с горячими точками (Hotspots)?**

1. **Shard Pre-Splitting:**
    - Разделяй популярные данные на несколько шардов заранее.
2. Используй **adaptive load balancing**:
    - Реализация через **dynamic weights** для балансировки.
