# **1. Расширенное понимание микросервисов**

Ты должен не только знать базовые принципы, но и понимать **глубокие компромиссы** и решения. Вот как произвести впечатление:

## **1.1. Границы микросервисов**

- **Как ты определяешь границы сервисов?**
    - **Ответ:** Использую подход DDD (Domain-Driven Design), чтобы каждый микросервис представлял конкретный **Bounded Context**.
    - Пример: "В интернет-магазине сервис корзины не должен знать, как работают заказы, но он должен уметь публиковать событие `OrderPlaced`, чтобы другие сервисы могли с ним взаимодействовать."

### **Удиви собеседников**:

- Скажи: "Неправильно спроектированные границы — это самый частый антипаттерн. Если вы видите, что микросервисы начинают часто вызывать друг друга, то вместо независимости мы получаем распределённый монолит."

---

## **1.2. Общие антипаттерны микросервисов**

**Подготовь такие примеры, чтобы они воскликнули: "Этому парню явно довелось решать такие проблемы!"**

1. **"Chatty" микросервисы (чрезмерная болтовня):**
    
    - Проблема: Сервисы делают слишком много сетевых запросов друг к другу.
    - Решение: Агрегировать данные в API Gateway или использовать CQRS.
2. **"Монолит в микросервисах":**
    
    - Проблема: Сервисы используют одну и ту же базу данных.
    - Решение: Каждый сервис должен владеть своим собственным хранилищем данных.
3. **"Too Many Services" (слишком мелкие сервисы):**
    
    - Проблема: Каждый микросервис становится настолько маленьким, что управление ими сложнее, чем монолитом.
    - Решение: Убедиться, что сервисы делятся по доменам, а не техническим слоям.

# **2. Глубокое понимание взаимодействия**

## **2.1. Расширенные паттерны коммуникации**

Ты должен знать больше, чем REST и gRPC. Расскажи про **event-driven подходы**, их плюсы и минусы:

### **Асинхронная обработка через брокеры сообщений**

1. **Пример:** Kafka, RabbitMQ, NATS.
    
2. **Паттерн "Event Sourcing":**
    
    - Вся бизнес-логика строится на основе событий.
    - Например: "Когда пользователь делает заказ, мы сохраняем `OrderCreated` и строим состояния на основе событий, а не изменяем текущее состояние напрямую."
3. **Idempotent Consumers**:
    
    - Убедись, что твои потребители сообщений могут безопасно обрабатывать повторяющиеся события.

#### **Секретный совет для собеседования:**

- Упомяни **dead-letter queues (DLQ)**.
    - "Когда сообщение невозможно обработать, оно отправляется в специальную очередь, чтобы мы могли его проанализировать позже."

---

## **2.2. Расширенные протоколы и компромиссы**

- **Когда использовать REST, gRPC или GraphQL?**
    
    - REST: Простота, масштабируемость.
    - gRPC: Высокая производительность, особенно для внутренних сервисов.
    - GraphQL: Подходит, если клиенту нужно кастомизировать запросы.
- **Как решать проблемы согласованности между синхронными и асинхронными вызовами?**
    
    - Например: "Если REST-запрос завершился ошибкой, но асинхронное сообщение уже было отправлено, мы используем компенсационные транзакции."

# **3. Отказоустойчивость и сложные сценарии**

## **3.1. Circuit Breaker**

Не просто упомяни паттерн Circuit Breaker, но разберись в его **тонкостях**:

- **Half-Open State**:
    
    - "Когда Circuit Breaker восстанавливается, он начинает пропускать ограниченное количество запросов, чтобы проверить, работает ли система."
- Расскажи про реальные сценарии:
    
    - "В случае, если база данных перегружена, Circuit Breaker может предотвратить каскадный сбой системы, временно заблокировав запросы."

---

## **3.2. Расширенные сценарии с нагрузкой**

1. **Load Shedding (сбрасывание нагрузки):**
    
    - "Когда сервис перегружен, мы можем отбрасывать менее важные запросы."
    - Пример: "API новостного сервиса может отдавать кэшированные данные вместо запросов к базе данных."
2. **Тайм-ауты и повторные запросы:**
    
    - Упомяни, как использовать экспоненциальную задержку:
    
    ```go
    func retryRequest(request func() error, retries int) error {
        delay := time.Millisecond * 100
        for i := 0; i < retries; i++ {
            if err := request(); err == nil {
                return nil
            }
            time.Sleep(delay)
            delay *= 2
        }
        return errors.New("request failed")
    }
    ```

### **Кейс 1: Проблема согласованности в распределённой системе**
