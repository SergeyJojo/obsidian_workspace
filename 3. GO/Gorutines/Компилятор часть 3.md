## **7. Исходный код компилятора Go**

### **7.1. Структура репозитория Go**

Компилятор Go (`gc`) находится в репозитории Go (`golang/go`) в каталоге `src/cmd/compile`. Основные директории:

1. **`cmd/compile/internal/`**:
    - **`base/`**: Основная логика работы компилятора.
    - **`ssa/`**: Модуль для обработки SSA (Static Single Assignment).
    - **`typecheck/`**: Анализ типов.
2. **`cmd/link/`**:
    - Линковщик, объединяющий машинный код в единый бинарный файл.
3. **`runtime/`**:
    - Код, связанный с планировщиком, garbage collector и системными вызовами.

---

### **7.2. Как работает генерация кода: внутренняя логика**

Компилятор генерирует код через серию преобразований. Каждый этап добавляет больше деталей и близости к машинному коду.

#### **1. AST (Abstract Syntax Tree):**

Дерево выражений программы.

Пример AST для `x = a + b`:

```plaintext
AssignStmt:
  LHS: x
  RHS: BinaryExpr:
        Op: Add
        Left: a
        Right: b
```

#### **2. SSA (Static Single Assignment):**

Компилятор переводит код в SSA для выполнения оптимизаций.

Пример SSA:

```plaintext
entry:
    t0 = Add a, b
    Store x, t0
    Ret
```

#### **3. Machine IR (MIR):**

На этом этапе код привязывается к целевой архитектуре (например, x86).

Пример MIR:

```plaintext
MOV RAX, [a]
ADD RAX, [b]
MOV [x], RAX
RET
```

---

### **7.3. Кодирование платформенных зависимостей**

Go поддерживает разные архитектуры, и генерация машинного кода учитывает особенности каждой платформы:

1. **Архитектурные модули:**
    - `cmd/compile/internal/x86/`
    - `cmd/compile/internal/arm/`

#### Пример: x86 и ARM

```plaintext
ADD RAX, RBX  // x86
ADD R0, R1, R2 // ARM
```

#### Оптимизации:

1. Векторные инструкции (SIMD) для обработки массивов.
2. Упрощение инструкций через peephole optimization.

## **8. Глубокий анализ сборщика мусора Go**

### **8.1. Write Barrier**

#### **Что это такое?**

Write Barrier — это механизм, который позволяет garbage collector отслеживать изменения в памяти во время параллельной сборки мусора.

#### **Как работает:**

1. Когда программа записывает значение в указатель, Write Barrier помечает изменённый объект.
2. Это нужно для гарантии, что сборщик мусора видит все изменения.

Пример:

```go
ptr.field = newValue
```

После применения Write Barrier:

```plaintext
CALL runtime.gcWriteBarrier
MOV ptr.field, newValue
```

---

### **8.2. Stop-the-World и Concurrent GC**

1. **Stop-the-World (STW):**
    
    - В ранних версиях Go (до 1.5) вся программа останавливалась для сборки мусора.
    - Проблема: Высокие задержки.
2. **Concurrent GC:**
    
    - Современные версии Go используют параллельный сборщик.
    - Большая часть работы выполняется параллельно с основной программой.

#### Оптимизация:

- Используется **Tri-Color Marking**:
    - **Белый цвет:** Объект ещё не проверен.
    - **Серый цвет:** Объект проверяется.
    - **Чёрный цвет:** Объект проверен.

## **9. Глубокие аспекты планировщика Go**

### **9.1. Взаимодействие M, P и G**

#### **Алгоритм планирования:**

1. Горутины (G) помещаются в локальную очередь процессора (P).
2. Если локальная очередь пустая, процессор вытягивает горутину из глобальной очереди.
3. Если все P заняты, Go запускает новые потоки M.

---

### **9.2. Steal Work (Воровство работы):**

- Если один логический процессор (P) простаивает, он может "украсть" горутины из другого P.

## **10. Разработка компилятора: сложные вопросы**

### **10.1. Как компилятор оптимизирует конкурентный код?**

#### Ответ:

1. Вставляет точки синхронизации (`runtime.gosched`) для контроля горутин.
2. Убирает избыточные барьеры памяти при работе с каналами (`chan`).

---

### **10.2. Как компилятор управляет кэшированием?**

#### Ответ:

1. Использует локальные переменные для минимизации операций с памятью.
2. Оптимизирует доступ к кэш-линии процессора (cache line alignment).
