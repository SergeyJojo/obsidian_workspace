
В PostgreSQL **`cost`** в планировщике запросов (Query Planner) — это условная единица, которая оценивает «стоимость» выполнения операции. Чем выше стоимость, тем «дороже» операция с точки зрения ресурсов (CPU, I/O, памяти).  

### **Основные операции и их примерная стоимость (`cost`)**
Postgres делит стоимость на две части:  
- **Start-up cost** – стоимость подготовки операции (например, сортировка перед выдачей первой строки).  
- **Total cost** – общая стоимость выполнения операции до конца.  

#### **1. Последовательное сканирование (Seq Scan)**
- **Операция**: Чтение всей таблицы подряд.  
- **Стоимость**:  
  ```
  cost = (seq_page_cost * количество_страниц) + (cpu_tuple_cost * количество_строчек)
  ```
  - `seq_page_cost` (по умолчанию `1.0`) – стоимость чтения одной страницы с диска.  
  - `cpu_tuple_cost` (по умолчанию `0.01`) – стоимость обработки одной строки CPU.  

#### **2. Сканирование по индексу (Index Scan, Bitmap Index Scan)**
- **Операция**: Чтение только нужных строк через индекс.  
- **Стоимость**:  
  ```
  cost = (random_page_cost * количество_страниц_индекса) + (cpu_index_tuple_cost * количество_записей_индекса) + (cpu_operator_cost * количество_проверок_условий)
  ```
  - `random_page_cost` (по умолчанию `4.0`) – стоимость чтения страницы в случайном порядке (обычно выше, чем `seq_page_cost`).  
  - `cpu_index_tuple_cost` (по умолчанию `0.005`) – обработка одной записи в индексе.  

#### **3. Сортировка (Sort)**
- **Операция**: Сортировка результата (`ORDER BY`).  
- **Стоимость**:  
  ```
  cost = (startup_cost) + (cpu_operator_cost * количество_строк * log2(количество_строк))
  ```
  - Чем больше строк, тем дороже сортировка (O(n log n)).  

#### **4. Хеш-соединение (Hash Join)**
- **Операция**: Соединение таблиц через хеш-таблицу.  
- **Стоимость**:  
  ```
  cost = (startup_cost) + (cpu_tuple_cost * размер_внешней_таблицы) + (hash_tuple_cost * размер_внутренней_таблицы)
  ```
  - `hash_tuple_cost` (по умолчанию `0.0025`) – стоимость обработки строки при хешировании.  

#### **5. Вложенные циклы (Nested Loop)**
- **Операция**: Поиск по внутренней таблице для каждой строки внешней.  
- **Стоимость**:  
  ```
  cost = (стоимость_внешнего_цикла) + (стоимость_внутреннего_цикла * количество_строк_внешней_таблицы)
  ```
  - Может быть очень дорогим, если внутренний цикл не использует индекс.  

#### **6. Группировка (GroupAggregate, HashAggregate)**
- **Операция**: Группировка (`GROUP BY`).  
- **Стоимость**:  
  ```
  cost = (cpu_operator_cost * количество_строк * log(количество_групп))
  ```
  - Зависит от алгоритма (HashAggregate обычно дешевле для больших данных).

### **Как Postgres выбирает план?**
Планировщик оценивает стоимость всех возможных планов и выбирает **самый дешёвый**.  

#### **Параметры стоимости (можно менять в `postgresql.conf`)**  
| Параметр               | Значение по умолчанию | Описание |
|------------------------|----------------------|----------|
| `seq_page_cost`        | `1.0`                | Стоимость чтения страницы последовательно |
| `random_page_cost`     | `4.0`                | Стоимость чтения страницы в случайном порядке (меньше на SSD) |
| `cpu_tuple_cost`       | `0.01`               | Стоимость обработки строки |
| `cpu_index_tuple_cost` | `0.005`              | Стоимость обработки записи индекса |
| `cpu_operator_cost`    | `0.0025`             | Стоимость операции (сравнение, вычисление) |

### **Как посмотреть стоимость операций?**
```sql
EXPLAIN ANALYZE SELECT * FROM users WHERE age > 30;
```
Вывод будет содержать:  
- `cost=0.00..20.00` (start-up cost..total cost)  
- `actual time=0.01..0.05 ms` (фактическое время).  

Если Postgres выбирает неоптимальный план, можно:  
- Поправить `random_page_cost` (например, `2.0` для SSD).  
- Добавить/оптимизировать индексы.  
- Использовать `SET enable_seqscan=off;` для тестов.
