В Kafka (или аналогичных системах очередей сообщений), **распределение сообщений по партициям** при отправке из **продюсера** происходит по чётко определённому алгоритму. Рассмотрим его подробно.

---

## 📦 Как работает распределение сообщений по партициям

### 1. Продюсер получает:

- **Топик** — логическое имя канала сообщений.
    
- **Ключ (key)** — может быть задан или не задан.
    
- **Сообщение (value)** — полезная нагрузка.
    

---

## 🧮 Алгоритм распределения по партициям

### 🔹 Сценарий 1: Указан `key`

Если ключ указан, используется **хеш-функция**:

```kotlin
partition = hash(key) % num_partitions
```

- Хеш-функция по умолчанию: `murmur2` (в Java-клиенте Kafka).
    
- Один и тот же ключ **всегда попадёт в одну и ту же партицию**, пока количество партиций не изменится.
    

### 🔹 Сценарий 2: Ключ **не** указан

Если ключ не указан, Kafka использует **раунд-робин** или **стики-алгоритм**:

#### 🌀 Sticky Partitioner (по умолчанию с Kafka 2.4+):

- Сообщения без ключа будут попадать в **одну выбранную партицию** до тех пор, пока:
    
    - не заполнился batch
        
    - или не прошёл таймаут отправки
        
- После этого выбирается новая партиция случайно
    

Такой подход:

- снижает фрагментацию
    
- улучшает производительность (меньше переключений)
    

#### 🔄 Старый Round-Robin:

- Каждое новое сообщение — в **следующую по кругу партицию**.
    

---

## 📘 Примеры

### Пример 1: С ключом

```go
producer.Send("orders", key="user42", value="order123")
→ partition = hash("user42") % N
```

### Пример 2: Без ключа

```go
producer.Send("orders", value="order124")
→ sticky-partition (до смены батча)
```

---

## 📊 Когда и зачем использовать ключ

- Для **гарантии порядка** — все сообщения с одним ключом будут в **одной партиции**, а в партиции порядок **гарантирован**.
    
- Для **логической группировки** (например, по пользователю, заказу и т.д.)
