
### **Уровни изоляции в SQL: полный разбор**

Уровни изоляции в SQL определяют, как транзакции взаимодействуют друг с другом, чтобы избежать конфликтов и некорректных данных. Они описаны в стандарте **SQL-92** и реализованы в большинстве реляционных баз данных, включая PostgreSQL.

---

## **1. Основы**

Каждая транзакция должна:

1. Видеть данные в **согласованном состоянии**.
2. Обеспечивать **независимость от других транзакций**.

Стандарт определяет четыре уровня изоляции, которые балансируют между **производительностью** и **корректностью данных**.

---

### **2. Проблемы параллельного выполнения транзакций**

#### **2.1. Dirty Reads (грязное чтение)**

- Транзакция читает данные, которые были изменены другой транзакцией, но не зафиксированы.
- Пример:
    - Транзакция A обновляет строку, но не фиксирует.
    - Транзакция B читает эту строку и видит незафиксированные изменения.

---

#### **2.2. Non-repeatable Reads (неповторяющееся чтение)**

- Транзакция повторно читает данные и получает разные значения, потому что другая транзакция изменила эти данные.
- Пример:
    - Транзакция A читает строку.
    - Транзакция B изменяет эту строку и фиксирует.
    - Транзакция A снова читает строку и видит другое значение.

---

#### **2.3. Phantom Reads (фантомные чтения)**

- Транзакция видит новые строки при повторном запросе, потому что другая транзакция добавила данные.
- Пример:
    - Транзакция A выполняет запрос `SELECT COUNT(*) FROM table WHERE condition`.
    - Транзакция B добавляет строки, соответствующие `condition`, и фиксирует.
    - Транзакция A выполняет запрос снова и получает другой результат.

---

## **3. Уровни изоляции: от слабого к сильному**

---

### **3.1. Read Uncommitted (Чтение незафиксированных данных)**

- **Описание**: Самый слабый уровень. Позволяет читать изменения, которые не были зафиксированы.
    
- **Разрешает**: Dirty Reads, Non-repeatable Reads, Phantom Reads.
    
- **Использование**: Только для чтения данных, где корректность не критична, но важна скорость.
    
- Пример:
    
    ```sql
    SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED;
    BEGIN;
    SELECT * FROM table_name;
    ```
    
- **Поддержка в PostgreSQL**: Не поддерживается напрямую. PostgreSQL автоматически поднимает уровень до **Read Committed**.
    

---

### **3.2. Read Committed (Чтение зафиксированных данных)**

- **Описание**: Позволяет читать только зафиксированные изменения. Грязные чтения запрещены.
    
- **Разрешает**: Non-repeatable Reads, Phantom Reads.
    
- **Использование**: Используется по умолчанию в PostgreSQL.
    
- Пример:
    
    ```sql
    SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
    BEGIN;
    SELECT * FROM table_name;
    ```
    
- **Как работает**:
    
    - Каждый `SELECT` видит данные, зафиксированные на момент выполнения запроса.
    - Если данные были изменены другой транзакцией, то запрос ждёт их фиксации или отката.

---

### **3.3. Repeatable Read (Повторяемое чтение)**

- **Описание**: Гарантирует, что все данные, прочитанные в одной транзакции, не изменятся в рамках этой же транзакции.
    
- **Разрешает**: Phantom Reads.
    
- **Использование**: Подходит для аналитики, где важно, чтобы данные оставались неизменными.
    
- Пример:
    
    ```sql
    SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
    BEGIN;
    SELECT * FROM table_name WHERE id = 1;
    ```
    
- **Как работает**:
    
    - Транзакция создаёт **снимок данных** (snapshot).
    - Все `SELECT` возвращают данные из этого снимка, игнорируя изменения, сделанные другими транзакциями.

---

### **3.4. Serializable (Сериализуемый уровень)**

- **Описание**: Самый строгий уровень. Гарантирует, что транзакции выполняются последовательно, как если бы они выполнялись одна за другой.
    
- **Разрешает**: Никакие проблемы (Dirty Reads, Non-repeatable Reads, Phantom Reads) не допускаются.
    
- **Использование**: Критически важные сценарии, где важна абсолютная согласованность данных.
    
- Пример:
    
    ```sql
    SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    BEGIN;
    SELECT * FROM table_name WHERE id = 1;
    ```
    
- **Как работает**:
    
    - Транзакция получает **эксклюзивный снимок данных**.
    - Любая операция, которая нарушает согласованность, приводит к ошибке `Serialization failure`.

---

## **4. Сравнение уровней изоляции**

|Уровень|Dirty Reads|Non-repeatable Reads|Phantom Reads|Производительность|
|---|---|---|---|---|
|**Read Uncommitted**|Да|Да|Да|Очень высокая|
|**Read Committed**|Нет|Да|Да|Высокая|
|**Repeatable Read**|Нет|Нет|Да|Средняя|
|**Serializable**|Нет|Нет|Нет|Низкая|

## **5. Как работает изоляция в PostgreSQL**

---

### **5.1. MVCC (Многоверсионный контроль параллелизма)**

PostgreSQL использует **MVCC** для управления транзакциями. Это позволяет:

1. Каждой транзакции видеть свою "версию" данных.
2. Избегать блокировок при чтении.

#### **Как это реализовано:**

- Каждая строка в таблице имеет:
    - `xmin`: Транзакция, которая создала строку.
    - `xmax`: Транзакция, которая удалила или обновила строку.
- `SELECT` возвращает только строки, где:
    - `xmin` <= текущая транзакция.
    - `xmax` > текущая транзакция или `NULL`.

---

### **5.2. Dead Tuples и VACUUM**

Из-за MVCC старые версии строк остаются в таблице. Это может привести к раздуванию таблиц.

- **VACUUM**: Удаляет "мёртвые" строки.
    
    ```sql
    VACUUM ANALYZE;
    ```
    
- **Автоматический Autovacuum**:
    
    - Настраивается в `postgresql.conf`:
        
        ```ini
        autovacuum = on
        autovacuum_vacuum_threshold = 50
        autovacuum_vacuum_scale_factor = 0.2
        ```

## **6. Реальные примеры**

---

### **6.1. Пример с Read Committed**

- Транзакция A:
    
    ```sql
    BEGIN;
    UPDATE accounts SET balance = balance - 100 WHERE id = 1;
    -- COMMIT/ROLLBACK;
    ```
    
- Транзакция B:
    
    ```sql
    BEGIN;
    SELECT balance FROM accounts WHERE id = 1;
    ```
    

Транзакция B подождёт завершения транзакции A.

---

### **6.2. Пример с Serializable**

- Транзакция A:
    
    ```sql
    BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    SELECT SUM(balance) FROM accounts;
    ```
    
- Транзакция B:
    
    ```sql
    BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
    UPDATE accounts SET balance = balance + 100 WHERE id = 1;
    ```
    
- Одна из транзакций завершится с ошибкой:
    
    ```
    ERROR: could not serialize access due to concurrent update
    ```
