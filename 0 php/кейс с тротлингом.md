# ✅ **Короткий ответ**

Да. Если библиотека кеширования (или любая структура данных) создаёт большое количество объектов / массивов / ссылок, то PHP-GC (garbage collector) начинает работать агрессивно, что может приводить к:

- скачкам CPU до 80–100%
    
- резкому росту latency
    
- фризам/троттлингу под нагрузкой
    

Особенно это проявляется в **PHP 7.4 и выше**, где GC стал умнее, но всё равно дорогостоящий при больших графах ссылок.

---

# 🔬 **Детальный разбор: почему так происходит**

В PHP сборщик мусора выполняет **cycle collection**:

- PHP освобождает обычные объекты через refcount = 0 (дёшево)
    
- но циклические ссылки (A → B → A) требуют **отдельного прохода GC**
    
- если библиотека кеширования хранит сложные структуры (например, LRU, деревья, multidimensional arrays), там куча циклических ссылок
    

Пример проблемной структуры:

- массив объектов
    
- каждый объект имеет ссылки друг на друга
    
- объекты с замыканиями (`Closure`) внутри
    
- кеши с internal references
    
- графы типа `SplDoublyLinkedList` / `SplObjectStorage`
    

Такие структуры → пиковая нагрузка на GC.

### Когда возникает троттлинг:

- когда сервис крутится как долгоживущий процесс (**php-fpm worker**)
    
- рабочий обрабатывает много запросов до перезапуска
    
- память растёт → ссылки накапливаются → GC запускается чаще
    
- каждый запуск GC = CPU spike
    

Особенно сильно грузит CPU **полный GC-cycle**, когда PHP считает, что объектная графа слишком большая.

---

# 🔥 **Типичный симптом**

- Время ответа растёт скачками (например, каждые 50–200 запросов)
    
- CPU прыгает в момент выполнения GC
    
- Память не растёт бесконечно, но держится около 300–800 МБ на worker
    
- В логах при Xdebug Profiler видишь много вызовов `gc_collect_cycles()`

# 📌 **Конкретные кейсы, когда библиотека кеширования ломает производительность**

## 1. **PSR-6 / PSR-16 кеши, реализованные на массивах**

Например:

- Symfony Cache `ArrayAdapter`
    
- Doctrine ArrayCache
    
- Laravel Array Store
    
- самописные адаптеры
    

Если TTL большой и элементов много → heap разрастается → GC страдает.

## 2. **Высокоуровневые обёртки над Redis/Memcached**

Иногда адаптер превращает ответы Redis в граф объектов (DTO) → циклы.

## 3. **Doctrine ORM UnitOfWork**

Это вообще золотой источник циклических ссылок.

## 4. **Laravel Collections / Cache с вложенными массивами**

Коллекции → замыкания, nested closures → ссылки → GC жрёт CPU.

# 🧠 **Как точно понять, что дело в GC?**

### Способ 1: **включить GC stats**

Добавь в начало приложения:

```php
gc_enable();
gc_set_threshold(10000);
register_shutdown_function(function () {
    var_dump(gc_status());
});
```

Если `runs` растёт а `collected` низкий → GC грузится впустую.

---

### Способ 2: **профилирование через Xdebug / Tideways / Blackfire**

Ты увидишь:

- `gc_collect_cycles` в топ-5 функций по CPU
    
- много времени в `zend_gc.c`
    

---

### Способ 3: **наблюдение за php-fpm worker**

Если worker:

- поднимает CPU до 90%
    
- висит 100–150ms перед отправкой ответа
    
- memory ~400–500MB
    

→ 99% что виноват GC.

---

# 🛠 **Как это исправить**

## 🟢 1. **Не хранить огромные структуры в памяти**

Если кеш с MB-данными — лучше Redis/Memcached.

## 🟢 2. **Отключить GC в PHP-FPM worker**

Да — так реально делают в high-load.

```
php_admin_value[zend.enable_gc] = 0
```

А перезапускать worker через:

- pm.max_requests
    
- time-to-live
    

Быстрый worker умрёт раньше, чем накопятся циклы.

## 🟢 3. **Не использовать ArrayAdapter / ArrayCache в проде**

Они удобны, но убийцы GC.

## 🟢 4. **Профилировать объекты**

Часто в кеш впихивают:

- closures
    
- nested DTO
    
- графы Doctrine entities
    

→ нельза так.

## 🟢 5. **Следить за сериализацией**

Если при кешировании используется `serialize()` → создаются циклические ссылки.

# 💡 Итог

Да — **PHP-сервис может троттлить из-за библиотеки кеширования**, если:

- она создаёт много объектов
    
- структуры имеют циклические ссылки
    
- php-fpm worker живёт долго
    
- GC начинает работать всё чаще
    
- и он один из самых дорогих по CPU компонентов PHP
    

Это — один из классических узких мест в больших проектах.
