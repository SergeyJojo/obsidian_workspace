## **Что такое Apache Kafka?**

Apache Kafka — это распределённая система потоковой обработки данных, которая используется для построения реального времени (real-time) pipelines данных, обработки событий и интеграции систем. Она работает как брокер сообщений, но с акцентом на высокую пропускную способность, отказоустойчивость и горизонтальную масштабируемость.

---

## **Основные компоненты Kafka**

### 1. **Producer (Продюсер)**
   - Отправляет сообщения в Kafka.
   - Пример: веб-приложение, которое отправляет события (например, логи или действия пользователей) в Kafka.

### 2. **Consumer (Консьюмер)**
   - Читает сообщения из Kafka.
   - Пример: микросервис, который обрабатывает события и сохраняет их в базу данных.

### 3. **Broker (Брокер)**
   - Сервер, который хранит сообщения и управляет ими.
   - Kafka-кластер состоит из нескольких брокеров для обеспечения отказоустойчивости и масштабируемости.

### 4. **Topic (Топик)**
   - Логический канал, в который продюсеры отправляют сообщения, а консьюмеры их читают.
   - Пример: топик `user_actions` для хранения событий действий пользователей.

### 5. **Partition (Партиция)**
   - Топик делится на партиции для параллельной обработки.
   - Каждая партиция — это упорядоченная последовательность сообщений.
   - Пример: топик `user_actions` может быть разделён на 3 партиции для увеличения пропускной способности.

### 6. **Offset (Оффсет)**
   - Уникальный идентификатор сообщения внутри партиции.
   - Консьюмеры отслеживают свой прогресс чтения с помощью оффсетов.

### 7. **Consumer Group (Группа консьюмеров)**
   - Группа консьюмеров, которые совместно обрабатывают сообщения из топика.
   - Каждая партиция топика обрабатывается только одним консьюмером из группы.

### 8. **Zookeeper**
   - Координатор, который управляет метаданными Kafka-кластера (например, информация о брокерах, топиках, партициях).
   - В новых версиях Kafka (начиная с 2.8.0) Zookeeper заменяется на **Kafka Raft Metadata (KRaft)** для упрощения архитектуры.

---

## **Как устроена Kafka?**

### **Архитектура Kafka-кластера**
1. **Кластер Kafka** состоит из нескольких брокеров.
2. Каждый брокер хранит часть данных (партиции топиков).
3. Zookeeper (или KRaft) управляет метаданными и координацией между брокерами.
4. Продюсеры отправляют сообщения в топики, а консьюмеры читают их.

### **Репликация и отказоустойчивость**
- Каждая партиция реплицируется на несколько брокеров.
- Одна реплика — лидер (leader), остальные — фолловеры (followers).
- Если лидер падает, один из фолловеров становится новым лидером.

---

## **Топики и партиции**

### **Топик (Topic)**
- Логический канал для сообщений.
- Пример: `orders`, `logs`, `user_actions`.

### **Партиция (Partition)**
- Топик делится на партиции для параллельной обработки.
- Каждая партиция — это упорядоченный лог сообщений.
- Пример: топик `user_actions` с 3 партициями:
  - Партиция 0: сообщения 1, 4, 7, ...
  - Партиция 1: сообщения 2, 5, 8, ...
  - Партиция 2: сообщения 3, 6, 9, ...

### **Ключи сообщений (Keys)**
- Продюсер может указать ключ для сообщения.
- Сообщения с одинаковым ключом попадают в одну партицию.
- Пример: если ключ — это `user_id`, то все сообщения для одного пользователя будут в одной партиции.

---

## **Consumer Groups (Группы консьюмеров)**

- Группа консьюмеров совместно обрабатывает сообщения из топика.
- Каждая партиция топика обрабатывается только одним консьюмером из группы.
- Пример:
  - Топик `user_actions` с 3 партициями.
  - Группа консьюмеров из 3 консьюмеров:
    - Консьюмер 1 обрабатывает партицию 0.
    - Консьюмер 2 обрабатывает партицию 1.
    - Консьюмер 3 обрабатывает партицию 2.

---

## **Пример работы Kafka**

1. **Продюсер отправляет сообщение**:
   - Продюсер отправляет сообщение в топик `user_actions` с ключом `user_id=123`.
   - Kafka определяет партицию для этого ключа (например, партиция 1).

2. **Сообщение записывается в партицию**:
   - Сообщение добавляется в конец лога партиции 1.
   - Ему присваивается оффсет (например, 42).

3. **Консьюмер читает сообщение**:
   - Консьюмер из группы `analytics_group` читает сообщение с оффсетом 42 из партиции 1.
   - Консьюмер обновляет свой оффсет, чтобы продолжить чтение с оффсета 43.

## **Пример кода для работы с Kafka**

### **Продюсер на Python (с использованием `confluent-kafka`)**:
```python
from confluent_kafka import Producer

producer = Producer({'bootstrap.servers': 'localhost:9092'})

def delivery_report(err, msg):
    if err is not None:
        print(f'Message delivery failed: {err}')
    else:
        print(f'Message delivered to {msg.topic()} [{msg.partition()}]')

producer.produce('user_actions', key='123', value='User clicked button', callback=delivery_report)
producer.flush()
```

### **Консьюмер на Python**:
```python
from confluent_kafka import Consumer

consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'analytics_group',
    'auto.offset.reset': 'earliest'
})

consumer.subscribe(['user_actions'])

while True:
    msg = consumer.poll(1.0)
    if msg is None:
        continue
    if msg.error():
        print(f"Consumer error: {msg.error()}")
        continue
    print(f"Received message: {msg.value().decode('utf-8')}")
```

## **Вопросы на собеседовании по Kafka**

1. **Что такое Kafka и для чего она используется?**
   - Kafka — это распределённая система потоковой обработки данных, которая используется для передачи и обработки сообщений в реальном времени.

2. **Чем Kafka отличается от RabbitMQ?**
   - Kafka ориентирована на высокую пропускную способность и долгосрочное хранение данных, в то время как RabbitMQ лучше подходит для сложных маршрутизаций и гарантированной доставки.

3. **Что такое партиции и зачем они нужны?**
   - Партиции позволяют разделить топик на несколько частей для параллельной обработки и увеличения пропускной способности.

4. **Как Kafka обеспечивает отказоустойчивость?**
   - Через репликацию партиций на несколько брокеров. Если один брокер падает, его партиции могут быть обработаны другими брокерами.

5. **Что такое Consumer Group?**
   - Это группа консьюмеров, которые совместно обрабатывают сообщения из топика, распределяя партиции между собой.

## **1. Сбор и обработка логов (Log Aggregation)**

### **Проблема:**
- В распределённой системе (например, микросервисной архитектуре) логи генерируются на множестве серверов.
- Нужно централизованно собирать, хранить и анализировать логи.

### **Решение с Kafka:**
- Каждый микросервис отправляет логи в Kafka (например, в топик `logs`).
- Kafka выступает как буфер для логов.
- Консьюмеры (например, Elasticsearch, Splunk) читают логи из Kafka и сохраняют их в хранилище для дальнейшего анализа.

### **Пример:**
- **Uber** использует Kafka для сбора логов от тысяч микросервисов и их обработки в реальном времени.

## **2. Трекинг действий пользователей (User Activity Tracking)**

### **Проблема:**
- В приложении (например, интернет-магазине) нужно отслеживать действия пользователей (клики, просмотры, покупки).
- Эти данные используются для аналитики, персонализации и рекомендаций.

### **Решение с Kafka:**
- События действий пользователей отправляются в Kafka (например, в топик `user_actions`).
- Консьюмеры обрабатывают эти события:
  - Сохраняют в базу данных для аналитики.
  - Используют для построения рекомендательных систем.

### **Пример:**
- **LinkedIn** использует Kafka для трекинга действий пользователей (например, просмотры профилей, лайки) и построения рекомендаций.

## **3. Обработка транзакций в реальном времени (Real-time Transaction Processing)**

### **Проблема:**
- В финансовых системах (например, банки, платежные системы) нужно обрабатывать транзакции в реальном времени.
- Транзакции должны быть обработаны быстро и надёжно.

### **Решение с Kafka:**
- Транзакции отправляются в Kafka (например, в топик `transactions`).
- Консьюмеры обрабатывают транзакции:
  - Проверяют на мошенничество.
  - Обновляют балансы пользователей.
  - Отправляют уведомления.

### **Пример:**
- **PayPal** использует Kafka для обработки миллионов транзакций в реальном времени.

## **4. Синхронизация данных между микросервисами (Data Synchronization)**

### **Проблема:**
- В микросервисной архитектуре данные должны быть синхронизированы между разными сервисами.
- Например, изменение данных в одном сервисе должно быть отражено в другом.

### **Решение с Kafka:**
- События изменений данных отправляются в Kafka (например, в топик `data_changes`).
- Другие микросервисы подписываются на эти события и обновляют свои данные.

### **Пример:**
- **Netflix** использует Kafka для синхронизации данных между микросервисами, например, для обновления информации о пользователях.

### **Основные сценарии использования Kafka в разработке**
1. **Асинхронная коммуникация между микросервисами**  
   Сервисы обмениваются сообщениями через Kafka, что позволяет:
   - Уменьшить связность между компонентами.
   - Обрабатывать пиковые нагрузки без блокировки отправителя.
   - Гарантировать доставку сообщений даже при падении сервисов.

   Пример:  
   Сервис заказов публикует событие `OrderCreated` в топик Kafka, а сервис доставки и сервис уведомлений подписываются на него.

2. **Сбор и обработка логов/метрик**  
   Kafka выступает буфером для потоковой передачи данных в системы мониторинга (Prometheus, Grafana) или хранилища (Elasticsearch).

3. **Event Sourcing**  
   Сохранение всех изменений состояния системы в виде событий, что позволяет воссоздать состояние в любой момент времени.

4. **Трансформация данных**  
   Промежуточный слой между источниками данных (например, базами) и потребителями (аналитическими системами).

### **Как Kafka используется в Go**
- **Библиотеки**:  
  - `Sarama` — популярная Go-библиотека для работы с Kafka.  
  - `confluent-kafka-go` — обертка над официальным C-библиотекой (высокая производительность).  
  - `kafka-go` — альтернативная библиотека с упором на простоту API.

- **Пример Producer на Go (Sarama)**:
  ```go
  producer, _ := sarama.NewSyncProducer([]string{"kafka:9092"}, nil)
  defer producer.Close()

  msg := &sarama.ProducerMessage{
      Topic: "orders",
      Value: sarama.StringEncoder(`{"order_id": 123}`),
  }

  partition, offset, _ := producer.SendMessage(msg)
  fmt.Printf("Сообщение отправлено: partition=%d, offset=%d\n", partition, offset)
  ```

- **Пример Consumer на Go**:
  ```go
  consumer, _ := sarama.NewConsumer([]string{"kafka:9092"}, nil)
  defer consumer.Close()

  partitionConsumer, _ := consumer.ConsumePartition("orders", 0, sarama.OffsetOldest)
  defer partitionConsumer.Close()

  for msg := range partitionConsumer.Messages() {
      fmt.Printf("Получено сообщение: %s\n", string(msg.Value))
  }
  ```

### **Чем можно «пофлексить» на собеседовании**
1. **Exactly-Once Semantics (EOS)**  
   - Знание, как добиться гарантии «ровно одна доставка» через `idempotent producer` и транзакции.  
   - Пример:  
     ```go
     config := sarama.NewConfig()
     config.Producer.Idempotent = true
     config.Producer.RequiredAcks = sarama.WaitForAll
     config.Net.MaxOpenRequests = 1
     ```

2. **Consumer Groups и Rebalance**  
   - Объяснение, как Kafka распределяет партиции между консьюмерами в группе.  
   - Пример обработки ребалансировки:
     ```go
     consumer, _ := sarama.NewConsumerGroup([]string{"kafka:9092"}, "my-group", config)
     ```

### **Типовые вопросы на собеседовании**
8. **Как гарантировать порядок сообщений в Kafka?**  
   *Ответ:* Использовать партиции — сообщения в одной партиции обрабатываются строго по порядку. Для этого нужно указывать ключ сообщения (`Key`), чтобы все сообщения с одним ключом попадали в одну партицию.

9. **Что делать, если консьюмер не успевает обрабатывать сообщения?**  
   *Ответ:* Увеличить количество партиций и консьюмеров в группе, настроить `fetch.min.bytes` и `fetch.max.wait.ms`.

10. **Как избежать потери сообщений?**  
   *Ответ:* Для продюсера — использовать `acks=all` и `retries=N`. Для консьюмера — отключать авто-коммит и коммитить оффсеты только после обработки.
