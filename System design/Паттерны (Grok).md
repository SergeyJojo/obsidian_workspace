Что такое паттерны системного дизайна?

- Это проверенные шаблоны для решения типичных задач в разработке распределённых систем.
    
- Помогают справляться с нагрузкой, отказоустойчивостью, масштабируемостью и поддержкой.
    

Я разобью их на категории: данные, производительность, надёжность, коммуникация.

---

1. Паттерны работы с данными

1.1. Partitioning (Шардинг)

- Что это: Разделение данных на части (шарды) по ключу или диапазону.
    
- Зачем: Уменьшить нагрузку на одну БД, распределить данные по серверам.
    
- Как работает:
    
    - Range-based: Данные делятся по диапазону (например, user_id от 1 до 1000 — шард 1).
        
    - Hash-based: Хэш ключа определяет шард (например, hash(user_id) % 4).
        
- Пример: В Instagram посты делят по user_id на разные шарды.
    
- Плюсы: Масштабируемость.
    
- Минусы: Сложно ребалансировать, горячие ключи (hotspots).
    

1.2. Replication (Репликация)

- Что это: Копирование данных на несколько серверов.
    
- Зачем: Увеличить отказоустойчивость и скорость чтения.
    
- Как работает:
    
    - Master-Slave: Один мастер пишет, слейвы читают.
        
    - Master-Master: Все пишут и читают (сложнее синхронизация).
        
- Пример: MySQL с главным сервером и репликами для чтения.
    
- Плюсы: Высокая доступность.
    
- Минусы: Задержки синхронизации, конфликты.
    

1.3. Write-Ahead Logging (WAL)

- Что это: Логирование операций перед записью в основное хранилище.
    
- Зачем: Обеспечить восстановление после сбоев.
    
- Как работает: Пишешь в лог, потом в БД; при краше восстанавливаешь из лога.
    
- Пример: PostgreSQL использует WAL для транзакций.
    
- Плюсы: Надёжность.
    
- Минусы: Оверхед на запись.
    

---

2. Паттерны производительности

2.1. Caching (Кэширование)

- Что это: Хранение часто запрашиваемых данных в быстром доступе.
    
- Зачем: Ускорить чтение, снять нагрузку с БД.
    
- Как работает:
    
    - In-memory: Redis, Memcached.
        
    - Write-through: Пишешь в кэш и БД одновременно.
        
    - Write-back: Пишешь в кэш, потом асинхронно в БД.
        
- Пример: Кэш страниц в CDN (Cloudflare).
    
- Плюсы: Быстродействие.
    
- Минусы: Устаревание данных (cache invalidation).
    

2.2. Load Balancing (Балансировка нагрузки)

- Что это: Распределение запросов между серверами.
    
- Зачем: Избежать перегрузки одного сервера.
    
- Как работает:
    
    - Round Robin: По очереди.
        
    - Least Connections: К серверу с минимумом активных соединений.
        
- Пример: Nginx перед кластером веб-серверов.
    
- Плюсы: Масштабируемость.
    
- Минусы: Нужна синхронизация сессий.
    

2.3. CQRS (Command Query Responsibility Segregation)

- Что это: Разделение операций записи (Commands) и чтения (Queries).
    
- Зачем: Оптимизировать производительность для разных нагрузок.
    
- Как работает: Отдельные модели/БД для записи и чтения.
    
- Пример: Запись заказов в SQL, чтение статистики из NoSQL.
    
- Плюсы: Гибкость, скорость.
    
- Минусы: Сложность синхронизации.
    

---

3. Паттерны надёжности

3.1. Circuit Breaker (Автоматический выключатель)

- Что это: Прерывание запросов к сервису при сбоях.
    
- Зачем: Защитить систему от каскадных отказов.
    
- Как работает:
    
    - Норма: запросы идут.
        
    - Сбой: "выключатель" открывается, запросы блокируются.
        
    - Восстановление: частично пропускает, проверяет.
        
- Пример: Hystrix в микросервисах.
    
- Плюсы: Устойчивость.
    
- Минусы: Нужна настройка порогов.
    

3.2. Retry Pattern (Повторные попытки)

- Что это: Повтор запроса при временных сбоях.
    
- Зачем: Увеличить надёжность при сетевых ошибках.
    
- Как работает: Экспоненциальная задержка (backoff) между попытками.
    
- Пример: HTTP-клиент с retry-after.
    
- Плюсы: Простота.
    
- Минусы: Может усилить нагрузку.
    

3.3. Bulkhead (Переборка)

- Что это: Изоляция ресурсов для разных частей системы.
    
- Зачем: Ограничить влияние сбоев.
    
- Как работает: Отдельные пулы потоков/соединений для сервисов.
    
- Пример: Разные пулы соединений к БД в пуле микросервисов.
    
- Плюсы: Отказоустойчивость.
    
- Минусы: Больше ресурсов.
    

---

4. Паттерны коммуникации

4.1. Message Queue (Очередь сообщений)

- Что это: Асинхронная передача данных через очередь.
    
- Зачем: Развязать продюсеров и консьюмеров.
    
- Как работает: Продюсер пишет в очередь (Kafka, RabbitMQ), консьюмер читает.
    
- Пример: Обработка заказов в интернет-магазине.
    
- Плюсы: Масштабируемость, надёжность.
    
- Минусы: Сложность мониторинга.
    

4.2. Publish-Subscribe (Pub/Sub)

- Что это: Рассылка сообщений подписчикам.
    
- Зачем: Уведомлять множество компонентов.
    
- Как работает: Издатель шлёт в топик, подписчики получают.
    
- Пример: Google Pub/Sub для логов.
    
- Плюсы: Гибкость.
    
- Минусы: Потеря сообщений без гарантий.
    

4.3. API Gateway

- Что это: Единая точка входа для запросов к микросервисам.
    
- Зачем: Упростить доступ, добавить безопасность.
    
- Как работает: Проксирует запросы, делает авторизацию, балансировку.
    
- Пример: AWS API Gateway перед сервисами.
    
- Плюсы: Удобство, контроль.
    
- Минусы: Единая точка отказа.
    

---

5. Дополнительные паттерны

5.1. Event Sourcing

- Что это: Хранение состояния как последовательности событий.
    
- Зачем: Восстановление и аудит.
    
- Как работает: Вместо текущего состояния — лог событий (Kafka).
    
- Пример: Банк фиксирует транзакции.
    
- Плюсы: Полная история.
    
- Минусы: Сложность обработки.
    

5.2. Sidecar

- Что это: Дополнительный сервис рядом с основным.
    
- Зачем: Вынести сквозную логику (логи, мониторинг).
    
- Как работает: Контейнер рядом с приложением (Istio).
    
- Пример: Логирование через sidecar в Kubernetes.
    
- Плюсы: Разделение ответственности.
    
- Минусы: Увеличивает ресурсы.
    

5.3. Strangler Fig (Удавка)

- Что это: Постепенная замена legacy-системы.
    
- Зачем: Миграция без остановки.
    
- Как работает: Новый код "обвивает" старый, перенаправляя запросы.
    
- Пример: Рефакторинг монолита в микросервисы.
    
- Плюсы: Безопасность.
    
- Минусы: Долгий процесс.

Пример в коде (Go)

Вот как можно реализовать простую очередь сообщений (Message Queue):

go

```go
package main

import (
    "fmt"
    "sync"
)

type MessageQueue struct {
    queue []string
    mu    sync.Mutex
}

func (mq *MessageQueue) Publish(msg string) {
    mq.mu.Lock()
    defer mq.mu.Unlock()
    mq.queue = append(mq.queue, msg)
}

func (mq *MessageQueue) Consume() string {
    mq.mu.Lock()
    defer mq.mu.Unlock()
    if len(mq.queue) == 0 {
        return ""
    }
    msg := mq.queue[0]
    mq.queue = mq.queue[1:]
    return msg
}

func main() {
    mq := MessageQueue{}
    mq.Publish("Order #1")
    mq.Publish("Order #2")
    fmt.Println(mq.Consume()) // Order #1
    fmt.Println(mq.Consume()) // Order #2
}
```

- Это примитивный пример, в реале юзают Kafka или RabbitMQ.
