## 🧠 Общая идея интерфейсов в Go

Go поддерживает **интерфейсы**, которые дают **динамический диспетчинг методов** — то есть **вызов метода, не зная точного типа во время компиляции**.

Пример:

```go
type Speaker interface {
    Speak()
}

type Person struct{}

func (p Person) Speak() {
    fmt.Println("Hello!")
}
```

---

## 🚨 Go реализует интерфейсы **через скрытые структуры**, которые отличаются для:

- **пустого интерфейса** (`interface{}`) → `eface`
    
- **непустого интерфейса** (`interface{SomeMethod()}`) → `iface`
    

---

# 🧩 Структуры интерфейсов в runtime

---

## 🔹 `eface` (empty interface)

Пустой интерфейс `interface{}` описывается структурой:

```go
type eface struct {
    _type *_type    // информация о типе (указатель на runtime._type)
    data  unsafe.Pointer  // указатель на данные (значение)
}
```

🔸 Пример:

```go
var x interface{} = 42
```

Внутри:

- `_type` → информация о типе `int`
    
- `data` → указатель на само значение `42`
    

---

## 🔹 `iface` (non-empty interface)

Когда интерфейс содержит хотя бы **один метод**, используется другая структура:

```go
type iface struct {
    tab  *itab         // таблица методов + информация о типе
    data unsafe.Pointer // указатель на значение
}
```

---

## 📐 Структура `itab`

```go
type itab struct {
    inter  *interfacetype // описание интерфейса (его методы)
    _type  *_type         // описание конкретного типа (например, *MyStruct)
    hash   uint32         // хеш типа для быстрой проверки
    _      [4]byte        // padding
    fun    [1]uintptr     // массив указателей на функции (vtable)
}
```

🔹 Важно: `fun` — это `vtable`, аналог виртуальной таблицы в C++, где `fun[0]` — указатель на первую реализацию метода, `fun[1]` — на вторую и т.д.

---

## 🔧 Пример разбора `iface`

```go
type Speaker interface {
    Speak()
}

type Human struct{}

func (Human) Speak() { fmt.Println("I'm a human.") }

var s Speaker = Human{}
```

Под капотом:

- `s` — переменная типа `iface`
    
- `s.tab` — `itab`:
    
    - `inter` → содержит метод `Speak()`
        
    - `_type` → указывает на `Human`
        
    - `fun[0]` → указывает на `Human.Speak`
        
- `s.data` → указывает на `Human{}`
    

---

## 🔍 Что делает компилятор Go?

### При присваивании:

```go
var s Speaker = Human{}
```

1. Компилятор создаёт `itab` между `Speaker` и `Human`.
    
2. `Human{}` аллоцируется в heap (или stack).
    
3. `iface.tab` = `itab`, `iface.data` = указатель на `Human{}`.
    

---

## 🔬 Как вызывается метод?

```go
s.Speak()
```

На уровне рантайма:

```go
s.tab.fun[0](s.data)
```

То есть:

- Компилятор **не знает**, что `s` — это `Human`
    
- Но знает, что `tab.fun[0]` — это `Speak()`
    
- Вызов идёт через **vtable** — динамически
    

---

## 🔒 Почему в Go нет nil-паники при вызове метода интерфейса?

Если `iface.data == nil`, но `tab != nil` — ты получишь панику при вызове метода. Потому что Go всё равно попытается вызвать функцию через `fun[i](data)` — а `data == nil`.

---

## ⚠️ К чему всё это приводит?

| Явление                                            | Причина                              |
| -------------------------------------------------- | ------------------------------------ |
| `interface != nil` но `interface.(T)` паникует     | `iface.tab != nil`, но `data == nil` |
| Медленные вызовы методов через интерфейс           | Динамический вызов по `vtable`       |
| Нельзя сравнивать интерфейсы напрямую без костылей | Нужно сравнивать `_type` + `data`    |

## 👀 Бонус: как посмотреть `eface/iface` в `delve`

```bash
dlv debug
```

Внутри:

```go
var x interface{} = 123
```

В `delve`:

```bash
print x
print *(runtime.eface*)&x
```

Или:

```go
import "unsafe"

func inspect(x interface{}) {
    ef := (*[2]uintptr)(unsafe.Pointer(&x))
    fmt.Printf("type: %x, data: %x\n", ef[0], ef[1])
}
```

---

## ✅ Вывод

Интерфейс в Go — это **указатель на таблицу методов + указатель на данные**.

- `interface{}` — просто `_type + data`
    
- `interface{method}` — `itab + data`
    
- Таблица методов (`fun`) позволяет **динамически вызывать методы**
    
- Благодаря этому Go реализует **динамический полиморфизм без виртуальных классов**
