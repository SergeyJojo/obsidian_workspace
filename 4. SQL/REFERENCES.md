Отличный вопрос, Сергей 👍. В PostgreSQL **`REFERENCES`** — это способ задать внешний ключ (foreign key constraint). Давай разберёмся глубоко:

---

## 🔹 Что такое `REFERENCES`

`REFERENCES` — это **ограничение ссылочной целостности**.  
Оно говорит: _значение в одном столбце должно существовать в другом (родительском) столбце_.

Пример:

```sql
CREATE TABLE users (
    id SERIAL PRIMARY KEY,
    name TEXT
);

CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(id) ON DELETE CASCADE,
    amount NUMERIC
);
```

👉 Здесь `orders.user_id` **ссылается на** `users.id`.  
То есть нельзя вставить заказ на `user_id=999`, если такого пользователя нет.

---

## 🔹 Механика

- PostgreSQL при вставке/обновлении в таблице с foreign key проверяет, есть ли соответствующая запись в родительской таблице.
    
- При удалении/обновлении в родительской таблице проверяет, что делать с дочерними строками.
    

---

## 🔹 Варианты действий (`ON DELETE` / `ON UPDATE`)

Когда строка в родительской таблице изменяется или удаляется:

- **`NO ACTION`** (по умолчанию) — если в дочерней таблице есть ссылки, операция отменяется.
    
- **`RESTRICT`** — аналог `NO ACTION`, только проверяется немедленно (а не в конце транзакции).
    
- **`CASCADE`** — изменение/удаление родителя тянет за собой дочерние строки.
    
- **`SET NULL`** — в дочерней строке поле станет `NULL`.
    
- **`SET DEFAULT`** — поле получит значение по умолчанию.
    

Пример:

```sql
user_id INT REFERENCES users(id) ON DELETE CASCADE
```

👉 если удалить пользователя, удалятся и все его заказы.

---

## 🔹 Особенности PostgreSQL

1. **Индексы**
    
    - Для внешнего ключа PostgreSQL **не создаёт индекс автоматически**.
        
    - Но для родительского ключа (`users.id`) индекс обязателен (обычно это `PRIMARY KEY` или `UNIQUE`).
        
    - Для дочернего (`orders.user_id`) индекс нужен для скорости join'ов и проверок, но его надо создавать вручную.
        
2. **Целостность**
    
    - Проверки выполняются внутри транзакции.
        
    - Можно временно отключить проверки через `DEFERRABLE INITIALLY DEFERRED`, и они будут проверяться только при `COMMIT`.
        
3. **Составные ключи**
    
    - `REFERENCES` может ссылаться не только на один столбец, но и на составной `PRIMARY KEY` или `UNIQUE`.
        

Пример:

```sql
REFERENCES parent(col1, col2)
```

---

## 🔹 Плюсы использования

- Гарантия, что данные консистентные.
    
- Упрощение логики приложения (часть проверок выполняется самой БД).
    
- Хорошо работает для транзакционных систем.
    

---

## 🔹 Минусы / трейдоффы

- Каждая проверка = дополнительные накладные расходы.
    
- Может тормозить массовые вставки/удаления.
    
- В больших распределённых системах (микросервисы) часто избегают внешних ключей в БД → вместо этого делают **логическую целостность на уровне приложения**.
