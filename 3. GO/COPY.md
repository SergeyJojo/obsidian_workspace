Хороший вопрос, Сергей 👍  
Функция `copy` в Go кажется "магией", но на самом деле она довольно чётко описана в спецификации языка. Давай разберёмся, как она устроена **на уровне документации и реализации**.

---

## 📖 Спецификация Go (официальное описание)

В [Go Specification](https://go.dev/ref/spec#Appending_and_copying_slices) сказано:

- `copy(dst, src []T) int`
    
- Копирует элементы из `src` в `dst`.
    
- Копирование идёт **слева направо** (от младших индексов к старшим).
    
- Количество реально скопированных элементов = `min(len(src), len(dst))`.
    
- Возвращает число скопированных элементов.
    
- Если `src` и `dst` пересекаются (ссылаются на один и тот же массив), поведение безопасное — порядок гарантирован (как при `memmove`, а не `memcpy`).
    

---

## 📦 Как это устроено в рантайме

В стандартной библиотеке нет реализации `copy` как обычной функции. Это **встроенная функция компилятора** (intrinsic).

В Go исходники это можно увидеть в `builtin.go`:

```go
func copy(dst, src []Type) int
```

но без реализации — потому что она подменяется компилятором.

На уровне рантайма (`runtime/slice.go`) компилятор разворачивает вызов `copy` в вызов функции:

```go
func slicecopy(to, from slice, wid uintptr) int
```

где:

- `to` и `from` — внутренние структуры `slice` (содержат указатель на массив, длину и capacity),
    
- `wid` — размер одного элемента (в байтах).
    

---

## ⚙️ Что делает `slicecopy`

1. Определяет `n = min(len(to), len(from))`.
    
2. Если `n == 0`, возвращает 0.
    
3. Вычисляет количество байт: `nbytes = uintptr(n) * wid`.
    
4. В зависимости от типа данных:
    
    - Если элемент "простой" (байтовые массивы, int и т.д.) — использует низкоуровневую функцию `memmove` из runtime.
        
    - Если элемент сложный (строки, интерфейсы, указатели) — копирование требует правильного управления ссылками (чтобы GC видел живые объекты). Для этого используется `typedmemmove`.
        

---

## 🔍 Отличие от append

- `append` может расширить слайс (создать новый массив при нехватке места).
    
- `copy` **никогда не меняет capacity и длину** слайсов, только переносит данные.
    

---

## 🧠 Важный момент для GC

Почему нельзя просто `memcpy`?  
Потому что в Go есть **сборщик мусора**, и если элемент содержит указатели (строки, интерфейсы, структуры с указателями), GC должен знать, что новые ячейки массива указывают на живые объекты. Поэтому `copy` вызывает `typedmemmove`, которое обновляет метаданные для GC.

---

## 📊 Пример работы

```go
a := []int{1, 2, 3}
b := []int{9, 9, 9, 9}

n := copy(b, a) 
fmt.Println(b, n) // [1 2 3 9]  3
```

- Скопировали **3 элемента** (минимум из `len(a)=3` и `len(b)=4`).
    
- Возвращаемое значение — число реально скопированных элементов.
    

---

👉 В итоге:  
`copy` в Go — это **встроенная функция компилятора**, которая компилируется в вызов `runtime.slicecopy`, а дальше — в `memmove` или `typedmemmove` (в зависимости от типа). Она безопасна при перекрытии и интегрирована с GC.
