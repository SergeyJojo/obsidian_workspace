
### **1. Что такое TLB?**
**TLB (Translation Lookaside Buffer)** — это **специальный кеш процессора**, который ускоряет преобразование виртуальных адресов в физические (т. е. работу **MMU — Memory Management Unit**).

#### **Как работает TLB?**
- Когда процесс обращается к памяти по **виртуальному адресу**, MMU должен найти соответствующий **физический адрес** через таблицу страниц (Page Table).
- **Page Table** хранится в ОЗУ, и доступ к ней медленный.
- **TLB** кеширует последние использованные преобразования `виртуальный → физический адрес`, чтобы избежать полного прохода по Page Table.

#### **Структура TLB**
- Обычно это **ассоциативный кеш** (fully/set-associative), где:
  - **Ключ**: Виртуальный адрес (или его часть, например, `VPN — Virtual Page Number`).
  - **Значение**: Физический адрес + флаги прав доступа (R/W/X, User/Kernel).
- **Пример работы**:
  ```
  Виртуальный адрес 0x7ffeefbff000 → TLB проверяет, есть ли запись.
  - Если есть (TLB hit) → сразу возвращает физический адрес.
  - Если нет (TLB miss) → MMU ищет в Page Table и обновляет TLB.
  ```

#### **Почему TLB важен при переключении контекста?**
- У каждого процесса **своя таблица страниц** (Page Table).
- При переключении процессов **TLB становится невалидным**, так как старые записи ссылаются на память предыдущего процесса.
- **Решения**:
  1. **Полная очистка TLB** (flush) при переключении (простейший способ, но снижает производительность).
  2. **ASID (Address Space ID)** — метка процесса в TLB, чтобы не очищать его полностью (используется в современных CPU).

### **2. Как происходит переключение контекста процессов?**
**Переключение контекста (Context Switch)** — это замена одного выполняемого процесса/потока другим.  
Происходит при:
- Истечении **кванта времени** (scheduler tick).
- **Системном вызове** (например, `read()` блокирует процесс).
- **Прерывании** (I/O завершён, сигнал и т. д.).

#### **Шаги переключения контекста**
1. **Сохранить состояние текущего процесса**:
   - **Регистры CPU** (RAX, RBX, RIP, RSP и т. д.) сохраняются в **PCB (Process Control Block)**.
   - **Состояние FPU/SSE** (если используется).
   - **Указатель на текущую Page Table** (CR3 в x86).

2. **Выбор нового процесса**:
   - Планировщик (например, **CFS в Linux**) выбирает следующий процесс из очереди `runqueue`.

3. **Загрузить состояние нового процесса**:
   - Восстановить регистры из его PCB.
   - **Переключить таблицу страниц** (записать новый адрес в CR3 → **инвалидация TLB**).
   - Обновить кеш процессора (если нужно).

4. **Возобновление выполнения**:
   - CPU продолжает выполнение с точки, сохранённой в PCB (значение RIP).

#### **Временные затраты**
| **Операция**               | **Примерное время**       |
|----------------------------|--------------------------|
| Сохранение/восстановление регистров | ~100–500 нс |
| Переключение Page Table + TLB flush | ~100–1000 нс |
| Кеш-промахи (Cache misses) | ~1000–5000 нс (если данные не в L1/L2) |

#### **Разница между переключением процессов и потоков**
| **Критерий** | **Переключение процессов**         | **Переключение потоков**           |
| ------------ | ---------------------------------- | ---------------------------------- |
| **Память**   | Новая Page Table (CR3) + TLB flush | Та же Page Table (CR3 не меняется) |
| **Ресурсы**  | Полная изоляция                    | Общая память, FD, переменные       |
| **Время**    | Дорого (TLB/cache penalties)       | Дешевле (только регистры/стек)     |

### **3. Как TLB и переключение контекста влияют на производительность?**
1. **TLB-промахи после переключения**:
   - После смены процесса первые обращения к памяти приводят к TLB misses → замедление.
   - **Решение**: Использовать **ASID** (не очищать TLB полностью) или **большие страницы (HugePages)**.

2. **Кеш-промахи (Cache misses)**:
   - Данные нового процесса могут не быть в кеше CPU (L1/L2/L3) → дополнительные задержки.

3. **Оптимизации в Linux**:
   - **Preemption** (вытеснение) с минимальными задержками.
   - **Thread Local Storage (TLS)** для быстрого доступа к данным потока.

---

### **Вывод**
- **TLB** — это кеш трансляции адресов, критичный для скорости работы с памятью.  
- **Переключение контекста** требует сохранения/восстановления состояния процесса и очистки TLB (если нет ASID).  
- **Потоки переключаются быстрее процессов**, так как не требуют смены таблицы страниц.  

Если нужно минимизировать накладные расходы:
- Используйте **потоки вместо процессов** (если допустимо).
- Увеличьте **квант времени планировщика** (но это снизит интерактивность).
- Применяйте **асинхронные модели** (например, `epoll`/`io_uring`), чтобы реже переключать контекст.
