
Паттерн **Outbox** — это архитектурный паттерн, который используется в распределенных системах для гарантированной доставки сообщений и обеспечения надежности между сервисами, особенно в случае, когда один сервис должен отправлять сообщения в другой сервис или систему, и необходимо избежать потери сообщений или дублирования.

Этот паттерн помогает решить проблемы, связанные с **согласованностью** и **надёжностью** в распределенных системах, особенно в контексте **event-driven architecture** (событийно-ориентированных архитектур), и применяется в ситуациях, когда нужно обеспечить целостность данных между двумя системами при сбоях, транзакциях или асинхронной коммуникации.

### Проблема, которую решает паттерн Outbox

Предположим, у нас есть микросервисная архитектура, и один сервис (например, **Order Service**) должен отправить сообщение в другой сервис (например, **Shipping Service**) о создании нового заказа. Когда заказ создается, сервис **Order Service** должен одновременно:

1. Сохранить информацию о заказе в своей базе данных.
2. Отправить сообщение в очередь сообщений (например, Kafka, RabbitMQ и т. д.), чтобы другой сервис знал, что новый заказ был создан.

Но возникает проблема: если система неожиданно падает после того, как заказ был записан в базу данных, но сообщение не было отправлено, мы потеряем важную информацию. В то же время, если сообщение было отправлено, но изменения в базе данных не были завершены (например, из-за сбоя транзакции), мы получим неконсистентное состояние.

Паттерн **Outbox** помогает решить эту проблему, обеспечивая, что оба действия (сохранение данных и отправка сообщения) происходят атомарно и могут быть восстановлены при сбое.

### Как работает паттерн Outbox?

1. **Outbox Table**:
    
    - В базе данных сервиса (например, **Order Service**) добавляется специальная таблица **Outbox**.
    - Эта таблица предназначена для хранения сообщений, которые сервис должен отправить в другие системы или сервисы.
    - Каждое сообщение представляет собой запись в таблице с необходимой информацией (например, ID события, тело сообщения, тип события и статус).
2. **Процесс записи**:
    
    - Когда происходит важное событие (например, создание заказа), сервис записывает это событие в таблицу **Outbox** в своей базе данных как часть своей транзакции.
    - Таким образом, гарантируется, что сообщение будет сохранено только в том случае, если данные успешно сохранены в основной таблице.
3. **Процесс отправки сообщений**:
    
    - После того как событие записано в таблицу **Outbox**, отдельный процесс (или задача) извлекает эти сообщения и отправляет их в очередь сообщений или на событие-ориентированную шину (например, Kafka).
    - Когда сообщение отправлено успешно, оно помечается как отправленное (например, обновляется флаг в таблице **Outbox**).
4. **Гарантии**:
    
    - Если система падает после записи в **Outbox**, но до отправки сообщения, при перезапуске сервиса процесс доставки сообщений будет повторен, так как сообщения все ещё находятся в таблице **Outbox**.
    - Поскольку сообщение и транзакция с данными происходят атомарно (в одном контексте базы данных), мы избегаем проблемы потери данных или рассинхронизации между сервисами.
5. **Механизм повторной отправки**:
    
    - Некоторые реализации паттерна **Outbox** могут включать механизм повторных попыток отправки сообщений (например, с использованием очередей сообщений или фоновых задач), чтобы гарантировать доставку сообщений, даже если сервис временно недоступен.

### Преимущества паттерна Outbox:

1. **Атомарность**: Все действия (сохранение данных и отправка сообщений) выполняются в рамках одной транзакции, что предотвращает рассинхронизацию между состоянием данных и состоянием сообщений.
2. **Отказоустойчивость**: Паттерн обеспечивает восстановление после сбоев. Даже если сервис временно выходит из строя, сообщения, которые нужно было отправить, будут сохранены и отправлены позже.
3. **Простота реализации**: Этот паттерн можно реализовать с использованием стандартных механизмов транзакций в реляционных базах данных, без необходимости в сложной логике или внешних инструментов.
4. **Отслеживание событий**: Таблица **Outbox** служит для хранения всех событий, что позволяет отслеживать и контролировать все события, которые были или должны быть отправлены.

### Недостатки паттерна Outbox:

1. **Увеличение сложности**: Требуется создание и поддержка дополнительной таблицы для хранения сообщений, а также процесс мониторинга и повторной отправки сообщений.
2. **Производительность**: Если база данных обрабатывает большое количество транзакций и сообщений, то таблица **Outbox** может стать узким местом, так как каждый запрос на отправку сообщений должен извлекать данные из базы.
3. **Необходимость фоновых процессов**: Для извлечения и отправки сообщений необходимо иметь фоновый процесс или задачу, которая будет периодически опрашивать таблицу и отправлять сообщения.

### Пример реализации паттерна Outbox

Предположим, у нас есть таблица заказов и таблица **Outbox** для **Order Service**:

1. **Таблица заказов**:
    
    ```sql
    CREATE TABLE orders (
        id SERIAL PRIMARY KEY,
        user_id INT NOT NULL,
        total_amount DECIMAL(10, 2) NOT NULL,
        status VARCHAR(20) NOT NULL
    );
    ```
    
2. **Таблица Outbox**:
    
    ```sql
    CREATE TABLE outbox (
        id SERIAL PRIMARY KEY,
        event_type VARCHAR(100) NOT NULL,
        event_payload JSONB NOT NULL,
        status VARCHAR(20) DEFAULT 'pending',
        created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
    );
    ```
    
3. **Процесс транзакции (с использованием паттерна Outbox)**:
    
    - Когда заказ создается в **Order Service**, происходит следующая последовательность:
        1. Запись данных о заказе в таблицу **orders**.
        2. Запись события в таблицу **outbox** (например, событие "ORDER_CREATED").
4. **Фоновый процесс**:
    
    - Фоновый процесс или сервис извлекает записи из **Outbox**, отправляет их в очередь сообщений (например, RabbitMQ, Kafka), и обновляет статус записей в **Outbox** на "sent".

### Заключение

Паттерн **Outbox** решает проблему гарантированной доставки сообщений в распределенных системах, обеспечивая атомарность записи данных и отправки сообщений. Он гарантирует, что данные и сообщения будут синхронизированы, даже если система временно выйдет из строя, что важно для обеспечения надежности и целостности в микросервисных и событийно-ориентированных архитектурах.
