
Отличный вопрос — эти параметры конфигурации PostgreSQL играют **ключевую роль в управлении памятью** и сильно влияют на производительность. Давай разберем каждый:

---

## 🔹 `shared_buffers` — **буферный кэш PostgreSQL**

### 📌 Что это:

- Это **область оперативной памяти**, которую PostgreSQL использует для **кэширования данных таблиц и индексов**.
    
- Все данные, читаемые с диска, сначала попадают в `shared_buffers`, и только потом в обработку.
    
- Это как **внутренний кэш PostgreSQL** (аналог page cache в ОС, но специфичный для базы).
    

### 📌 Как работает:

- Когда ты выполняешь `SELECT`, PostgreSQL сначала смотрит: «Есть ли нужная страница в shared_buffers?»
    
    - Если **есть** — читается из памяти (быстро).
        
    - Если **нет** — читается с диска и сохраняется в `shared_buffers` на будущее.
        

### 📌 Размер:

- Обычно настраивается на **25–40% от RAM**.
    
- Пример: на сервере с 16GB можно поставить `shared_buffers = 4GB`.
    

---

## 🔹 `work_mem` — **оперативная память на одну операцию**

### 📌 Что это:

- Объем памяти, который PostgreSQL выделяет **на каждую операцию сортировки, хэширования или объединения** (`JOIN`, `ORDER BY`, `DISTINCT` и т.д.).
    
- Выделяется **на каждую операцию** в каждом параллельном узле **в каждом запросе**.
    

### 📌 Что происходит при нехватке:

- Если операция **не влезает в `work_mem`**, PostgreSQL создаёт **временные файлы на диск** → сильно замедляет запрос.
    

### 📌 Пример:

```sql
SELECT DISTINCT name FROM users ORDER BY name;
```

- если список большой, сортировка может **уйти на диск**, если `work_mem` мал.
    

### 📌 Советы:

- Лучше начинать с ~`4MB–64MB` и профилировать запросы с `EXPLAIN (ANALYZE, BUFFERS)`.
    

---

## 🔹 `temp_buffers` — **буферы для временных таблиц**

### 📌 Что это:

- Количество памяти, выделенной **на каждое подключение** для хранения данных **во временных таблицах** (`CREATE TEMP TABLE`).
    
- Используется **только до тех пор, пока сессия активна**.
    

### 📌 Где важно:

- Если ты активно используешь временные таблицы для промежуточных результатов, агрегаций, ETL — увеличь `temp_buffers`.
    

---

## 🧠 Визуализация:

```
RAM
├── PostgreSQL
│   ├── shared_buffers      (общий кэш страниц для всех)
│   ├── work_mem            (операции: join, sort — для каждого запроса отдельно)
│   ├── temp_buffers        (временные таблицы на сессию)
│
└── OS page cache           (буферизация файловой системы, включая .data файлов БД)
```

---

## 🧪 Практические советы

|Параметр|Тип|Значение по умолчанию|Рекомендации для настройки|
|---|---|---|---|
|shared_buffers|глобальный|~128MB|25–40% от RAM|
|work_mem|на операцию|~4MB|увеличить до 16MB+ если много JOIN|
|temp_buffers|на сессию|~8MB|до 32MB+, если используешь TEMP|

---

## 📎 Хочешь протестировать?

```sql
SET work_mem = '128MB'; -- только для текущей сессии
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM large_table ORDER BY heavy_column;
```

Если при маленьком `work_mem` ты увидишь `Disk:` в плане — значит PostgreSQL использовал временные файлы, и стоит подумать об увеличении.
