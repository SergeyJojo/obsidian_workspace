
Давай разберем каждый вопрос по порядку:

### 1. Что делать в случае если у нас 500-ит сервис, как будем искать проблему?

**Ответ:** В случае с 500-ит ошибкой нужно сразу проверить несколько ключевых моментов:

- Логи: для диагностики проблем стоит смотреть логи на всех уровнях системы, начиная от сервера и заканчивая отдельными сервисами (если они есть).
- Мониторинг: важно следить за метриками (например, через Prometheus и Grafana), чтобы отслеживать нагрузку, пиковые значения, количество ошибок.
- Тайм-ауты и ограничения: проверьте, нет ли тайм-аутов, которые могут привести к срабатыванию 500 ошибки.
- Состояние базы данных: например, чрезмерная нагрузка на базу данных может вызывать ошибки сервиса.

### 2. Как узнать что с сервисом что-то не так, тормозит, как узнать где тормозит?

**Ответ:** Чтобы понять, где тормозит сервис:

- Логирование и метрики: с помощью логирования, мониторинга и трейсинга (например, через OpenTelemetry) можно отслеживать выполнение каждого запроса.
- Профилирование: в Go можно использовать встроенные профайлеры, такие как pprof для анализа CPU и памяти.
- Распределенные трассировки: для микросервисов это позволяет увидеть, где и на каком этапе происходит задержка.

### 3. Всегда ли в Go имеет смысл создавать горутины?

**Ответ:** Нет, не всегда. Горутины могут быть полезными для параллельной обработки задач, но их избыточное использование может привести к высокому расходу памяти и контекстным переключениям. Лучше создавать горутины только в случае явной необходимости — когда нужно параллельно обрабатывать независимые задачи или когда задача не блокирует другие процессы.

### 4. Как ты реализовал кеш в приложении? LRU, Redis, Memcache? Как понять, что кеш работает эффективно?

**Ответ:**

- **LRU**: это алгоритм, который используется для удаления наименее используемых элементов из кэша. Хорошо подходит для ограниченных объемов памяти.
- **Redis**: может быть использован для хранения кеша с возможностью использования разных структур данных. Например, Redis поддерживает LRU автоматически через свои настройки.
- **Memcache**: тоже популярный инструмент для кэширования. Подходит для простого кэширования данных с возможностью установки лимитов на размер и время жизни. Чтобы понять, что кеш работает эффективно, важно:
- Снизить количество запросов к базе данных.
- Измерять скорость ответов сервиса с кэшем и без.
- Следить за метками времени: кеш должен иметь ограничение по времени жизни данных (TTL).

### 5. Ты разработчик системы управления заказами, у тебя есть 2 api grpc. Система работает довольно давно и тебе необходимо добавить 2 поля (client_phone, updated_at), а также удалить поле (orderID). Как сделать?

**Ответ:**

1. **Обновление структуры данных**:
    
    - Добавить новые поля в структуру данных, определенную для grpc сообщений.
    - Добавить логику для нового поля `client_phone`, например, валидатор для номера телефона, чтобы он был корректным.
    - Обновить логику хранения и передачи данных в базе данных.
    - Для поля `updated_at` — можно добавить логику автоматического обновления времени последнего изменения записи.
    - Удалить поле `orderID` из структуры данных и обеспечить поддержку старых данных в миграциях.
2. **Миграции**:
    
    - Провести миграцию базы данных для добавления новых столбцов и удаления старого.
3. **API-гибкость**:
    
    - Поддержите старые версии API с использованием версии (например, v1, v2).
    - Для изменения полей при обслуживании старой версии API можно использовать дефолтные значения или оставить поле как устаревшее.

### 6. У тебя начал медленно работать запрос в бд, как будешь оптимизировать и как поймешь, что помогло?

**Ответ:**

- **Первоначальная диагностика**: проверить выполнение запроса с помощью EXPLAIN, чтобы понять, как SQL-движок выполняет запрос.
- **Индексация**: проанализировать таблицы на предмет недостающих индексов. Можно добавить индексы на поля, по которым идет поиск или сортировка.
- **Нормализация запросов**: если запрос слишком сложный или включает большое количество соединений, можно разбить его на несколько более простых.
- **Кэширование**: использовать кэш (например, Redis) для хранения часто запрашиваемых данных, чтобы снизить нагрузку на базу.
- **Репликация**: использование реплик для уменьшения нагрузки на основной сервер базы данных.
- **Миграция на более производительную СУБД или кластеризация**: если есть необходимость, можно перейти на более производительное решение.

### 7. Ответ, навешивай индексов без аргументации не считается.

**Ответ**: Индексация — это не панацея. Мы добавляем индексы только на те поля, по которым часто происходит поиск или сортировка. Но индексы могут замедлить операции вставки и обновления. Поэтому важно тщательно анализировать производительность до и после добавления индексов. Индексы следует использовать, но без избытка. Лучше применять их на основании анализа, например, через EXPLAIN в SQL.

### 8. Нужно спроектировать решение, которое будет фиксировать изменение сущности и отдавать diff.

**Ответ**: Это типичный случай использования **event sourcing**. Event sourcing предполагает, что вся информация о изменениях данных хранится в виде событий (events), а текущее состояние данных можно реконструировать, обрабатывая эти события.

- Преимущества: полная история изменений, возможность отката.
- Для реализации нужно:
    - Создавать событие каждый раз, когда происходит изменение сущности.
    - Хранить все события в базе данных или в специализированном хранилище (например, Kafka).
    - Для работы с такими данными можно использовать подходы, такие как CQRS (Command Query Responsibility Segregation).
