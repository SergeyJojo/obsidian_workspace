# 🧹 Памятка: Рефакторинг сервисов на Go

> **Цель рефакторинга**: улучшить структуру, читаемость, тестируемость и производительность **без изменения поведения**.

---

## 1. 🔍 Когда нужно рефакторить?

| Признак | Что делать |
|--------|------------|
| Функция длиннее 20 строк | Разбить на подфункции |
| Файл больше 300 строк | Разделить на несколько файлов |
| Пакет не проходит `golint` / `gosec` | Починить |
| Тесты не покрывают 80%+ | Добавить тесты перед рефакторингом |
| Код "пахнет" (code smell) | Выявить и устранить |
| Много `if err != nil` подряд | Использовать `errors.Is`, `errors.As`, вынести валидацию |
| Глобальные переменные | Инкапсулировать, внедрить через DI |
| Нет интерфейсов | Выделить и использовать для моков |

---

## 2. 🧱 Принципы рефакторинга

### ✅ Маленькие шаги
- Рефакторь **по одному шагу**, а не всё сразу.
- После каждого шага — **запусти тесты**.

### ✅ Тесты — твои страховочные тросы
- Перед рефакторингом — **напиши тесты**, если их нет.
- Запускай `go test -race` и `go test -cover`.

### ✅ Используй IDE (GoLand, VS Code)
- Автоматическое переименование, выделение функций, анализ зависимостей.

---

## 3. 🛠 Конкретные шаги рефакторинга

### 1. **Раздели на слои (Clean Architecture)**

Преврати монолит в:

```
handler → service → repository
```

| Было | Стало |
|------|--------|
| Логика в хендлере | Логика в `service` |
| Прямой SQL в `handler` | SQL в `repository` |
| Нет интерфейсов | `UserRepository interface{}` |

---

### 2. **Выдели интерфейсы**

Замени жёсткие зависимости:

```go
// Было
type UserService struct {
    db *sql.DB
}

// Стало
type UserRepository interface {
    GetUser(ctx context.Context, id int) (*User, error)
}

type UserService struct {
    repo UserRepository
}
```

> Теперь можно мокать `UserRepository` в тестах.

---

### 3. **Устрани "мокрые" функции (long functions)**

Разбей длинную функцию:

```go
func (s *OrderService) ProcessOrder(ctx context.Context, order *Order) error {
    // 1. Validate
    if err := s.validate(order); err != nil {
        return err
    }

    // 2. Reserve inventory
    if err := s.inventory.Reserve(ctx, order.Items); err != nil {
        return err
    }

    // 3. Charge payment
    if err := s.payment.Charge(ctx, order); err != nil {
        return err
    }

    // 4. Save order
    return s.repo.Create(ctx, order)
}
```

> Каждый шаг — отдельная приватная функция.

---

### 4. **Замени глобальные переменные**

| Было | Стало |
|------|--------|
| `var DB *sql.DB` | Передавай `*sql.DB` в конструктор |
| `var Logger = log.New(...)` | Внедряй логгер через `Logger interface{}` |

---

### 5. **Улучши обработку ошибок**

#### Было:
```go
if err != nil {
    log.Println("Error:", err)
    return err
}
```

#### Стало:
```go
if err != nil {
    return fmt.Errorf("failed to create user: %w", err)
}
```

> Используй `errors.Is()` и `errors.As()`:

```go
if errors.Is(err, ErrUserNotFound) { ... }
if errors.As(err, &validationError) { ... }
```

---

### 6. **Устрани дублирование (DRY)**

Если видишь одинаковый код в нескольких местах — вынеси в `pkg/utils` или отдельный пакет.

Пример:
```go
// Вместо
if err != nil { return nil, err }

// Используй
func handleError(err error) (*Response, error) { ... }
```

---

### 7. **Добавь контекст**

Убедись, что **все публичные методы принимают `context.Context`**:

```go
func (s *UserService) Get(ctx context.Context, id int) (*User, error)
```

> Это нужно для таймаутов, отмены, логирования.

---

### 8. **Упрости ветвление**

Избегай глубоких вложенностей:

```go
// Плохо
if err != nil {
    return err
} else {
    if user.Active {
        ...
    }
}

// Хорошо
if err != nil {
    return err
}
if !user.Active {
    return ErrUserInactive
}
```

---

### 9. **Используй `defer` правильно**

```go
tx, err := db.BeginTx(ctx, nil)
if err != nil {
    return err
}
defer tx.Rollback() // откат, если не сделаем Commit

// ... операции

return tx.Commit()
```

---

### 10. **Замени `map[string]interface{}` на структуры**

| Было | Стало |
|------|--------|
| `data := make(map[string]interface{})` | `type User struct{ ... }` |
| Нет типов, легко ошибиться | Типобезопасность, автодополнение |

## 4. 🧪 Тесты: как рефакторить безопасно

### Перед рефакторингом:
1. Напиши **юнит-тесты** на текущее поведение
2. Запусти **интеграционные тесты**
3. Убедись, что `go test ./...` проходит

### После каждого шага:
- Запускай тесты
- Проверяй покрытие: `go test -cover`

## 6. 🧩 Пример: рефакторинг хендлера

### Было:
```go
func handler(w http.ResponseWriter, r *http.Request) {
    var user User
    json.NewDecoder(r.Body).Decode(&user)

    db, _ := sql.Open("postgres", "...")
    _, err := db.Exec("INSERT INTO users ...")
    if err != nil {
        log.Println(err)
        return
    }

    w.Write([]byte("OK"))
}
```

### Стало:
```go
type UserHandler struct {
    service UserService
}

func (h *UserHandler) CreateUser(w http.ResponseWriter, r *http.Request) {
    var input CreateUserRequest
    if err := json.NewDecoder(r.Body).Decode(&input); err != nil {
        http.Error(w, "Invalid JSON", http.StatusBadRequest)
        return
    }

    if err := h.service.Create(r.Context(), input); err != nil {
        handleError(w, err)
        return
    }

    w.WriteHeader(http.StatusCreated)
    json.NewEncoder(w).Encode("OK")
}
```

## 7. ✅ Чек-лист: код готов к продакшену?

| Пункт | Готово? |
|------|--------|
| Есть модули (`go.mod`) | ✅ |
| Нет глобальных переменных | ✅ |
| Все ошибки обрабатываются | ✅ |
| Есть `context.Context` везде | ✅ |
| Есть интерфейсы для репозиториев | ✅ |
| Есть юнит- и интеграционные тесты | ✅ |
| Проходит `golint`, `gosec` | ✅ |
| Есть graceful shutdown | ✅ |
| Есть `/health` endpoint | ✅ |
| Нет `if err != nil { log.Fatal }` | ✅ |

## 8. 💡 Когда остановиться?

Рефакторинг — процесс, а не цель. Остановись, когда:

- Код **понятен новому разработчику**
- **Тесты проходят**
- **Поведение не изменилось**
- **Нет срочных задач**

> Не доводи до "идеала" — лучше **хороший код в продакшене**, чем "идеальный" в ветке.
