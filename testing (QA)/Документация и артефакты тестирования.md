### **Документация и артефакты тестирования, которые должен знать тестировщик**  

Тестировщик (QA) работает не только с кодом и багами, но и с **документацией**. Вот что нужно знать о ключевых артефактах: тест-кейсах, баг-репортах, чек-листах и других.  

---

## **1. Тест-кейсы (Test Cases)**  
**Что это?**  
Пошаговые инструкции для проверки функционала.  

**Зачем нужны?**  
- Систематизируют процесс тестирования.  
- Позволяют воспроизвести проверку.  
- Упрощают обучение новых тестировщиков.  

### **Структура тест-кейса**  
| Поле                 | Пример заполнения                                                                 |
|-----------------------|----------------------------------------------------------------------------------|
| **ID**               | `TC-101`                                                                        |
| **Название**         | Проверка входа в систему с валидными данными                                    |
| **Предусловия**      | Пользователь зарегистрирован, сервер доступен                                   |
| **Шаги**            | 1. Открыть страницу входа.<br>2. Ввести логин: `test@example.com`.<br>3. Ввести пароль: `Qwerty123`.<br>4. Нажать "Войти". |
| **Ожидаемый результат** | Пользователь авторизован, открывается главная страница.                       |
| **Фактический результат** | *(Заполняется при выполнении)*                                               |
| **Статус**          | `Passed` / `Failed` / `Blocked`                                                |
| **Приоритет**       | `High` / `Medium` / `Low`                                                      |

**Пример тест-кейса**:  
```markdown
**TC-102**: Проверка входа с неверным паролем  
**Шаги**:  
1. Ввести логин: `test@example.com`.  
2. Ввести пароль: `WrongPass123`.  
3. Нажать "Войти".  
**Ожидаемо**: Сообщение "Неверный пароль".  
```

**Где хранить?**  
- **TestRail**  
- **Qase**  
- **Excel/Google Sheets** (для небольших проектов).

## **2. Баг-репорты (Bug Reports)**  
**Что это?**  
Документ, описывающий найденный дефект.  

**Зачем нужны?**  
- Чтобы разработчик понял, как воспроизвести баг.  
- Для отслеживания статуса исправления.  

### **Структура баг-репорта**  
| Поле                  | Пример                                                                 |
|-----------------------|-----------------------------------------------------------------------|
| **Название**         | `[Login Page] Ошибка 500 при вводе email без "@"`                    |
| **Шаги воспроизведения** | 1. Открыть страницу входа.<br>2. Ввести `testexample.com`.<br>3. Нажать "Войти". |
| **Ожидаемый результат** | Сообщение "Некорректный email".                                    |
| **Фактический результат** | Ошибка сервера 500.                                               |
| **Среда**            | `Chrome 120, Windows 11`                                             |
| **Приоритет**        | `Critical` / `Major` / `Minor` / `Trivial`                           |
| **Скриншот/лог**     | `[Прикреплен screenshot_500_error.png]`                              |

**Пример (Jira/YouTrack)**:  
```markdown
**Summary**: [Checkout] Payment fails with empty card number  
**Steps to Reproduce**:  
1. Go to checkout page.  
2. Leave "Card Number" field empty.  
3. Click "Pay".  
**Expected**: Validation error "Please enter card number".  
**Actual**: Payment processed, order created with status "Paid".  
**Priority**: Critical  
**Attachment**: [screen.png]  
```

**Что делает баг-репорт хорошим?**  
✅ **Четкие шаги** (как воспроизвести).  
✅ **Ожидаемый vs фактический** результат.  
✅ **Контекст**: ОС, браузер, версия приложения.  
✅ **Скриншоты/логи** (если есть).

## **3. Чек-листы (Checklists)**  
**Что это?**  
Список пунктов для проверки **без детальных шагов** (в отличие от тест-кейсов).  

**Зачем нужны?**  
- Быстрая проверка критичного функционала.  
- Удобны для регрессионного тестирования.  

**Пример чек-листа для формы регистрации**:  
```markdown
- [ ] Валидный email → успешная регистрация.  
- [ ] Email без "@" → ошибка валидации.  
- [ ] Пароль < 8 символов → ошибка.  
- [ ] Повтор пароля не совпадает → ошибка.  
- [ ] Кнопка "Зарегистрироваться" неактивна, пока все поля не заполнены.  
```

**Плюсы**:  
✔ Гибкость (можно быстро добавить пункт).  
✔ Экономия времени (не нужно писать шаги).  

**Минусы**:  
❌ Нет деталей (новичок может не понять, как проверить).

## **4. Тест-план (Test Plan)**  
**Что это?**  
Документ, описывающий **стратегию тестирования** проекта.  

**Что включает?**  
- Цели и объем тестирования.  
- Распределение ресурсов (кто и что тестирует).  
- График тестирования.  
- Критерии начала/окончания тестов.  

**Пример структуры**:  
```markdown
1. Введение  
   - Цель: Проверить функционал оплаты.  
2. Объем тестирования  
   - Что тестируем: API оплаты, UI формы.  
   - Что не тестируем: Интеграцию с банком (тестирует банк).  
3. Подход  
   - Ручное тестирование: Smoke-тесты.  
   - Автоматизация: API-тесты (Postman).  
4. Критерии качества  
   - Все критические баги исправлены.  
5. Риски  
   - Нехватка времени на нагрузочное тестирование.  
```

## **5. Отчет о тестировании (Test Summary Report)**  
**Что это?**  
Итоговый документ после завершения тестирования.  

**Что включает?**  
- Сколько тест-кейсов выполнено/провалено.  
- Критические баги (если есть).  
- Рекомендации: можно ли выпускать продукт?  

**Пример**:  
```markdown
**Статистика**:  
- Всего тест-кейсов: 150  
- Passed: 140  
- Failed: 10 (из них 2 критических).  

**Вывод**:  
- Критические баги исправлены.  
- Рекомендуется выпустить версию 1.0.  
```

## **6. Mind Maps (для тест-дизайна)**  
**Что это?**  
Визуальная схема для генерации тестовых сценариев.  

**Пример**:  
```
Форма регистрации  
├── Валидные данные → Успешная регистрация  
├── Невалидные данные  
│   ├── Email без "@" → Ошибка  
│   ├── Пароль < 8 символов → Ошибка  
└── Граничные значения  
    ├── Пароль ровно 8 символов → Успех  
    ├── Email 255 символов → Успех  
```

**Инструменты**:  
- XMind  
- Miro  
- MindMeister

## **7. Traceability Matrix**  
**Что это?**  
Таблица, связывающая **требования** с **тест-кейсами**.  

**Зачем?**  
- Чтобы убедиться, что все требования покрыты тестами.  
- Для аудита (например, по ISO 9001).  

**Пример**:  
| ID требования | Описание                | ID тест-кейса | Статус     |  
|---------------|-------------------------|---------------|------------|  
| REQ-101       | Пользователь может войти | TC-101        | Passed     |  
| REQ-102       | Пароль должен быть ≥ 8 символов | TC-102 | Failed    |

## **8. Best Practices**  
1. **Тест-кейсы**:  
   - Пишите так, чтобы их мог выполнить даже новичок.  
   - Добавляйте предварительные условия (например, "Пользователь должен быть зарегистрирован").  

2. **Баг-репорты**:  
   - Всегда указывайте **шаги воспроизведения**.  
   - Прикрепляйте **скриншоты/видео**.  

3. **Чек-листы**:  
   - Используйте для регресса и smoke-тестов.  

4. **Тест-план**:  
   - Согласуйте с командой перед началом тестирования.

- **Тест-кейсы** — детальные инструкции.

- **Тест-план** — стратегия тестирования.
