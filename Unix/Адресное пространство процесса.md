

Да, у каждого процесса в Linux есть стек, и он играет ключевую роль в его работе. Давай разберём, как устроен стек, как он используется, очищается, и на какие ещё области делится адресное пространство процесса в Linux. Я объясню это "диким разбором", чтобы ты понял всё как "владелец вселенной памяти"!

---

Что такое стек процесса?

- Стек (Stack): Это область памяти в виртуальном адресном пространстве процесса, которая используется для хранения временных данных, таких как локальные переменные, аргументы функций и информация о вызовах функций.
    
- Где живёт: В структуре task_struct есть поле stack, указывающее на начальный адрес стека.
    
- Кто создаёт: Ядро выделяет стек при создании процесса (fork) или потока (clone).
    

Характеристики стека:

- LIFO (Last In, First Out): Данные добавляются (push) и убираются (pop) с вершины.
    
- Растёт вниз: На большинстве архитектур (x86, x86_64) стек начинается с высокого адреса и растёт к меньшим адресам.
    
- Размер: Ограничен (по умолчанию ~8 МБ в Linux, настраивается через ulimit -s).
    

---

Как используется стек?

Стек нужен для выполнения программы, особенно при работе с функциями.

1. Хранение локальных переменных

- Когда ты вызываешь функцию, её локальные переменные "кладутся" на стек.
    
- Пример:
    
    c
    
    ```c
    void func(int x) {
        int y = 10;
    }
    ```
    
    - x и y занимают место на стеке.
        

2. Управление вызовами функций

- Стек вызовов (Call Stack): При вызове функции на стек кладётся:
    
    - Адрес возврата: Куда вернуться после завершения функции.
        
    - Аргументы: Передаваемые параметры.
        
    - Сохранённые регистры: Например, значение регистра rbp (указатель базы).
        
- Пример:
    
    c
    
    ```c
    void b() { int z = 5; }
    void a() { b(); }
    main() { a(); }
    ```
    
    - Вызов main → a → b:
        
        1. main кладёт на стек свои данные.
            
        2. a добавляет свои (адрес возврата в main).
            
        3. b добавляет свои (адрес возврата в a).
            

3. Передача управления

- Процессор использует регистр rsp (stack pointer), чтобы отслеживать вершину стека.
    
- При вызове функции (call) rsp уменьшается, при возврате (ret) — увеличивается.
    

---

Как очищается стек?

- Автоматически: Стек не "очищается" вручную — он самоуправляемый.
    
- Механизм:
    
    - Когда функция завершает работу, её "фрейм" (stack frame) снимается со стека:
        
        - rsp возвращается на предыдущий уровень.
            
        - Локальные переменные "исчезают" (память освобождается для переиспользования).
            
- Пример:
    
    - b() завершает работу → rsp сдвигается вверх → место под z освобождается.
        
    - Нет явного "удаления" данных — они просто перестают быть доступными.
        
- Полное очищение: Когда процесс завершает работу (exit), ядро освобождает всё его адресное пространство, включая стек.

На какие области делится адресное пространство процесса?

В Linux виртуальное адресное пространство процесса делится на несколько сегментов. На 64-битной системе оно огромно (2^64 байт, но используется только часть из-за ограничений архитектуры, например, 48 бит).

1. Текст (Text Segment)

- Что это: Код программы (машинные инструкции).
    
- Где: Низкие адреса (например, 0x400000 на x86_64).
    
- Кто создаёт: Ядро при загрузке исполняемого файла (exec).
    
- Зачем: Хранит исполняемый код, только для чтения.
    

2. Данные (Data Segment)

- Подсегменты:
    
    - Инициализированные данные (Initialized Data): Глобальные переменные с начальным значением.
        
        - Пример: int x = 10;.
            
    - Неинициализированные данные (BSS): Глобальные переменные без значения (заполняются нулями).
        
        - Пример: int y;.
            
- Где: Выше текста.
    
- Зачем: Постоянные данные программы.
    

3. Куча (Heap)

- Что это: Динамически выделяемая память.
    
- Где: Растёт вверх от конца данных.
    
- Кто управляет: Библиотека (malloc в glibc) через brk или mmap.
    
- Зачем: Для массивов, структур и других объектов, выделяемых в runtime.
    
- Пример: malloc(1024) → куча увеличивается.
    

4. Стек (Stack)

- Что это: Описан выше — для локальных переменных и вызовов.
    
- Где: Высокие адреса (например, 0x7fffffffe000), растёт вниз.
    
- Зачем: Управление выполнением функций.
    

5. Сегменты памяти, выделенные через mmap (Memory-Mapped Segments)

- Что это: Области для библиотек, файлов или анонимной памяти.
    
- Где: Между кучей и стеком.
    
- Пример:
    
    - Динамические библиотеки (libc.so).
        
    - mmap для больших буферов.
        
- Зачем: Гибкое выделение памяти.
    

6. Область ядра (Kernel Space)

- Что это: Верхняя часть адресного пространства, недоступная процессу напрямую.
    
- Где: Например, от 0xffff800000000000 до 0xffffffffffffffff (x86_64).
    
- Зачем: Для системных вызовов, таблиц страниц, кода ядра.
    

---

Пример адресного пространства (x86_64)

```text
0xffffffffffffffff +--------------------------+
                   |        Kernel Space      | ← Самый верх
0xffff800000000000 +--------------------------+
                   |     (не используется)    |
0x7fffffffffff     +--------------------------+
                   |         Stack            |
                   | - растёт вниз (LIFO)     |
                   | - локальные переменные   |
                   | - адреса вызова          |
                   | - rsp сдвигается вверх   |
0x7fffffffe000     +--------------------------+
                   |       mmap области       |
                   | - libc, so-файлы         |
                   | - буферы, анонимные map  |
0x00007f0000000000 +--------------------------+
                   |          Heap            |
                   | - malloc/new             |
                   | - растёт вверх           |
                   | - управляется brk/sbrk   |
0x0000000000600000 +--------------------------+
                   |    Data и BSS сегменты   |
                   | - глобальные переменные  |
                   | - инициализированные/нет |
0x0000000000400000 +--------------------------+
                   |         Text             |
                   | - код программы          |
                   | - const строки, функции  |
0x0000000000000000 +--------------------------+ ← Низ адресов


```

Как это работает на практике?

1. Ты запускаешь программу:
    
    - Ядро через exec загружает текст и данные.
        
    - Выделяет стек (например, 8 МБ).
        
    - Куча пуста, пока не вызовешь malloc.
        
2. Вызов функции:
    
    c
    
    ```c
    void main() {
        int x = 5; // На стеке
        char* buf = malloc(1024); // На куче
    }
    ```
    
    - x занимает 4 байта на стеке, rsp уменьшается.
        
    - buf — указатель на кучу, выделенную через brk или mmap.
        
3. Завершение:
    
    - Функция выходит → стек "очищается" (указатель rsp сдвигается).
        
    - Процесс завершается → ядро освобождает всё.
        

---

Подводные камни

1. Переполнение стека (Stack Overflow):
    
    - Слишком глубокая рекурсия → стек упирается в кучу → SIGSEGV.
        
    - Решение: Увеличить лимит (ulimit -s).
        
2. Фрагментация кучи:
    
    - Частые malloc/free → "дыры" в памяти.
        
3. Коллизия кучи и стека:
    
    - Если куча растёт слишком быстро, может "столкнуться" со стеком.
        

---

Шпаргалка "на стену"

```text
Стек:
- Растёт вниз, LIFO
- Локальные переменные, вызовы
- Очищается: rsp сдвигается вверх

Адресное пространство:
- Текст: Код (0x400000)
- Данные: Глобальные (выше текста)
- Куча: Динамическая, растёт вверх
- mmap: Библиотеки, буферы
- Стек: Высокие адреса, вниз
- Ядро: Самый верх
```

Итог

Стек — это динамическая рабочая зона процесса для функций и локальных данных, растущая вниз и самоочищающаяся при выходе из функций. Адресное пространство делится на текст, данные, кучу, стек и ядро, каждая область со своей ролью. Если хочешь углубиться (например, как читать /proc/[pid]/maps), дай знать! Что дальше?

Структуры в линукс. Процессов, потоков, файлов, сетевых соединений 

В Linux процессы, потоки, сетевые соединения и файлы управляются через структуры данных в ядре, которые содержат всю необходимую информацию для их работы. 1. struct task_struct — Структура процесса и потока

- Что это: Описывает процесс или поток (в Linux потоки — это "лёгкие процессы", различаются только степенью разделения ресурсов).
    
- Где живёт: <linux/sched.h>.
    
- Кто создаёт: Ядро через fork() (процесс) или clone() (поток).
    

Основные поля task_struct

c

```c
struct task_struct {
    // Состояние процесса
    volatile long state;          // TASK_RUNNING, TASK_INTERRUPTIBLE и т.д.
    int exit_state;               // EXIT_ZOMBIE, EXIT_DEAD (для завершения)

    // Идентификаторы
    pid_t pid;                    // PID процесса (например, 1234)
    pid_t tgid;                   // Thread Group ID (PID лидера группы потоков)
    struct task_struct *parent;   // Указатель на родительский процесс
    struct list_head children;    // Список дочерних процессов
    struct list_head sibling;     // Список братьев/сестёр в группе

    // Память
    struct mm_struct *mm;         // Виртуальная память процесса
    struct mm_struct *active_mm;  // Активное адресное пространство (для потоков)
    void *stack;                  // Указатель на стек

    // Файлы
    struct files_struct *files;   // Таблица открытых файлов

    // Планировщик
    int prio;                     // Приоритет процесса
    struct sched_entity se;       // Данные для планировщика (CFS)
    struct task_struct *group_leader; // Лидер группы потоков

    // Сигналы
    struct signal_struct *signal; // Обработка сигналов
    sigset_t blocked;             // Заблокированные сигналы

    // Ресурсы
    struct rlimit rlim[RLIM_NLIMITS]; // Лимиты (например, размер стека)
    cputime_t utime, stime;       // Время CPU (пользовательское и системное)
};
```

- Процесс vs Поток:
    
    - Процесс: Имеет собственный mm (память).
        
    - Поток: Делит mm с другими потоками группы (tgid), но имеет свой stack.
        

Зачем: Хранит всё о процессе/потоке: состояние, память, файлы, приоритет.

2. struct file — Структура открытого файла

- Что это: Представляет открытый файл в контексте процесса.
    
- Где живёт: <linux/fs.h>.
    
- Кто создаёт: Ядро через open().
    

Основные поля struct file

c

```c
struct file {
    struct path f_path;           // Путь к файлу (dentry + vfsmount)
    struct inode *f_inode;        // Указатель на inode файла
    const struct file_operations *f_op; // Операции (read, write, ioctl)
    loff_t f_pos;                 // Текущая позиция в файле (offset)
    unsigned int f_flags;         // Флаги (O_RDONLY, O_APPEND)
    atomic_t f_count;             // Счётчик ссылок (для close)
    void *private_data;           // Данные драйвера/файловой системы
    struct list_head f_list;      // Связь с другими файлами процесса
};
```

- Как работает: Связывает процесс с файлом на диске или устройстве через inode и операции f_op.
    

Зачем: Управляет доступом к файлу, отслеживает позицию и операции.

---

3. struct files_struct — Таблица открытых файлов процесса

- Что это: Хранит все открытые файлы процесса.
    
- Где живёт: <linux/fdtable.h>.
    
- Кто создаёт: Ядро при создании процесса.
    

Основные поля struct files_struct

c

```c
struct files_struct {
    atomic_t count;               // Счётчик ссылок (для потоков)
    struct fdtable *fdt;          // Указатель на таблицу дескрипторов
    struct file __rcu *fd_array[NR_OPEN_DEFAULT]; // Массив указателей на struct file
};
```

- Связь: task_struct->files указывает сюда.
    
- Пример: FD 3 → fd_array[3] → struct file для /etc/passwd.
    

Зачем: Обеспечивает доступ процесса к файлам через файловые дескрипторы (FD).

---

4. struct inode — Метаданные файла

- Что это: Описывает файл на уровне файловой системы (не путать с struct file).
    
- Где живёт: <linux/fs.h>.
    
- Кто создаёт: Файловая система (например, ext4) при доступе к файлу.
    

Основные поля struct inode

c

```c
struct inode {
    umode_t i_mode;               // Тип и права (файл, директория, S_IRWXU)
    unsigned long i_ino;          // Номер инода
    struct timespec i_atime;      // Время последнего доступа
    struct timespec i_mtime;      // Время модификации
    struct timespec i_ctime;      // Время изменения метаданных
    loff_t i_size;                // Размер файла
    struct super_block *i_sb;     // Указатель на суперблок ФС
    const struct inode_operations *i_op; // Операции с inode
};
```

- Связь: struct file->f_inode указывает сюда.
    

Зачем: Хранит метаданные файла (размер, права), независимо от того, открыт он или нет.

5. Структуры сетевых соединений

Сетевые соединения в Linux управляются через структуры, связанные с сокетами.

struct socket

- Что это: Высокоуровневая абстракция сокета в ядре.
    
- Где живёт: <linux/net.h>.
    
- Кто создаёт: Ядро через socket().
    

Основные поля struct socket

c

```c
struct socket {
    socket_state state;           // SS_CONNECTED, SS_DISCONNECTED
    short type;                   // SOCK_STREAM (TCP), SOCK_DGRAM (UDP)
    struct file *file;            // Связь с файловым дескриптором
    struct sock *sk;              // Указатель на низкоуровневый сокет
    const struct proto_ops *ops;  // Операции (send, recv, bind)
};
```

- Связь: Создаётся для каждого сокета, привязан к struct file.
    

---

struct sock

- Что это: Низкоуровневая структура для сетевых протоколов (TCP, UDP).
    
- Где живёт: <net/sock.h>.
    
- Кто создаёт: Ядро при установке соединения.
    

Основные поля struct sock

c

```c
struct sock {
    struct socket *sk_socket;     // Обратная связь с socket
    __be32 sk_daddr;              // IP-адрес назначения
    __be32 sk_rcv_saddr;          // IP-адрес источника
    __be16 sk_dport;              // Порт назначения
    unsigned short sk_num;        // Локальный порт
    int sk_state;                 // Состояние (TCP_ESTABLISHED, TCP_CLOSE)
    struct sk_buff_head sk_receive_queue; // Очередь входящих пакетов
    struct proto *sk_prot;        // Протокол (tcp_prot, udp_prot)
};
```

- Пример: Для TCP-соединения хранит IP, порты, состояние (SYN_SENT, ESTABLISHED).
    

Зачем: socket — интерфейс для процесса, sock — реализация протокола.

---

Как всё связано?

1. Процесс (task_struct):
    
    - Создаётся через fork/clone.
        
    - Имеет files → files_struct для файлов и сокетов.
        
2. Файл (struct file):
    
    - Создаётся через open.
        
    - Ссылается на inode (файл на диске) или socket (сеть).
        
3. Сеть (struct socket, struct sock):
    
    - Создаётся через socket().
        
    - socket привязан к file, sock управляет соединением.
        
4. Метаданные (struct inode):
    
    - Создаётся файловой системой для каждого файла.
        

Пример:

- Ты открываешь файл и сокет в Go:
    
    go
    
    ```go
    f, _ := os.Open("/etc/passwd")
    conn, _ := net.Dial("tcp", "google.com:80")
    ```
    
    - task_struct->files->fd_array[3] → struct file → inode для /etc/passwd.
        
    - task_struct->files->fd_array[4] → struct file → socket → sock для TCP-соединения.
