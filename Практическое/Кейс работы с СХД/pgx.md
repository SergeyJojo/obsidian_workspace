
Отличный запрос! Вот подборка реально встречающихся **нетривиальных багов, подводных камней и необычных кейсов** при работе с [pgx](https://github.com/jackc/pgx) (Go driver для PostgreSQL), с фокусом на мелкие детали, ловушки и решения:

---

## 1. **"Connection leak" из-за не закрытых Rows**

### Баг:
- После запроса не вызывается `rows.Close()`, даже если прочитаны все результаты.
- В результате пул соединений быстро забивается "мертвыми" соединениями, новые запросы тупят или падают с ошибкой “no connections available”.

**Деталь:**  
- Всегда делайте `defer rows.Close()` сразу после проверки ошибки!
- Даже если сделали `for rows.Next()`, все равно нужен `rows.Close()` — иначе connection останется занят.

---

## 2. **Потеря ошибок при Scan**

### Баг:
- Ошибка возникает при `rows.Scan(...)`, но цикл перебора продолжается (`for rows.Next()`), ошибка теряется.
- Например, одна из колонок не мапится по типу — ошибка есть, но если не проверить `rows.Err()` после цикла, вы это пропустите.

**Деталь:**  
- После любого цикла по rows всегда делайте:
  ```go
  if err := rows.Err(); err != nil {
      // handle error
  }
  ```

---

## 3. **"Unexpected EOF" при работе с context**

### Баг:
- Запросы делаются с контекстом с коротким таймаутом или отменённым context.
- В логах появляется “unexpected EOF” или странные ошибки сети.

**Деталь:**  
- Всегда проверяйте, не истёк ли context ДО самого запроса.
- В случае таймаута — pgx может вернуть низкоуровневую ошибку, в которой сложно узнать, что случилось (особенно, если её не обернули через errors.Wrap).

---

## 4. **Потеря транзакций из-за panic**

### Баг:
- Внутри транзакции происходит panic, но `tx.Rollback()` не вызывается явно.
- В пуле остаётся "мертвая" транзакция, которая может блокировать другие операции.

**Нетривиальное решение:**  
- Используйте обёртку, которая всегда вызывает Rollback, если Commit не был успешен:
  ```go
  func doTx(ctx context.Context, db *pgxpool.Pool, fn func(tx pgx.Tx) error) (err error) {
      tx, err := db.Begin(ctx)
      if err != nil { return err }
      defer func() {
          if p := recover(); p != nil || err != nil {
              tx.Rollback(ctx)
          }
      }()
      err = fn(tx)
      if err == nil {
          err = tx.Commit(ctx)
      }
      return err
  }
  ```

---

## 5. **Типизация: sql.NullXXX vs. pgtype**

### Баг:
- Используете `sql.NullString` или `sql.NullInt64` для работы с nullable-значениями, но в pgx они не поддерживаются напрямую.
- В результате значения неправильно читаются/записываются, появляются nil или дефолтные значения.

**Деталь:**  
- Для pgx используйте типы из пакета `github.com/jackc/pgtype` (например, `pgtype.Text`, `pgtype.Int4`).
- Или пишите сканы руками через pointer-значения.

---

## 6. **Проблемы с batch-запросами**

### Баг:
- Запускаете Batch запросы (Batch, BatchResults), но не читаете ВСЕ результаты (`BatchResults.Query()`).
- Если не вычитать все — соединение в пуле “залипает” и может использоваться некорректно в будущем.

**Деталь:**  
- Всегда полностью вычитывайте batch-результаты (даже если некоторые не нужны).

---

## 7. **Проблемы с пулом соединений и MaxConnLifetime**

### Баг:
- В облаке (например, AWS RDS, Yandex Cloud) соединения могут внезапно дропаться, если пул держит их слишком долго.
- По дефолту соединения могут жить очень долго, пока PostgreSQL их не убьёт по своим internal policy.

**Деталь:**  
- Настраивайте MaxConnLifetime (например, 5 минут), чтобы пул сам обновлял соединения, и вы не ловили “broken pipe” в неожиданный момент.

---

## 8. **Атомарные операции через RETURNING**

### Необычный кейс:
- Нужно получить результат вставки/обновления сразу, не делать два запроса (например, id только что вставленной строки).

**Решение:**  
- Используйте `RETURNING` прямо в SQL:
  ```go
  var id int
  err := db.QueryRow(ctx, `INSERT INTO table (foo) VALUES ($1) RETURNING id`, foo).Scan(&id)
  ```

---

## 9. **Проблемы с массивами и кастомными типами**

### Баг:
- Передаёте массив Go (например, []int) напрямую в запрос, но pgx не всегда умеет их конвертировать в PostgreSQL-массив (`int[]`, `text[]`).

**Деталь и решение:**  
- Используйте `pgtype` или кастомные сериализаторы для массивов.
- Для простых случаев:  
  ```go
  db.Query(ctx, "SELECT * FROM table WHERE id = ANY($1)", pgx.Array([]int{1,2,3}))
  ```

---

## 10. **Параллелизм и sharing одного соединения**

### Баг:
- Несколько goroutine используют один и тот же connection/Tx — pgx не потокобезопасен!  
- В результате: data race, паника, непредсказуемое поведение.

**Деталь:**  
- Один connection или Tx — только для одного потока (goroutine) за раз.
- Если нужно параллелить — берите отдельные соединения из пула.

---

## 11. **Работа с COPY**

### Кейс:
- Используете bulk-insert через COPY, но не вызываете `CopyFrom` корректно, не читаете все ошибки.

**Деталь:**  
- Проверяйте ошибки после каждой операции с CopyFrom.
- Для больших batch-ов следите за размером batch-а, чтобы не словить OOM.

---

## 12. **Миграции и schema drift**

### Баг:
- Приложение ожидает одно поле/тип, а в БД оно изменилось (например, изменили тип поля), и pgx начинает ругаться на Scan.

**Деталь:**  
- Для миграций используйте автоматизированные инструменты (golang-migrate, goose), не допускайте “ручных” изменений схемы.

---

## 13. **Работа с JSONB**

### Баг:
- Передаёте структуру как map/struct в JSONB напрямую — но pgx требует []byte или string.

**Деталь:**  
- Marshal вручную:
  ```go
  b, _ := json.Marshal(myStruct)
  db.Exec(ctx, "INSERT INTO t (data) VALUES ($1)", b)
  ```
- Или используйте pgtype.JSONB (и его Scan/Value).

---

## 14. **Проблемы с prepared statements**

### Баг:
- Используете предварительно подготовленные запросы (`Prepare`), а потом меняете структуру таблицы (например, добавили/удалили колонку).
- Старый prepared statement становится невалидным, а pgx не всегда пересоздаёт его автоматически.

**Деталь:**  
- После миграций таблицы лучше пересоздать пул или хотя бы prepared statements.

---

## 15. **Пропущенные context timeout/cancel**

### Баг:
- Не задаёте контекст с таймаутом — запросы могут “висеть” вечно при сетевых проблемах или блокировках в БД.

**Решение:**  
- Всегда используйте context с явным timeout или deadline:
  ```go
  ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
  defer cancel()
  ```

---

## 16. **Проблемы с time.Time и часовыми поясами**

### Баг:
- В БД поле timezone-agnostic (timestamp without time zone), а в Go — time.Time с таймзоной. Результат — неожиданные сдвиги времени.

**Деталь:**  
- Следите за типами времени, используйте timestamp with time zone, если нужна корректная работа с часовыми поясами.

---

## 17. **"Too many connections" из-за долгих запросов**

### Баг:
- Долгие запросы занимают все соединения пула, новые запросы ждут или падают.

**Деталь:**  
- Оценивайте размер пула и лимиты в PostgreSQL (`max_connections`).
- Логируйте и профилируйте медленные запросы!

---

## 18. **Проблемы с IN ($1) и пустыми срезами**

### Баг:
- Пишете `WHERE id IN ($1)` и передаёте пустой срез — запрос падает с ошибкой о синтаксисе.

**Решение:**  
- Обрабатывайте пустой срез отдельно (например, добавляйте `WHERE false` или не делайте запрос совсем).

---

## 19. **"Silent" потери данных при Batch Insert**

### Баг:
- В batch insert с ON CONFLICT DO NOTHING silently теряются строки, но приложение не узнаёт об этом.

**Деталь:**  
- Используйте `RETURNING` чтобы получить реально вставленные id, или проверяйте affected rows.

---

## 20. **Ошибка с ENUM-типами**

### Баг:
- В БД — ENUM, а в Go — string/int.  
- При несовпадении значений — ошибка типа, иногда неявная (panic, ошибка Scan).

**Деталь:**  
- Обеспечьте строгий маппинг и обработку ошибок для ENUM.
