---

## 💥 **Кейс: Index Scan выбирается, но тормозит — почему?**

### ❓ Проблема

Ты смотришь на `EXPLAIN`, видишь `Index Scan`, и думаешь: «Отлично! Быстро, эффективно». Но при `EXPLAIN ANALYZE` оказывается, что:

- запрос выполняется **медленно**,
    
- читается **десятки тысяч страниц**,
    
- планировщик всё равно **не выбирает seq scan**.
    

---

## 1. **Что такое "селективность" в PostgreSQL**

**Селективность** — это оценка, сколько строк будет возвращено из таблицы по условию запроса.

Примеры:

- `WHERE id = 123` — высокая селективность (одна строка);
    
- `WHERE status = 'active'` — может быть низкой (если половина записей с таким статусом).
    

**Planner (оптимизатор)** использует _статистику_ колонок, чтобы решить, что быстрее: `Index Scan` или `Seq Scan`.

---

## 2. **Когда Index Scan работает плохо**

### ❗ Причина: плохая селективность + высокий cost random I/O

Представим таблицу:

```sql
CREATE TABLE events (
  id SERIAL PRIMARY KEY,
  user_id INTEGER,
  event_type TEXT,
  created_at TIMESTAMP
);

CREATE INDEX idx_event_type ON events(event_type);
```

Запрос:

```sql
SELECT * FROM events WHERE event_type = 'click';
```

Если `event_type = 'click'` встречается в **50% записей**, и их много (миллионы), то:

- `Index Scan` найдёт все `TID` (tuple ids) по индексу,
    
- а потом будет делать **random I/O**, вытаскивая **физические строки** из таблицы.
    

👉 На SSD это терпимо, на HDD — **катастрофа**: тысячи страниц читаются несбалансированно.

---

## 3. **Почему планировщик всё равно выбирает Index Scan?**

- Он **недооценивает cost random_page_access** или **не знает** реальной селективности.
    
- В статистике колонок PostgreSQL хранит только **N most common values** и гистограммы.
    
- Для `event_type`, если "click" — не самый часто встречающийся, то оценка будет неверной.
    

---

## 🔍 Пример с реальной `EXPLAIN (ANALYZE, BUFFERS)`

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM events WHERE event_type = 'click';
```

Результат:

```
Index Scan using idx_event_type on events
  Index Cond: (event_type = 'click')
  Buffers: shared hit=10500
  Rows Removed by Index Recheck: 0
  Rows=1,000,000
  Time: 1500 ms
```

- 10,500 буферов = 10,500 * 8KB ≈ **80MB random access**
    
- Из-за того, что каждый tuple поднимается с диска — **медленно**
    

---

## ✅ Решения

### 🔧 1. **Принудительно использовать Seq Scan**

Иногда `Seq Scan` быстрее. Можно подсказать Postgres:

```sql
SET enable_indexscan = OFF;
EXPLAIN ANALYZE ...
```

### 🔧 2. **Собрать точную статистику**

Если ты знаешь, что значения skew'нуты:

```sql
ALTER TABLE events ALTER COLUMN event_type SET STATISTICS 1000;
ANALYZE events;
```

Это даст планировщику **больше информации**.

### 🔧 3. **Материализовать / денормализовать**

Если запрос повторяется и важен:

- завести materialized view или
    
- использовать [pg_bm25](https://github.com/aaronriekenberg/pg_bm25) или другую форму GIN индекса.
    

### 🔧 4. **Кластеризовать таблицу**

Если ты часто фильтруешь по `event_type`, и данные сильно сгруппированы:

```sql
CLUSTER events USING idx_event_type;
```

Это **физически перестроит таблицу**, упорядочив строки по индексу → меньше random I/O.

> ⚠️ Важно: `CLUSTER` блокирует таблицу. Использовать с осторожностью.

## 💡 Итог

|🧠 Принцип|💬 Что это значит|
|---|---|
|Index Scan ≠ быстро|Особенно при плохой селективности|
|Planner не всеведущ|Он работает по статистике — обновляй её!|
|Анализируй `Buffers`|Только `ANALYZE` покажет реальную цену|
|Кэш → спасение, но не вечное|Warm cache прячет проблемы — до первого сброса|
