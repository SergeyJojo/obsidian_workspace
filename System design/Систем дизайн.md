### 1. **Декомпозиция системы и Domain-Driven Design (DDD)**

Микросервисная архитектура во многом строится на подходе **Domain-Driven Design (DDD)**, где сложная бизнес-логика разбивается на **домены** и **поддомены**. Глубже в этом аспекте:

#### **Этапы декомпозиции:**

1. **Выделение доменов:**
    
    - Разделите систему на **основные бизнес-домены**:
        - В интернет-магазине это могут быть "каталог товаров", "платежи", "пользователи".
    - Используйте **контекстные ограничения** (Bounded Contexts), чтобы понять, где начинается и заканчивается ответственность каждого сервиса.
2. **Определение взаимодействия между доменами:**
    
    - Связи между доменами моделируются через **агрегаты** и **внешние контексты**.
    - Пример: Сервис "платежи" может вызывать "заказы" для проверки статуса заказа, но не должен напрямую управлять его данными.

#### **Реальные примеры доменов и контекстов:**

- **Core Domain:** Ключевые области вашего бизнеса (например, "обработка заказов").
- **Supporting Subdomains:** Поддерживающие поддомены (например, "уведомления").
- **Generic Subdomains:** Общие поддомены (например, "аутентификация").

**Инструменты для проектирования:**

- **Event Storming:** Визуализация событий, которые происходят в системе.
- **Context Mapping:** Чертёж взаимодействий между сервисами.

### 2. **Шардирование и масштабирование**

#### **Модели шардирования:**

1. **На основе данных (Data Sharding):**
    
    - Разделение данных между несколькими базами данных.
    - Пример: Деление пользователей по региону (`region_id % num_shards`).
2. **На основе нагрузки (Load Sharding):**
    
    - Разделение запросов по нескольким экземплярам одного сервиса.
3. **Вертикальное деление:**
    
    - Разделение функциональности между сервисами (например, сервис пользователей и сервис заказов).

#### **Реализация шардирования:**

```go
func getShard(key string, numShards int) int {
    h := fnv.New32a()
    h.Write([]byte(key))
    return int(h.Sum32()) % numShards
}
```

### 3. **Оркестрация или хореография?**

#### **Оркестрация:**

- Центральный компонент (например, **Saga Orchestrator**) управляет процессом.
- Удобна для сложных рабочих процессов.

#### **Хореография:**

- Сервисы реагируют на события и сами принимают решения.
- Легче расширяется, но сложнее отлаживать.

**Пример:** В процессе создания заказа:

- **Оркестрация:** Централизованный процесс управляет вызовами сервисов оплаты и доставки.
- **Хореография:** Сервис заказов генерирует событие "Заказ создан", а сервисы доставки и оплаты реагируют на него независимо.

### 4. **Service Mesh**

Когда система становится сложной, управление взаимодействиями между сервисами становится вызовом. Здесь на помощь приходит **Service Mesh**.

#### **Функционал:**

1. **Трассировка запросов (Tracing):**
    
    - Инструменты вроде Jaeger показывают, как запросы проходят через всю систему.
2. **Балансировка нагрузки:**
    
    - Service Mesh автоматически распределяет трафик между экземплярами сервисов.
3. **Шифрование:**
    
    - Включение TLS без изменения кода приложений.

Примеры: **Istio**, **Linkerd**.

### 5. **Разработка API и контрактов**

#### **Versioning API:**

- Поддержка нескольких версий API.
- Использование версионирования через URL:
    
    ```
    /v1/orders
    /v2/orders
    ```
    

#### **Контрактное тестирование:**

- Инструмент **Pact** помогает проверить, что взаимодействия между сервисами остаются корректными после изменений.

---

### 6. **Управление конфигурациями**

Когда сервисов много, управление конфигурациями становится критичным. Используйте:

- **Centralized Configuration Management:**
    - Например, Consul или Spring Cloud Config.
- **Feature Toggles (флаги функций):**
    - Включение/выключение функциональности на лету.

---

### 7. **Обработка ошибок и отказоустойчивость**

#### **Паттерны:**

1. **Circuit Breaker:**
    
    - Разрывает цепочку вызовов, если один из сервисов не отвечает.
    - Пример: Netflix Hystrix (или встроенный функционал в Istio).
2. **Timeouts и Retries:**
    
    - Устанавливайте таймауты для вызовов:
        
        ```go
        client := http.Client{Timeout: 5 * time.Second}
        ```
        

---

### 8. **Сложности распределённых систем**

#### **CAP-теорема:**

- Три свойства системы:
    1. **Consistency:** Все узлы видят одинаковые данные.
    2. **Availability:** Система отвечает на запросы.
    3. **Partition Tolerance:** Работает даже при разделении сети.

В микросервисах обычно жертвуют **Consistency** ради **Availability**.

#### **Eventual Consistency:**

- Данные синхронизируются через некоторое время.
- Подходит для асинхронных операций (например, обработки платежей).
