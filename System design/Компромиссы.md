## **1. Архитектурные компромиссы: как делать правильный выбор**

На высоком уровне твои собеседники будут оценивать, как ты подходишь к **компромиссам**. Это важно, потому что в системах нет "идеальных решений", есть только **лучшие решения для конкретного контекста**.

### **1.1. Разбор компромиссов**

1. **Consistency vs Availability (CAP-теорема)**:
    
    - Если у тебя распределённая система, ты должен выбрать между:
        - **Сильной согласованностью (strong consistency):**
            - Данные всегда консистентны, но высокая задержка при записи.
            - Пример: Банковские транзакции.
        - **Высокой доступностью (availability):**
            - Система продолжает работать даже при разделении сети, но данные могут быть неактуальными (eventual consistency).
            - Пример: Системы кэширования.
2. **Микросервисы vs Монолит:**
    
    - Когда говорить: "Лучше микросервисы":
        - Если команда большая и каждый микросервис может быть разрабатываться независимо.
        - Если требуется масштабирование отдельных частей.
    - Когда говорить: "Монолит эффективнее":
        - Если проект небольшой и накладные расходы на микросервисы неоправданны.

## **2. Eventual Consistency: углубляемся в детали**

**Согласованность в конечном итоге (eventual consistency)** — это основа большинства современных микросервисных систем. Давайте разберёмся в её деталях.

### **2.1. Вызовы в реальной жизни**

1. **Расхождение данных:**
    - Например, сервис A обработал заказ, но сервис B получил оповещение о заказе только через 10 секунд.
2. **Дублирование данных:**
    - Если один и тот же ивент обработан дважды (например, из-за повторной доставки Kafka).

### **2.2. Паттерны решения**

1. **Idempotency (Идемпотентность):**
    
    - Обработчик событий должен быть идемпотентным: если одно и то же сообщение придёт несколько раз, результат будет одинаковым.
    - Пример:
        
        ```go
        func ProcessOrder(orderID string) error {
            if IsOrderProcessed(orderID) {
                return nil
            }
            MarkOrderAsProcessed(orderID)
            return nil
        }
        ```
        
2. **Событийная версия (Event Versioning):**
    
    - Чтобы обработчики могли корректно работать с изменениями структуры данных в событиях.
    - Пример:
        - В Kafka можно добавлять версии событий, например `OrderCreatedV1`, `OrderCreatedV2`.

## **3. Алгоритмы в распределённых системах**

Чтобы покорить собеседование, нужно не только знать, как строить системы, но и понимать **глубокие алгоритмы**, которые лежат в их основе.

### **3.1. Алгоритмы консенсуса**

**Распределённые системы используют консенсус, чтобы согласовать состояние между узлами.** Вот самые популярные алгоритмы:

1. **Raft (гораздо проще, чем Paxos):**
    
    - Используется в распределённых базах данных (например, etcd).
    - Главная идея:
        - Один узел становится лидером.
        - Все изменения данных проходят через лидера.
    - Пример: etcd, Consul.
2. **Gossip Protocol (Протокол сплетен):**
    
    - Каждый узел случайным образом делится данными с соседним узлом.
    - Используется в системах, где важна **eventual consistency**, например, в Cassandra.

## **4. Распределённые транзакции**

Когда у тебя есть данные, распределённые по нескольким базам данных или сервисам, ты сталкиваешься с вызовом: **Как выполнить транзакцию, затрагивающую несколько систем?**

### **4.1. Паттерн 2PC (Two-Phase Commit):**

- Используется, чтобы убедиться, что все участники транзакции либо завершают её, либо откатывают.
- Проблема:
    - Высокая задержка.
    - Уязвимость к сбоям координатора.

### **4.2. Паттерн SAGA**

Saga решает проблему распределённых транзакций через **последовательность шагов и компенсаций**:

1. Каждый шаг — это независимый вызов.
2. Если один из шагов не удался, система выполняет компенсационные действия.

#### Пример:

```plaintext
1. Заказ сделан -> Сервис оплаты списывает деньги -> Сервис доставки резервирует товар.
2. Если доставка не удалась -> Сервис оплаты возвращает деньги -> Сервис заказов отменяет заказ.
```

#### Реализация:

```go
type SagaStep struct {
    Action       func() error
    Compensation func() error
}

type Saga struct {
    Steps []SagaStep
}

func (s *Saga) Execute() error {
    for _, step := range s.Steps {
        if err := step.Action(); err != nil {
            // Выполнить компенсацию
            for _, cStep := range s.Steps {
                cStep.Compensation()
            }
            return err
        }
    }
    return nil
}
```

## **5. Оркестрация микросервисов: углубляемся в Service Mesh**

Service Mesh (например, Istio) — это способ управления сетевым взаимодействием между сервисами.

### **5.1. Проблемы, которые решает Service Mesh**

1. **Безопасность:**
    - Автоматическое шифрование трафика через mTLS.
2. **Трассировка:**
    - Каждое взаимодействие между сервисами логируется.
3. **Политики маршрутизации:**
    - Например, направлять только 10% трафика на новую версию сервиса.

## **6. Как отвечать на сложные вопросы**

### **6.1. Что делать, если система перегружена?**

1. Включить **Rate Limiting (Ограничение запросов)**:
    
    - Пример: Используй токен-бакет для контроля скорости запросов.
2. Используй **Backpressure (обратное давление)**:
    
    - Если очередь сообщений заполняется, начни отклонять новые сообщения.

---

### **6.2. Как справляться с отказами?**

1. **Circuit Breaker**:
    - Защитит систему от перегрузки.
2. **Retry with Exponential Backoff**:
    - Автоматически повторяет запросы с увеличивающимся интервалом.
