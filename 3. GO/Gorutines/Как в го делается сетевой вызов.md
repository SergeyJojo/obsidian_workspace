
# **Полный цикл сетевого запроса в Go: от горутины до результата**

Рассмотрим, как Go обрабатывает сетевые запросы, начиная с вызова горутины и заканчивая возвратом данных, с участием планировщика, netpoller'а и системных вызовов.

---

## **1. Инициализация запроса (горутина)**
```go
resp, err := http.Get("https://example.com") // Горутина создается для запроса
```
- Горутина (`G`) создается планировщиком (`GOMAXPROCS` рабочих потоков `M`).
- Она попадает в **очередь локального (P) или глобального планировщика**.

---

## **2. Работа с сокетом**
### **Создание сокета**
1. Go вызывает `socket()` → создается файловый дескриптор (`fd`).
2. Для этого `fd` настраивается **неблокирующий режим** (`fcntl(fd, F_SETFL, O_NONBLOCK)`).

### **Установка соединения (TCP)**
```go
conn, err := net.Dial("tcp", "example.com:80")
```
- Системный вызов `connect()` в неблокирующем режиме возвращает `EINPROGRESS`.
- Go регистрирует `fd` в **netpoller**.

---

## **3. Netpoller и асинхронный I/O**
### **Что такое netpoller?**
- Компонент рантайма Go, который мониторит **готовность файловых дескрипторов** (сокетов).
- Использует **эффективный системный механизм**:
  - Linux: `epoll` (или `poll` в старых версиях)
  - macOS: `kqueue`
  - Windows: `IOCP`

### **Регистрация fd в netpoller**
1. При вызове `conn.Read()` или `conn.Write()`:
   ```go
   n, err := conn.Read(buf) // Неблокирующий вызов
   ```
2. Go создает **`pollDesc`** — структуру, связывающую `fd` и горутину.
3. `pollDesc` регистрируется в netpoller через:
   ```c
   // Псевдокод из рантайма Go
   poll_runtime_pollOpen(fd) // Добавляет fd в epoll/kqueue
   ```

---

## **4. Блокировка горутины**
- Если данные недоступны, горутина **переходит в режим ожидания**:
  ```go
  gopark(netpollblock, pd, waitReasonIOWait) // Горутина приостанавливается
  ```
- Планировщик (`P`) **отвязывает горутину** от потока (`M`).
- Поток `M` освобождается для выполнения других горутин.

---

## **5. Ожидание события (системный вызов)**
1. Netpoller вызывает `epoll_wait()` (Linux) или `kevent()` (macOS).
2. Ядро ОС **будит netpoller**, когда сокет готов:
   - Для чтения (`EPOLLIN`).
   - Для записи (`EPOLLOUT`).
3. Netpoller **находит `pollDesc`**, связанный с `fd`.

---

## **6. Пробуждение горутины**
1. Netpoller помечает горутину **как готовую к выполнению**.
2. Горутина возвращается в **очередь планировщика** (локальную или глобальную).
3. Когда `P` получает квант времени, он **запускает горутину**.

---

## **7. Чтение/запись данных**
- Горутина **повторно вызывает системный вызов** (теперь он выполнится без блокировки):
  ```c
  n, err = syscall.Read(fd, buf) // Данные уже готовы
  ```
- Если ошибок нет, данные копируются в буфер Go.

---

## **8. Возврат результата**
```go
resp, err := http.Get("https://example.com") // Горутина получает ответ
```
- Результат возвращается в горутину.
- Сокет закрывается (или возвращается в пул для keep-alive).

---

## **Схема цикла**
```
Горутина → Создание сокета (неблокирующий) → Netpoller (epoll/kqueue)
          ↓                                      ↑
          |--- Блокировка (gopark) —-------------|
          ↓
Планировщик переключается на другие горутины
          ↓
Сокет готов → Netpoller будит горутину → Возврат в планировщик → Чтение данных
```

---

## **Ключевые компоненты**
| Компонент          | Роль                                                                 |
|---------------------|----------------------------------------------------------------------|
| **Горутина (G)**    | Легковесный поток, выполняющий запрос.                              |
| **Поток (M)**       | Системный поток, привязанный к ядру CPU.                            |
| **Планировщик (P)** | Менеджер горутин (до `GOMAXPROCS` на процесс).                       |
| **Netpoller**       | Мониторит сокеты через `epoll`/`kqueue`.                            |
| **pollDesc**        | Связывает `fd` и горутину.                                          |
| **Файловый дескриптор (fd)** | Неблокирующий сокет.                                          |

---

## **Почему это эффективно?**
1. **Нет блокировки потоков** — горутины приостанавливаются, а не потоки ОС.
2. **Меньше накладных расходов** — netpoller использует 1 поток на все I/O-операции.
3. **Масштабируемость** — тысячи горутин работают на нескольких потоках.

---

## **Пример с `strace` (Linux)**
Если трассировать Go-программу, можно увидеть:
1. `epoll_create1()` — создание netpoller'а.
2. `socket()` + `fcntl(..., O_NONBLOCK)` — неблокирующий сокет.
3. `epoll_ctl(EPOLL_CTL_ADD)` — регистрация fd.
4. `epoll_wait()` — ожидание событий.

---

## **Итог**
- **Горутины** + **netpoller** — основа сетевого I/O в Go.
- **Неблокирующие сокеты** и **эффективные системные вызовы** (`epoll`) позволяют обрабатывать миллионы соединений.
- **Планировщик** переключает горутины при блокировке I/O.

Это объясняет, почему Go так хорошо подходит для сетевых сервисов! 🚀
