
В PostgreSQL блокировки обеспечивают согласованность данных при параллельных транзакциях. Вот основные типы и пример дедлока:

---

## **1. Типы блокировок в PostgreSQL**
### **A. Блокировки таблиц (на уровне SQL)**
| Тип блокировки       | Описание                                                                 | Когда срабатывает                                                                 |
|----------------------|--------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| **ACCESS SHARE**     | Самая слабая. Чтение данных.                                            | `SELECT`                                                                         |
| **ROW SHARE**        | Разрешает параллельное чтение, но запрещает эксклюзивные блокировки.    | `SELECT FOR UPDATE/SHARE`                                                        |
| **ROW EXCLUSIVE**    | Блокирует изменение строк, но разрешает чтение.                         | `INSERT`, `UPDATE`, `DELETE`                                                     |
| **SHARE**           | Запрещает изменение данных, но разрешает чтение.                        | `CREATE INDEX` (без `CONCURRENTLY`)                                               |
| **SHARE ROW EXCLUSIVE** | Более строгая версия `SHARE`.                                          | Альтер-команды (`ALTER TABLE`), некоторые формы `CREATE INDEX`                   |
| **EXCLUSIVE**        | Разрешает только `ACCESS SHARE`, блокирует все остальные операции.      | `VACUUM FULL`, `CREATE INDEX CONCURRENTLY` (на финальной стадии)                 |
| **ACCESS EXCLUSIVE** | Полная блокировка таблицы.                                              | `DROP TABLE`, `TRUNCATE`, большинство `ALTER TABLE`                               |

---

### **B. Блокировки строк**
| Тип                | Описание                                     |
|--------------------|---------------------------------------------|
| **FOR UPDATE**     | Блокирует строку для изменения (другие транзакции ждут). |
| **FOR SHARE**      | Разрешает чтение, но запрещает `FOR UPDATE`.             |
| **FOR NO KEY UPDATE** | Блокирует только неключевые изменения.                 |

**Пример**:
```sql
BEGIN;
SELECT * FROM accounts WHERE id = 1 FOR UPDATE; -- Блокировка строки
-- Другая транзакция, пытающаяся изменить эту строку, будет ждать...
COMMIT;
```

---

## **2. Когда срабатывают блокировки?**
- **Автоматически**: При `INSERT/UPDATE/DELETE` (ROW EXCLUSIVE).  
- **Явно**: При `SELECT ... FOR UPDATE/SHARE`.  
- **Неявно**: При DDL-операциях (`ALTER TABLE` → ACCESS EXCLUSIVE).  

---

## **3. Как создать дедлок?**
Дедлок возникает, когда две транзакции блокируют ресурсы в разном порядке и бесконечно ждут друг друга.

### **Пример дедлока**:
1. **Транзакция 1**:
   ```sql
   BEGIN;
   UPDATE accounts SET balance = balance - 100 WHERE id = 1; -- Блокирует строку id=1
   ```

2. **Транзакция 2**:
   ```sql
   BEGIN;
   UPDATE accounts SET balance = balance + 50 WHERE id = 2; -- Блокирует строку id=2
   ```

3. **Транзакция 1** пытается изменить `id=2`:
   ```sql
   UPDATE accounts SET balance = balance + 100 WHERE id = 2; -- Ждёт Транзакцию 2
   ```

4. **Транзакция 2** пытается изменить `id=1`:
   ```sql
   UPDATE accounts SET balance = balance - 50 WHERE id = 1; -- Ждёт Транзакцию 1
   ```

**Результат**:  
PostgreSQL обнаруживает дедлок и **абортирует одну из транзакций**:
```
ERROR: deadlock detected
DETAIL: Process 123 waits for ShareLock on transaction 456; blocked by process 789.
```

## **4. Как мониторить блокировки?**
### **A. Просмотр активных блокировок**
```sql
SELECT blocked_locks.pid AS blocked_pid,
       blocking_locks.pid AS blocking_pid,
       blocked_activity.query AS blocked_query,
       blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
     AND blocking_locks.DATABASE IS NOT DISTINCT FROM blocked_locks.DATABASE
     AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
     AND blocking_locks.page IS NOT DISTINCT FROM blocked_locks.page
     AND blocking_locks.tuple IS NOT DISTINCT FROM blocked_locks.tuple
     AND blocking_locks.virtualxid IS NOT DISTINCT FROM blocked_locks.virtualxid
     AND blocking_locks.transactionid IS NOT DISTINCT FROM blocked_locks.transactionid
     AND blocking_locks.classid IS NOT DISTINCT FROM blocked_locks.classid
     AND blocking_locks.objid IS NOT DISTINCT FROM blocked_locks.objid
     AND blocking_locks.objsubid IS NOT DISTINCT FROM blocked_locks.objsubid
     AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.GRANTED;
```

### **B. Логирование дедлоков**
В `postgresql.conf`:
```ini
log_lock_waits = on
deadlock_timeout = 1s  -- Время, после которого ожидание считается потенциальным дедлоком
```

## **5. Как избежать дедлоков?**
1. **Унифицированный порядок блокировки**: Всегда блокируйте ресурсы в одинаковом порядке (например, сначала `id=1`, потом `id=2`).  
2. **Короткие транзакции**: Чем быстрее транзакция, тем меньше шансов на конфликт.  
3. **`NOWAIT`**: Если не хотите ждать:  
   ```sql
   SELECT * FROM accounts WHERE id = 1 FOR UPDATE NOWAIT;
   ```
4. **Оптимизация запросов**: Используйте индексы, чтобы уменьшить время блокировок.  

---

### **Итог**
- Блокировки в PostgreSQL работают на уровне **таблиц** и **строк**.  
- Дедлоки возникают при **циклической зависимости** блокировок.  
- Мониторинг через `pg_locks` и настройки `log_lock_waits`.  
- Профилактика: порядок блокировок + короткие транзакции.
