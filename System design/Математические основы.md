## **1. Математические основы распределённых систем**

### **1.1. Алгоритмы консенсуса на атомарном уровне**

Для построения отказоустойчивых систем, где несколько узлов согласуются о состоянии данных, используются **Paxos**, **Raft** и их производные.

#### **Paxos: основа всего**

1. Paxos решает проблему, как несколько узлов могут прийти к единому решению, даже если некоторые из них выходят из строя.
2. Основные роли:
    - **Proposer:** Предлагает значение.
    - **Acceptor:** Принимает или отвергает предложение.
    - **Learner:** Узнаёт, какое значение было принято.

Примерная логика Paxos:

```plaintext
1. Proposer предлагает значение.
2. Acceptor принимает, если это значение имеет высший приоритет.
3. Если большинство Acceptor'ов согласились, значение становится "закреплённым".
```

#### **Raft: упрощённая версия Paxos**

Raft делает акцент на удобочитаемости и практической реализации.

1. **Лидер:** Один узел становится "лидером" и управляет записью данных.
2. **Фолловеры:** Остальные узлы реплицируют данные лидера.
3. Если лидер недоступен, проводится выбор нового лидера.

### **1.2. Eventual Consistency: математическая модель**

Eventual Consistency основана на **CRDT (Conflict-Free Replicated Data Types)**:

- Это структуры данных, которые могут автоматически синхронизироваться между узлами без конфликта.

#### **Примеры CRDT:**

1. **Grow-Only Set (G-Set):**
    
    - Добавление элементов идемпотентно.
    - Конфликты разрешаются путём объединения всех элементов.
2. **Conflict-Free Counter:**
    
    - Обеспечивает согласованность счётчиков при параллельных изменениях.
    - Пример: Использование в Redis для подсчёта.

## **2. Продвинутые алгоритмы маршрутизации и балансировки нагрузки**

### **2.1. Consistent Hashing (углубление)**

1. **Что это такое?**
    
    - Это метод распределения данных по узлам так, чтобы при добавлении/удалении узлов изменения в распределении данных были минимальными.
2. **Виртуальные узлы:**
    
    - Для равномерного распределения нагрузки каждый физический узел ассоциируется с несколькими виртуальными узлами.

#### **Реализация на Go:**

```go
type ConsistentHash struct {
    nodes []int
}

func (ch *ConsistentHash) AddNode(node int) {
    ch.nodes = append(ch.nodes, node)
    sort.Ints(ch.nodes)
}

func (ch *ConsistentHash) GetNode(key int) int {
    idx := sort.Search(len(ch.nodes), func(i int) bool { return ch.nodes[i] >= key })
    if idx == len(ch.nodes) {
        idx = 0
    }
    return ch.nodes[idx]
}
```

## **3. Теория очередей: управление запросами**

### **3.1. Закон Литтла**

- Основное правило теории очередей:
    
    ```plaintext
    L = λ * W
    ```
    
    Где:
    - `L`: Среднее количество запросов в системе.
    - `λ`: Средняя скорость поступления запросов.
    - `W`: Среднее время обработки запроса.

Пример: если твоя система обрабатывает 100 запросов в секунду (λ = 100), а среднее время ответа составляет 0,2 секунды (W = 0.2), то в системе одновременно будет около 20 запросов (`L = 100 * 0.2`).

---

### **3.2. Алгоритмы обработки очередей**

1. **First In, First Out (FIFO):**
    - Простая стратегия, где запросы обрабатываются в порядке поступления.
2. **Priority Queue:**
    - Запросы с более высоким приоритетом обрабатываются раньше.
3. **Weighted Fair Queueing (WFQ):**
    - Алгоритм, который равномерно распределяет пропускную способность между разными типами трафика.

## **4. Расширенные паттерны отказоустойчивости**

### **4.1. Quorum-Based Systems**

- **Quorum** — это минимальное количество узлов, которые должны согласиться для принятия решения.
- Пример: Если у тебя 5 узлов, то для записи данных ты можешь потребовать согласия 3 из них.

#### **Преимущества:**

- Обеспечивает баланс между согласованностью и доступностью.
- Используется в DynamoDB, Cassandra.

---

### **4.2. Backpressure в очередях**

- **Backpressure** — это механизм, который предотвращает перегрузку системы, ограничивая скорость поступления запросов.
- Пример: RabbitMQ может сообщить издателю, что очередь заполнена, и временно остановить приём сообщений.

## **5. Метрики и мониторинг на новом уровне**

### **5.1. Расширенные метрики**

1. **RED Метрики:**
    
    - **Rate:** Количество запросов в секунду.
    - **Errors:** Количество ошибок.
    - **Duration:** Средняя длительность запроса.
2. **USE Метрики (для систем):**
    
    - **Utilization (использование):** Процент использования ресурса.
    - **Saturation (перегрузка):** Сколько ресурсов в очереди.
    - **Errors:** Количество ошибок в системе.

### **5.2. Инструменты мониторинга**

- **Prometheus + Grafana:**
    - Сбор метрик и визуализация.
- **OpenTelemetry:**
    - Полная трассировка запросов через распределённые системы.

### **Кейс 1: Дизайн глобальной системы чата**

- Проблема: "Пользователи по всему миру отправляют сообщения, которые должны доставляться за миллисекунды."
- Решение:
    1. Используй **CDN для сообщений**:
        - Пользователи отправляют сообщения в локальные сервера.
    2. **Eventual Consistency**:
        - Все сообщения реплицируются через Kafka или Pulsar.

---

### **Кейс 2: Как уменьшить стоимость системы?**

- Проблема: "Текущая инфраструктура слишком дорогая."
- Решение:
    - Перенеси "холодные" данные в хранилище S3.
    - Увеличь использование кэша:
        - Например, Cloudflare Workers для обработки запросов на периферии.
