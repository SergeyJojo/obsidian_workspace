# **Сборщик мусора в Go: глубокий разбор**

---

## **1. Основы работы GC в Go**

---

### **1.1. Что такое сборщик мусора (Garbage Collector)?**

GC отвечает за автоматическое управление памятью:

- Освобождает память, занятую объектами, которые больше не используются.
- Предотвращает утечки памяти.
- Упрощает разработку, снимая с разработчика обязанность вручную управлять памятью.

---

### **1.2. Основные принципы GC в Go**

1. **Concurrent** (Конкурентный):
    
    - Выполняется параллельно с пользовательским кодом.
    - Минимизирует "стоп-мир" паузы.
2. **Tri-color marking** (Трёхцветная маркировка):
    
    - Используется для определения "живых" объектов.
3. **Generational** (Поколенческий подход):
    
    - Объекты, которые "долго живут", реже проверяются.
4. **Non-compacting** (Неуплотняющий):
    
    - GC в Go не перемещает объекты в памяти.

---

### **1.3. Жизненный цикл объекта**

1. **Allocation**:
    
    - Память выделяется через `new`, `make`, или явную инициализацию.
2. **Reachability**:
    
    - Если объект доступен из корней (например, глобальные переменные, стек горутин), он считается живым.
3. **Garbage Collection**:
    
    - Если объект больше недостижим, его память освобождается.

---

## **2. Трёхцветный алгоритм маркировки (Tri-color marking)**

---

### **2.1. Основы алгоритма**

Алгоритм работает на базе трёхцветной схемы:

1. **Белые объекты**:
    - Кандидаты на удаление.
2. **Серые объекты**:
    - Известно, что объект жив, но его ссылки ещё не проверены.
3. **Чёрные объекты**:
    - Объект жив, и все его ссылки уже проверены.

---

### **2.2. Этапы работы**

1. **Initial Mark** (Начальная маркировка):
    
    - Сканируются "корни" (глобальные переменные, стеки горутин).
2. **Concurrent Mark** (Конкурентная маркировка):
    
    - Проверяются ссылки на объекты, начиная с серых объектов.
    - На этом этапе пользовательский код может продолжать работать.
3. **Sweep** (Очистка):
    
    - Белые объекты (неиспользуемые) удаляются.
4. **Final Mark**:
    
    - Короткий "стоп-мир", чтобы завершить маркировку.

---

### **2.3. Почему алгоритм эффективен?**

1. **Concurrency**:
    
    - Основные этапы маркировки выполняются параллельно с пользовательским кодом.
2. **Incremental**:
    
    - Не блокирует выполнение программы на долгие периоды.
3. **Write Barrier** (Барьер записи):
    
    - Используется, чтобы отслеживать изменения в ссылках во время работы GC.

---

## **3. Настройка и управление GC в Go**

---

### **3.1. GOGC (Garbage Collection Percent)**

**GOGC** определяет, как часто запускается GC, основываясь на росте кучи.

- **Формула**:
    
    ```
    GOGC = 100 * (новый размер кучи / текущий размер кучи - 1)
    ```
    

#### **Пример настройки GOGC**

```bash
GOGC=100 ./my_program
```

- **Значения**:
    - `GOGC=0`: Отключает GC.
    - `GOGC=100`: По умолчанию (GC запускается, когда куча увеличивается на 100%).
    - `GOGC=200`: Реже запуск GC (лучше для пропускной способности, но больше памяти).
    - `GOGC=50`: Чаще запуск GC (меньше памяти, но больше задержек).

---

### **3.2. Отладка GC**

1. **Сбор метрик GC**:
    
    - Используй **runtime.MemStats**:
        
        ```go
        var memStats runtime.MemStats
        runtime.ReadMemStats(&memStats)
        fmt.Printf("HeapAlloc: %v KB\n", memStats.HeapAlloc/1024)
        ```
        
2. **Включение трассировки GC**:
    
    ```bash
    GODEBUG=gctrace=1 ./my_program
    ```
    
    **Вывод**:
    
    ```
    gc 6 @8.34s 5%: 0.008+0.15+0.002 ms clock, 0.008+0.015/0.067/0.15+0.002 ms cpu, 4->5->3 MB, 5 MB goal, 8 P
    ```
    
    - `gc 6`: Шестой запуск GC.
    - `@8.34s`: Время выполнения программы.
    - `4->5->3 MB`: Размеры кучи до/после/освобождения.
3. **Профилирование памяти**:
    
    - Используй **pprof**:
        
        ```bash
        go tool pprof http://localhost:6060/debug/pprof/heap
        ```
        

---

### **3.3. Управление памятью**

#### **Пример ручного освобождения памяти**

```go
runtime.GC() // Принудительный запуск GC
debug.FreeOSMemory() // Освобождение памяти в ОС
```

---

## **4. Влияние GC на производительность**

---

### **4.1. Задержки GC**

- Основная метрика: **Stop-the-world (STW)** паузы.
- Современный GC в Go минимизирует STW до микросекунд.

#### **Как уменьшить задержки**:

1. Оптимизируй структуру данных (меньше ссылок между объектами).
2. Увеличь значение `GOGC`, если память позволяет.

---

### **4.2. Пропускная способность (Throughput)**

GC может замедлить программы с большим количеством короткоживущих объектов (например, временные слайсы).

#### **Как улучшить производительность**:

1. Используй **sync.Pool** для повторного использования объектов.
2. Избегай чрезмерного выделения памяти в горячих циклах.

---

## **5. Реальные примеры оптимизации**

---

### **5.1. Использование sync.Pool**

`sync.Pool` — это кеш для объектов, который помогает уменьшить нагрузку на GC.

#### **Пример**:

```go
package main

import (
	"fmt"
	"sync"
)

var pool = sync.Pool{
	New: func() interface{} {
		return make([]byte, 1024) // Аллоцируем 1KB
	},
}

func main() {
	buf := pool.Get().([]byte) // Получаем объект из пула
	fmt.Printf("Buffer length: %d\n", len(buf))
	pool.Put(buf) // Возвращаем объект в пул
}
```

- Объекты в пуле не учитываются GC, пока они не используются.

---

### **5.2. Уменьшение ссылок**

GC проверяет все ссылки между объектами. Чем их меньше, тем быстрее GC.

#### **Пример плохого дизайна**:

```go
type Node struct {
	Children []*Node
}
```

#### **Пример оптимизированного дизайна**:

Если дерево неизменяемо:

```go
type Node struct {
	Children []int // Храним индексы, а не указатели
}
```

---

### **5.3. Анализ и оптимизация утечек памяти**

1. **Поиск утечек**:
    
    - Используй профилирование:
        
        ```bash
        go tool pprof ./my_program heap.prof
        ```
        
2. **Используй go build с флагами отладки**:
    
    ```bash
    go build -gcflags="-m" ./main.go
    ```
    
    **Вывод**:
    
    ```
    main.go:10: leaking param: msg
    ```

# **Сборщик мусора в Go: Углубление**

---

## **1. Внутренние структуры памяти в Go**

Чтобы понять, как работает сборщик мусора, нужно сначала разобрать, как организована память в Go.

---

### **1.1. Организация кучи**

Куча в Go делится на три зоны:

1. **Allocated objects**: Объекты, которые активно используются.
2. **Free spans**: Участки памяти, которые больше не используются и могут быть перераспределены.
3. **Metadata**: Хранит информацию о всех объектах в куче.

#### **Основные структуры**

- **mheap**: Главная структура, управляющая всей кучей.
- **mspan**: Участки памяти, выделяемые для объектов.
- **mcache**: Локальный кеш для каждого потока, чтобы уменьшить блокировки при аллокации.

---

### **1.2. Аллокация памяти**

#### **Как Go выделяет память:**

1. **Маленькие объекты (<32 KB)**:
    
    - Выделяются из **mcache**, локального кеша потока.
    - Аллокация почти моментальная.
2. **Крупные объекты (>32 KB)**:
    
    - Выделяются напрямую из **mheap**, что может быть дороже.

#### **Пример: оптимизация под маленькие объекты**

Если у тебя много мелких объектов, избегай частых выделений:

```go
type SmallStruct struct {
	Field1 int
	Field2 string
}

// Вместо этого:
slice := make([]SmallStruct, 1000)

// Используй буферы, такие как sync.Pool
```

---

### **1.3. Write Barrier**

Go использует **write barrier**, чтобы отслеживать изменения ссылок между объектами во время выполнения программы. Это ключевая часть работы сборщика мусора.

#### **Пример: как это работает**

Когда программа изменяет ссылку на объект:

1. Write barrier добавляет ссылку в список "серых" объектов.
2. Это позволяет GC корректно отслеживать новые зависимости.

---

### **1.4. Поколения объектов**

Go использует **поколенческий подход**:

1. **Short-lived objects**: Умирают быстро (например, временные объекты).
2. **Long-lived objects**: Проверяются реже, так как вероятность их удаления ниже.

---

## **2. Оптимизация для низкоресурсных систем**

Если ты работаешь с ограниченной памятью (например, IoT-устройства), важно настроить сборщик мусора.

---

### **2.1. Отключение GC в критических секциях**

Иногда GC может вызывать нежелательные паузы. Ты можешь отключить его на время выполнения критического кода:

```go
debug.SetGCPercent(-1) // Отключить GC
// Критический код
runtime.GC()           // Принудительный запуск GC
debug.SetGCPercent(100) // Включить GC
```

---

### **2.2. Уменьшение объёмов аллокации**

#### **Пример: использование массивов вместо слайсов**

```go
// Плохо
func doSomething() {
	data := make([]int, 1000)
	// Массив часто пересоздаётся
}

// Хорошо
var data [1000]int // Объект создаётся один раз
```

---

### **2.3. Минимизация временных объектов**

#### **Пример: использование bytes.Buffer**

```go
// Плохо
str := "Hello" + " " + "World"

// Хорошо
var buf bytes.Buffer
buf.WriteString("Hello")
buf.WriteString(" ")
buf.WriteString("World")
```

---

### **2.4. Настройка GOGC для низкой памяти**

Если у тебя мало памяти, настрой GOGC так, чтобы GC запускался чаще:

```bash
GOGC=50 ./my_program
```

## **4. Углубление в исходники runtime**

Если ты хочешь понять, как работает GC в Go на низком уровне, можно посмотреть исходники.

---

### **4.1. Основные файлы**

1. **`mgc.go`**:
    
    - Основной файл, где описана логика сборщика мусора.
    - Функция `gcStart` запускает процесс сборки мусора.
2. **`mheap.go`**:
    
    - Управление кучей.
    - Функции `allocSpan` и `freeSpan` отвечают за выделение и освобождение памяти.

---

### **4.2. Разбор функции gcStart**

Функция `gcStart`:

1. Выполняет фазу "Initial Mark".
2. Запускает "Concurrent Mark".
3. Завершает процесс через "Sweep".

---

### **4.3. Расширенная отладка runtime**

1. Включи отладочные логи GC:
    
    ```bash
    GODEBUG=gctrace=1 ./my_program
    ```
    
2. Включи дополнительные трассировки:
    
    ```bash
    GODEBUG=gctrace=1,scheddetail=1 ./my_program
    ```
    

---

## **5. Реальные кейсы оптимизации**

---

### **5.1. Снижение нагрузки на GC с помощью sync.Pool**

#### **Когда использовать?**

- Для временных объектов, которые могут быть переиспользованы.

#### **Пример**:

```go
var pool = sync.Pool{
    New: func() interface{} {
        return make([]byte, 1024)
    },
}

func main() {
    buf := pool.Get().([]byte)
    // Используй буфер
    pool.Put(buf) // Возвращай объект в пул
}
```

---

### **5.2. Уменьшение Stop-the-World задержек**

Если у тебя важен минимальный `STW` (например, low-latency системы), настрой GOGC и используй профилирование:

```bash
GOGC=20 ./my_program
```
