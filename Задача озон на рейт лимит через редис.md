
### **Суть вопроса и разбор ответа**  

**Контекст:**  
У вас есть сервис, который использует внешний API для построения маршрутов. В рамках тарифного плана этого API есть ограничение на количество запросов в секунду (RPS — Requests Per Second). Чтобы не превысить лимит, нужно реализовать **Rate Limiter** (ограничитель запросов).  

---

## **Решение для Grade 18**  
### **1. Вариант 1: Внешнее хранилище (Redis)**  
**Как работает:**  
- В Redis хранится счетчик запросов (например, по ключу `user123:api_requests`).  
- При каждом запросе к API:  
  1. Увеличиваем счетчик в Redis.  
  2. Если счетчик превышает лимит — блокируем запрос.  
  3. Через N секунд (окно ограничения) счетчик сбрасывается.  

**Плюсы:**  
✅ **Простота реализации** — Redis поддерживает `INCR` + `EXPIRE`.  
✅ **Точность** — Все инстансы сервиса видят единый счетчик.  
✅ **Гибкость** — Можно настраивать лимиты для разных пользователей/API.  

**Минусы:**  
❌ **Единая точка отказа** — Если Redis упадет, rate limiting сломается.  
❌ **Задержки** — Дополнительный сетевой запрос к Redis.  

---

### **2. Вариант 2: Локальный Rate Limiter (без Redis)**  
**Как работает:**  
- Каждый инстанс сервиса имеет свой локальный счетчик.  
- Общий лимит `X` делится на количество инстансов (`X / N`).  
- Например, если лимит API = 100 RPS, а инстансов = 5, то каждый инстанс ограничен 20 RPS.  

**Плюсы:**  
✅ **Нет зависимости от Redis** — Устойчивость к отказам.  
✅ **Нет задержек** — Не нужны сетевые запросы.  

**Минусы:**  
❌ **Дисбаланс запросов** — Если один инстанс получит больше нагрузки, возможны превышения лимита API.  
❌ **Сложность конфигурации** — При изменении числа инстансов нужно пересчитывать квоты.  

---

## **Решение для Grade 19**  
### **Оптимизация работы с Redis**  
**Проблема:**  
Каждый запрос к Redis — это `INCR` + проверка лимита + `EXPIRE`. Это 2-3 команды, что создает нагрузку.  

**Решение:**  
Использовать **Lua-скрипт** в Redis для атомарной проверки лимита:  
```lua
local key = KEYS[1]        -- Ключ (например, "user123:api_requests")
local limit = tonumber(ARGV[1]) -- Лимит (например, 100)
local window = tonumber(ARGV[2]) -- Окно в секундах (например, 60)

local current = redis.call("GET", key)
if current and tonumber(current) >= limit then
    return 0  -- Лимит превышен
else
    redis.call("INCR", key)
    redis.call("EXPIRE", key, window)
    return 1  -- Запрос разрешен
end
```
**Преимущества:**  
- **1 запрос вместо 3** — Скрипт выполняется атомарно на сервере Redis.  
- **Нет race condition** — Между `INCR` и `EXPIRE` не будет разрыва.

## **Когда что выбирать?**  
| Критерий               | Redis-решение          | Локальное решение     |  
|------------------------|------------------------|-----------------------|  
| **Точность**           | ✅ Да (единый счетчик) | ❌ Нет (риск дисбаланса) |  
| **Отказоустойчивость** | ❌ Зависит от Redis    | ✅ Да                 |  
| **Производительность** | ❌ Задержки            | ✅ Быстро             |  
| **Балансировка**       | Не важно               | ❌ Требует баланса    |  

**Рекомендации:**  
- Если API **строго** следит за RPS → **Redis + Lua**.  
- Если допустимы кратковременные превышения → **Локальный счетчик**.  
- Для гибридного подхода: **Token Bucket** (комбинация локальных и Redis-счетчиков).

## **Дополнительные вопросы (Grade 19+)**
1. **Как избежать единой точки отказа в Redis?**  
   → Кластер Redis (Redis Cluster) или репликация + Sentinel.  

2. **Что делать при резком скачке RPS?**  
   → Реализовать **burst-ограничение** (например, Token Bucket).  

3. **Как учитывать разные лимиты для разных пользователей?**  
   → Хранить в Redis отдельные ключи для каждого пользователя (`user123:limit`, `user456:limit`).  

**Пример запроса к Redis через Lua:**  
```bash
EVAL "локальный_скрипт.lua" 1 "user123:api_requests" 100 60
```
