
### Задача: Currency Hub

В этой задаче нужно спроектировать систему, которая предоставляет API для получения текущего и исторического курса валют, используя несколько поставщиков (например, Bloomberg и Yahoo). Для этого нужно создать сервис, который будет агрегировать данные с этих поставщиков, обеспечивать отказоустойчивость и корректно работать с ошибками.

Давайте разберёмся поэтапно.

---

### 0. Сколько валютных пар и объём хранения?

- **Общее количество валютных пар**: Количество валютных пар будет зависеть от того, какие именно валюты мы поддерживаем. Если поддерживаем **100 валют**, то общее количество валютных пар будет равно:
    
    Число валютных пар=100×992=4950 пар\text{Число валютных пар} = \frac{100 \times 99}{2} = 4950 \text{ пар}
- **Объём хранения**: Для каждой валютной пары нужно хранить текущий курс и, возможно, историю курсов. Если у нас будет несколько источников, например, 2 источника данных для каждой валютной пары, то это удвоит объём хранения. Исторические курсы также будут занимать место в зависимости от их глубины (например, если храним курсы за последние 5 лет по дням, это увеличивает объём данных).
    

Предположим, что для каждой валютной пары нужно хранить:

- Текущий курс от двух поставщиков (Bloomberg и Yahoo).
- Исторический курс за последние несколько лет.

Примерный объём данных можно оценить по количеству валютных пар и необходимости хранения курсов по дням.

### 1. Набор компонентов системы

Для решения задачи давайте разделим систему на несколько основных компонентов:

- **API для получения текущего курса валюты (Exchange Rates API)**:
    
    - Это публичный API, который возвращает текущий курс валютной пары. Мы будем делать запросы к поставщикам данных (Bloomberg, Yahoo) и предоставлять результат пользователю.
- **API для получения исторического курса валюты (Historical Rates API)**:
    
    - Публичный API, который позволяет получить курс валюты за определённый промежуток времени. Мы храним исторические данные на сервере, и этот API будет использовать эти данные для предоставления информации.
- **Сервисы для получения данных от поставщиков (Data Aggregators)**:
    
    - Компонент, который собирает данные с различных поставщиков (например, Bloomberg и Yahoo) для каждой валютной пары. Эти сервисы будут периодически запрашивать актуальные курсы и сохранять их в базе данных.
- **База данных**:
    
    - Хранилище для хранения текущих и исторических курсов валют. Мы можем использовать **реляционную базу данных** или **NoSQL хранилище** (например, **MongoDB**), в зависимости от того, какой объём данных мы планируем хранить.
- **Планировщик задач (Scheduler)**:
    
    - Сервис, который по расписанию будет делать запросы к поставщикам и обновлять курсы валют в базе данных.

#### Разделение на сервисы:

- **Сервис чтения**:
    - Обрабатывает запросы на получение текущих курсов и исторических данных.
- **Сервис записи**:
    - Записывает данные в базу данных, обновляя текущие курсы и историю по расписанию. Это позволяет разгрузить сервис чтения от лишней нагрузки.

#### Проблема с выбором поставщика (что делать, если курсы расходятся):

- **Ручной выбор**:
    - Поставщик с более надёжной репутацией (например, Bloomberg) будет использоваться как основной для получения курса.
- **Математический метод**:
    
    - **Среднее** между курсами от разных поставщиков.
    - **Медиана** или **перцентиль** для уменьшения влияния выбросов.
    
    Например:
    
    ```python
    trusted_rate = median(bloomberg_rate, yahoo_rate)
    ```

### 2. Как обеспечить отказоустойчивость?

Для обеспечения отказоустойчивости можно использовать следующие методы:

1. **Резервирование поставщиков**:
    
    - При недоступности одного из поставщиков автоматически запрашивать данные у другого.
    - Использовать fallback-систему, которая переключается на резервного поставщика, если основной недоступен.
2. **Кэширование**:
    
    - Использование кэша для хранения курсов валют на некоторое время (например, в Redis). Это уменьшает нагрузку на внешний API и повышает производительность при высоких запросах.
    - Кэширование помогает также при временных сбоях в подключении к API поставщиков.
3. **Механизм повторных попыток**:
    
    - Если поставщик временно недоступен, нужно автоматически повторить попытку с некоторыми интервалами. Это уменьшит вероятность потери данных.
4. **Тайм-ауты и аварийное завершение**:
    
    - Устанавливать разумные тайм-ауты на запросы к внешним API и реализовать обработку ошибок с фоллбеком.

### 3. Как поступать, если курс расходится между поставщиками?

Если курсы от двух поставщиков сильно различаются, можно использовать несколько стратегий:

1. **Выбор доверенного поставщика**:
    
    - Простой подход: всегда использовать данные от одного из поставщиков (например, Bloomberg), если они доступны.
2. **Среднее или медианное значение**:
    
    - При различии между курсами можно взять **среднее** или **медиану** от курсов двух поставщиков:
        
        ```go
        rate := (bloombergRate + yahooRate) / 2
        ```
        
3. **Перцентиль**:
    
    - Для защиты от выбросов можно использовать перцентиль. Например, если разница в курсах значительна, то можно взять **90-й перцентиль** между курсами двух поставщиков.
        
    - Если разница в курсах меньше, чем определённый порог, можно использовать среднее значение.

### 4. Как обрабатывать ошибки сервиса?

1. **Системы повторных попыток (Retries)**:
    
    - Когда поставщик не доступен, следует повторить запрос несколько раз с интервалом.
    - Использование **экспоненциальной задержки** поможет избежать перегрузки системы.
2. **Fallback механизмы**:
    
    - Если один поставщик не отвечает, можно переключиться на другого поставщика.
    - Реализовать логику, где сервис может использовать кэшированные данные в случае, если оба поставщика недоступны.
3. **Ошибки с возвратом**:
    
    - В случаях, когда невозможно получить данные, можно возвращать ошибку с кодом, например, 503 (Service Unavailable) или 408 (Request Timeout).
4. **Обратная связь (Alerting)**:
    
    - Важно настраивать систему мониторинга и оповещений (например, с использованием Prometheus и Grafana), чтобы оперативно реагировать на сбои в работе поставщиков.

### Архитектура

- **API Gateway**: Принимает запросы от клиентов и перенаправляет их на соответствующий сервис для получения данных.
- **Service Layer**: Включает логику получения курса, обработки ошибок и выбора поставщика.
- **Data Aggregators**: Сервисы для взаимодействия с поставщиками (Bloomberg, Yahoo) и получения актуальных курсов.
- **Database**: Хранение текущих и исторических курсов.
- **Cache**: Использование Redis или Memcached для кэширования данных и повышения производительности.
- **Scheduler**: Периодическое обновление курсов валют с внешних сервисов.

Использование различных математических методов для разрешения расхождений между поставщиками позволит обеспечить точность и надёжность данных.
