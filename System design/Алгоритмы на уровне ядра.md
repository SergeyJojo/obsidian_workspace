## **1. Алгоритмы на уровне ядра распределённых систем**

### **1.1. Алгоритмы согласованности на атомарном уровне**

Мы уже разобрали Paxos и Raft, но есть менее известные, невероятно эффективные алгоритмы.

#### **EPaxos (Efficient Paxos)**

- EPaxos — это оптимизация Paxos, которая минимизирует количество сетевых взаимодействий.
- **Ключевая идея:**
    - Не требует строгой координации, если операции не конфликтуют.
    - Использует **dependency graph**, чтобы определить порядок выполнения транзакций.

Пример применения:

- Современные распределённые базы данных (например, CockroachDB).

---

### **1.2. Алгоритмы для глобального консенсуса**

Когда ты строишь систему на уровне Google или Amazon, ты сталкиваешься с необходимостью согласованности данных по всему миру.

#### **Spanner (Google): TrueTime API**

1. **TrueTime API**:
    - Использует GPS-спутники и атомные часы для синхронизации времени.
    - Каждый запрос имеет временные метки с гарантированными границами (`earliest` и `latest`).
2. **Компромисс:**
    - Spanner жертвует низкой задержкой ради сильной согласованности.

## **2. Криптография в распределённых системах**

### **2.1. Алгоритмы шифрования**

1. **TLS 1.3:**
    
    - Используй только TLS 1.3 для минимизации времени рукопожатия.
    - Пример:
        - "Zero Round Trip Time" (0-RTT) позволяет клиенту возобновить сессию без дополнительных задержек.
2. **End-to-End Encryption (E2EE):**
    
    - Шифруй данные на клиенте и расшифровывай только на другом клиенте.
    - Используй **Diffie-Hellman** для генерации общего ключа.

---

### **2.2. Подпись данных**

1. **HMAC (Hash-Based Message Authentication Code):**
    - Используется для проверки целостности и аутентичности данных.
2. **JWT (JSON Web Token):**
    - Используй алгоритм `RS256`, а не `HS256` для более безопасной подписи.

Пример структуры JWT:

```json
{
    "header": {
        "alg": "RS256",
        "typ": "JWT"
    },
    "payload": {
        "user_id": "12345",
        "role": "admin"
    },
    "signature": "base64url-encoded signature"
}
```

## **3. Структуры данных для Big Data**

### **3.1. Advanced Bloom Filters**

Bloom Filter — это структура данных для проверки принадлежности элемента.

#### **Проблема:**

- У Bloom Filter есть "ложные срабатывания".

#### **Решение: Counting Bloom Filter**

- Учитывает количество вставок для каждого элемента.
- Пример: используется для реализации кэша в Redis.

---

### **3.2. LSM-Tree (Log-Structured Merge-Tree)**

1. **Использование:**
    - Применяется в высокопроизводительных базах данных, таких как Cassandra и RocksDB.
2. **Как это работает:**
    - Запись происходит в память.
    - Периодически данные записываются на диск в виде сегментов.
    - Старые сегменты объединяются для оптимизации.

## **4. Сложные сценарии высокой доступности**

### **4.1. Устойчивость к сбоям нескольких зон**

1. Используй **multi-zone deployment**:
    
    - Каждая зона может работать автономно.
    - Данные реплицируются между зонами.
2. **Erasure Coding**:
    
    - Альтернатива репликации.
    - Разбивает данные на фрагменты и добавляет избыточные куски.
    - Пример: MinIO.

---

### **4.2. Стратегии Graceful Shutdown**

Когда сервисы останавливаются:

1. Уведомляй Load Balancer, чтобы он прекратил направлять новые запросы.
2. Обрабатывай все текущие запросы перед завершением.

---

## **5. Дизайн для ультранизкой задержки**

### **5.1. Lock-Free Data Structures**

1. Используй структуры данных без блокировок:
    - Пример: ConcurrentQueue, реализованная через CAS (Compare-And-Swap).
2. Реализация CAS:
    
    ```go
    func compareAndSwap(ptr *int, old, new int) bool {
        return atomic.CompareAndSwapInt32(ptr, int32(old), int32(new))
    }
    ```
    

---

### **5.2. Реактивные системы**

1. **Backpressure**:
    - Автоматическое регулирование скорости данных, чтобы предотвратить перегрузку.
2. **Reactive Streams API**:
    - Позволяет создавать асинхронные потоки данных.
