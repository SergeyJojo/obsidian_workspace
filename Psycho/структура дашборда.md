
Сергей, вот как на практике строится и используется дешбординг по инцидентам — особенно для **разбора latency spikes, queue buildup, error rate jumps** и прочего.

Разберу **по шагам**, как это реально делают в продакшене: от сбора данных до визуализации и использования при RCA (Root Cause Analysis).

---

## 📌 Цель дешборда: **быстро локализовать и объяснить проблему**

> Например: spike в latency API → это сеть? БД? очередь? goroutine starvation?

---

## 🧱 Шаг 1: Что отслеживать (метрики)

### 🔸 Latency spikes

- `http_server_duration_seconds_bucket` (Prometheus histogram)
    
- `grpc_server_handling_seconds`
    
- `db.query.duration`
    
- `redis.get.duration`
    
- `kafka.consumer.lag`
    
- `go_gc_duration_seconds` / `go_threads`
    

### 🔸 Queue buildup

- Количество сообщений в Kafka / RabbitMQ
    
- Длина очередей в сервисе (в Go: channel len)
    
- Число активных goroutines (`runtime.NumGoroutine`)
    
- Показатели backpressure
    

### 🔸 Errors

- `http_requests_total{status=~"5.."}`
    
- `db.query.errors`
    
- `kafka.producer.errors`
    
- `timeouts`, `circuit breaker trips`

## 🛠️ Шаг 2: Сбор данных

### 🔹 Источники:

- Prometheus (и Alertmanager)
    
- Loki (логи)
    
- Tempo / Jaeger (трейсы)
    
- Kafka / Redis метрики
    
- PostgreSQL через `pg_exporter`
    

### 🔹 Примеры экспорта:

```go
// В Go с prometheus:
prometheus.NewHistogramVec(prometheus.HistogramOpts{
    Name: "http_request_duration_seconds",
    Buckets: prometheus.DefBuckets,
}, []string{"handler", "status"})
```

## 🎨 Шаг 3: Структура дешборда

### 💡 Блоки дешборда:

1. **Top-level summary**:
    
    - p50/p95/p99 latency
        
    - RPS
        
    - error rate
        
    - queue depth
        
    - cpu, memory
        
2. **Drill-down по компонентам**:
    
    - БД (queries / locks / IO)
        
    - Kafka (produce/consume lag)
        
    - gRPC/HTTP latency breakdown
        
3. **Latency vs Queue Correlation**:
    
    - График: latency spikes ↔ queue size ↔ GC
        
4. **Трейсы**:
    
    - ссылку на Tempo/Jaeger по `trace_id`
        
    - топ медленных запросов
        

---

## 📊 Пример: Latency spike дешборд

|Панель|Что показывает|
|---|---|
|p99 latency|Всплески задержек|
|queue length|Длина очереди → backpressure|
|goroutine count|Утечки/блокировки|
|db.query.duration|Не тормозит ли БД|
|kafka.lag|Накопление сообщений|
|redis.miss_ratio|Потери кэша = рост задержек|
|request error rate|Критично? или spike "мягкий"|

---

## 🔍 Шаг 4: Реакция при инциденте

**Инцидент**: Spike latency до 5s, API падает.

**Действия:**

1. Смотришь дешборд — видишь latency spike + рост `queue_depth`
    
2. Смотришь `goroutines` — их стало 20k → подозрение на deadlock/пул
    
3. Смотришь БД → один запрос висит 3s (нет индекса)
    
4. Kafka lag? Нормально → не она
    
5. Коррелируешь в трейсе — медленный `db.query` на `/search`
    

**Вывод**: сбой в индексации → spike latency в API
