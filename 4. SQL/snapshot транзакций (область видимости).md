# 🔹 Что такое снимок (snapshot) в PostgreSQL

Снимок — это **логическое состояние БД в момент начала транзакции или запроса**, состоящее из:

- списка **активных транзакций**, которые ещё не закоммичены;
    
- идентификаторов видимых коммитов (XID);
    
- границы XID (минимум и максимум).
    

Этот снимок определяет:

- какие строки видит транзакция,
    
- какие строки считаются «невидимыми» (ещё не закоммичены чужими или удалены).
    

👉 Важно: Postgres никогда не перезаписывает строки, он создаёт новые версии (tuple versions). Снимок определяет, **какую версию строки транзакция может читать**.

---

# 🔹 1. READ COMMITTED (уровень по умолчанию)

- Снимок делается **на каждый запрос** (не на всю транзакцию).
    
- То есть каждый `SELECT`, `UPDATE`, `DELETE` может увидеть новые коммиты других транзакций.
    

Пример:

```sql
-- Сессия 1
BEGIN;
SELECT count(*) FROM orders; -- допустим, 1000 строк

-- Сессия 2
INSERT INTO orders VALUES (...);
COMMIT;

-- Сессия 1
SELECT count(*) FROM orders; -- уже 1001, потому что новый запрос сделал новый снимок
COMMIT;
```

📌 Важно: данные «живые», но результат внутри одной транзакции может быть **неконсистентным** (разные запросы видят разное состояние).

---

# 🔹 2. REPEATABLE READ

- Снимок делается **один раз в начале транзакции**.
    
- Все запросы в транзакции работают с этим снимком.
    
- Новые коммиты других транзакций не видны до конца.
    

Пример:

```sql
-- Сессия 1
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT count(*) FROM orders; -- 1000

-- Сессия 2
INSERT INTO orders VALUES (...);
COMMIT;

-- Сессия 1
SELECT count(*) FROM orders; -- всё ещё 1000 (старый снимок)
COMMIT;
```

📌 Таким образом:

- нет «неповторяющихся чтений» (repeatable read anomaly),
    
- но возможны «фантомные чтения» (phantom reads), если ты используешь разные условия выборки.
    

Хотя в Postgres фактически **phantom reads тоже не возникают** благодаря MVCC, но по стандарту этот уровень их допускает.

---

# 🔹 3. SERIALIZABLE

- Работает как `REPEATABLE READ` (снимок фиксируется на старте транзакции),
    
- но Postgres дополнительно проверяет **логическую сериализуемость** транзакций.
    
- Если два параллельных коммита дали бы результат, которого не могло бы быть в последовательном исполнении, одна транзакция откатывается с `serialization_failure`.
    

Пример:

```sql
-- Сессия 1
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT sum(balance) FROM accounts WHERE type='debit'; -- 1000

-- Сессия 2
BEGIN ISOLATION LEVEL SERIALIZABLE;
INSERT INTO accounts(type, balance) VALUES('debit', 100);
COMMIT;

-- Сессия 1
INSERT INTO accounts(type, balance) VALUES('debit', 200);
COMMIT; -- тут Postgres может выдать ошибку serialization_failure
```

📌 Здесь Postgres "поймает", что два параллельных коммита ломают сериализуемость, и принудительно одну транзакцию откатит.

---

# 🔹 4. READ UNCOMMITTED

- В Postgres **нет настоящего read uncommitted**.
    
- Этот уровень работает как `READ COMMITTED`.
    
- То есть "грязные" (dirty) данные в PG никогда не видны.
    

---

# 🔹 Сравнительная таблица

|Уровень изоляции|Когда делается снимок|Видимость чужих коммитов|Аномалии|
|---|---|---|---|
|READ UNCOMMITTED|каждый запрос|только закоммиченные|= READ COMMITTED|
|READ COMMITTED|каждый запрос|видны новые коммиты|non-repeatable read, phantom|
|REPEATABLE READ|на старте транзакции|новые коммиты не видны|phantom (по SQL стандарту)|
|SERIALIZABLE|на старте + проверка конфликтов|новые коммиты не видны, возможен откат|никаких аномалий|

---

✅ Итог:

- В PostgreSQL **снимок данных — это набор видимых версий строк**, определяемый уровнем изоляции.
    
- READ COMMITTED → свежий снимок на каждый запрос.
    
- REPEATABLE READ → фиксированный снимок на всю транзакцию.
    
- SERIALIZABLE → фиксированный снимок + защита от нелогичных комбинаций транзакций.
