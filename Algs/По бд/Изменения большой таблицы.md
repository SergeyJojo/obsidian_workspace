
Отлично, ты сейчас спрашиваешь про **"онлайн-обновление данных в hot-таблице без долгой блокировки"** — это прям настоящая задача уровня production в крупных системах.

🟢 Давай я тебе расскажу это **профессионально, по шагам, с практическими приемами**.

---

## 🟢 Задача:

- Огромная таблица (миллиарды записей).
    
- Нужно обновить 1 млн записей.
    
- Таблица **hot** (есть постоянные SELECT, INSERT, UPDATE, транзакции).
    
- **Блокировать её "массивно" нельзя** — иначе "тронешь продакшн".
    

---

## 🟡 Основные проблемы:

| Проблема                                               | Почему плохо                                           |
| ------------------------------------------------------ | ------------------------------------------------------ |
| 🔥 Долгая блокировка строк                             | SELECT / UPDATE / INSERT начнут ждать → лаги, таймауты |
| 🐌 Большие UPDATE → full table scan, нагрузка на диски | IOPS, locks, WAL (write ahead log), репликация         |
| 💾 Рост UNDO / REDO логов (rollback segments)          | Убьет производительность                               |
| 🕒 Репликация (logical/physical replication)           | Большие транзакции → реплики отстают                   |

---

## 🟢 Как обновляют такие данные в продакшне?

### 📍 Шаг 1: Не делай "одним UPDATE"

❌ **Вот так делать нельзя:**

```sql
UPDATE my_table SET field = 'fixed' WHERE condition = 'bad';
```

- Такой запрос может повесить продакшн на десятки минут.
    
- Lock escalation → долгая блокировка строк → катастрофа.
    

---

### 📍 Шаг 2: Обновляем **батчами (batch update)**

✅ Делаем **много маленьких транзакций**.

- Например, по 1000 строк за раз.
    

📦 Пример на PostgreSQL:

```sql
BEGIN;

WITH cte AS (
    SELECT id FROM my_table
    WHERE condition = 'bad'
    LIMIT 1000
    FOR UPDATE SKIP LOCKED
)
UPDATE my_table
SET field = 'fixed'
WHERE id IN (SELECT id FROM cte);

COMMIT;
```

📊 Объяснение:

|Почему так?|Зачем|
|---|---|
|`LIMIT 1000`|Ограничиваем партию|
|`FOR UPDATE SKIP LOCKED`|Не ждём заблокированные строки (берём те, что свободны)|
|Быстрый COMMIT|Маленькая транзакция → быстрый rollback, быстрый WAL|

📦 Циклом в приложении/скрипте крутим это:

```bash
while true; do
  psql -f update_batch.sql
  sleep 0.1
done
```

---

### 📍 Шаг 3: throttle (ограничение нагрузки)

- Добавляем **sleep между батчами** (например, 100 мс).
    
- Следим за метриками (CPU, IOPS, locks).
    
- Можно динамически адаптировать скорость (см. Load Shedding / Rate Limiting).
    

---

### 📍 Шаг 4: Параллелизм (опционально)

- Если хотим быстрее: запускаем несколько параллельных воркеров.
    
- Каждый берёт свои строки через `SKIP LOCKED`.
    
- Таким образом, мы не создаём конфликтов между воркерами.
    

---

### 📍 Шаг 5: Проверка индексов

- Чтобы быстро находить нужные строки → индексы по `condition` / `id` должны быть в порядке.
    
- **Если индекса нет → сначала его создать CONCURRENTLY**, чтобы не блокировать таблицу:
    

```sql
CREATE INDEX CONCURRENTLY idx_condition ON my_table (condition);
```

---

### 📍 Шаг 6: Репликация (WAL impact)

- Следим, чтобы WAL не захлестнулся.
    
- Можно регулировать batch size → меньше батчи → меньше WAL.
    
- Можно использовать **logical replication slots** чтобы мониторить отставание реплик.
    

---

## 🟢 Альтернативные подходы (если прям сложно):

|Способ|Вариант|
|---|---|
|🟡 Shadow table|Создаёшь копию таблицы, обновляешь в фоне, потом атомарно switchover (дорого по времени)|
|🟡 Partial reindex|Чинишь данные на уровне индексов (редко применимо)|
|🟡 Флаг "исправлена"|Вместо UPDATE → ставишь флажок, который игнорирует bad-данные в будущем|

---

## 🟢 Реальный сценарий: как делают в крупных базах

1. Создаётся **batch update worker**.
    
2. Он читает по кусочкам нужные записи (`LIMIT 1000 SKIP LOCKED`).
    
3. Медленно, но стабильно обновляет данные.
    
4. Если у тебя миллион строк, при скорости 1000 строк / сек → примерно 15 минут обновления без трогания продакшна.
    
5. Весь трафик продолжается, SELECT работает, блокировки минимальные.
    

---

## 🟡 Итоговый вывод:

|✅ Что важно|📊 Почему|
|---|---|
|Маленькие батчи|Мгновенные транзакции, быстрые коммиты|
|SKIP LOCKED|Без блокировки горячих строк|
|Параллелизм + Throttle|Быстро, но контролируемо|
|Мониторинг (locks, WAL, репликация)|Не убить продакшн|
