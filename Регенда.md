# 🚀 Как устроен сервис управления контейнерами типа "Evolution Managed Kubernetes"

**Тезисно:**

- Это прослойка между **реальным Kubernetes-кластером** и **пользователем**.
    
- Задача сервиса: **спрятать сложность** управления кластерами Kubernetes.
    
- Предоставить пользователю **API или интерфейс**, чтобы он мог деплоить контейнеры, не погружаясь в сложный kubectl / Helm.
    

---

# 🏗 Основная архитектура

```
Пользователь → Портал (Web UI / API) → Сервис управления → Kubernetes API → Кластеры
```

**Компоненты:**

|Компонент|Что делает|
|:--|:--|
|Web UI / API|Интерфейс пользователя: создать контейнер, настроить приложение, обновить версию|
|Оркестратор (Backend)|Принимает команды с UI и вызывает Kubernetes API|
|Kubernetes Cluster|Настоящий кластер, где реально запускаются ваши поды, сервисы, ингрессы|
|Сервисные компоненты|Мониторинг, логирование, автоскейлинг, обновления|

---

# 🔥 Что скрывает от пользователя Evolution

- Развёртывание и управление мастер-нодами.
    
- Настройку сети (CNI плагины типа Calico, Flannel).
    
- Настройку хранилищ (StorageClasses, PVC).
    
- Обновление версий Kubernetes.
    
- Балансировку нагрузки (LoadBalancer).
    
- Мониторинг и алерты.
    
- Автоматическую установку ingress-контроллеров (например, nginx-ingress).
    
- Автоматическую интеграцию с Artifact Registry (реестр образов).
    

---

# 📦 Как работает деплой контейнера через Evolution

1. Пользователь в UI выбирает: "Хочу задеплоить приложение из образа `myregistry/myapp:latest`."
    
2. UI отправляет запрос на Backend сервиса.
    
3. Backend формирует:
    
    - Deployment манифест
        
    - Service манифест
        
    - Ingress манифест (если нужно)
        
4. Backend вызывает Kubernetes API (`POST /apis/apps/v1/namespaces/.../deployments`) и создаёт ресурсы в кластере.
    
5. Kubernetes сам:
    
    - Скачивает образ с Artifact Registry.
        
    - Стартует поды.
        
    - Выставляет сервисы и ингрессы.
        
6. Пользователь видит в UI: "Ваше приложение запущено."

## ❓ Что такое SaaS

**SaaS (Software as a Service)** — это модель, когда ты **пользуешься программным обеспечением через интернет**, не устанавливая его у себя на компьютере или серверах.

- Программа работает **на стороне поставщика** (например, в облаке).
    
- Ты работаешь **через браузер** или через **API**, **платишь за использование** (или иногда бесплатно, с ограничениями).
    
- **Не заботишься** про установку, обновления, бэкапы, безопасность — за всё отвечает поставщик услуги.
    

---

## 📦 Примеры SaaS

|SaaS-приложение|Что делает|
|:--|:--|
|Gmail|Почта без настройки серверов|
|Google Docs|Документы без Word на компе|
|GitHub|Репозитории кода как сервис|
|Zoom|Видеоконференции через браузер|
|Slack|Чаты для работы без собственных серверов|
|Evolution Managed Kubernetes|Управление кластерами без ручного развертывания|

---

## 🔥 Почему SaaS удобен

- **Быстро начать** работу — не надо развертывать железо и софт.
    
- **Экономия** денег на поддержке инфраструктуры.
    
- **Масштабируемость** — можно быстро увеличить ресурсы по запросу.
    
- **Фокус** на продукте, а не на настройке серверов и обновлениях.
    

---

## 🛠 Чем SaaS отличается от других моделей

|Модель|Описание|
|:--|:--|
|**SaaS**|Ты просто пользуешься готовым приложением.|
|**PaaS** (Platform as a Service)|Тебе дают платформу для запуска своих приложений (например, базы данных, среды исполнения).|
|**IaaS** (Infrastructure as a Service)|Тебе дают просто виртуальные машины, сеть, диски — строй что хочешь сам.|

## ❓ Что такое **Service** в Kubernetes

**Service** в Kubernetes — это **абстракция**, которая создаёт **постоянную сетевую точку доступа** (IP + порт) для группы Pod'ов.

**Проблема:** Pod'ы в Kubernetes живут недолго и меняют свои IP-адреса.

**Решение:** Service автоматически:

- находит нужные Pod'ы по **label'ам**,
    
- даёт им **один стабильный IP/имя**,
    
- **балансирует трафик** между ними.
    

---

## 📦 Как устроен Service внутри

1. Ты описываешь объект **Service** в YAML.
    
2. Указываешь **selector** — какие Pod'ы он должен обслуживать (по меткам `labels`).
    
3. Kubernetes автоматически:
    
    - отслеживает, какие Pod'ы подходят под селектор,
        
    - отправляет на них трафик,
        
    - следит, чтобы новые Pod'ы тоже начали получать трафик, а удалённые — убрались.
        

---

## 🔥 Типы Service в Kubernetes

|Тип|Что делает|
|:--|:--|
|**ClusterIP** (по умолчанию)|Доступен **только внутри** кластера.|
|**NodePort**|Открывает **порт на всех нодах** кластера.|
|**LoadBalancer**|Создаёт **внешний балансировщик** в облаке (например, в AWS, GCP).|
|**ExternalName**|Переадресует запросы на **внешний DNS**.|

---

## 🛠 Пример простого Service (ClusterIP)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app     # выбирает все Pod'ы с этой меткой
  ports:
    - protocol: TCP
      port: 80      # порт сервиса
      targetPort: 8080  # на какой порт Pod'а пересылать
```

**Что происходит:**

- Внутри кластера можно обратиться к `my-service:80`.
    
- Kubernetes сам найдёт нужный Pod и отправит трафик на его `8080`.
    

---

## 🚀 Пример с NodePort (доступ снаружи)

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-nodeport-service
spec:
  type: NodePort
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
      nodePort: 30007    # порт на нодах
```

**Что происходит:**

- Kubernetes откроет порт **30007** на всех узлах.
    
- Можно будет обратиться по IP любой ноды: `http://<node-ip>:30007`.
    

---

## 📌 Как работать с Service в реальной жизни

1. **Создать Service:**  
    `kubectl apply -f service.yaml`
    
2. **Посмотреть IP и порты:**  
    `kubectl get svc`
    
3. **Привязать Deployment/Pod:**  
    Убедись, что метки (labels) у Pod'ов и селектор в Service совпадают.
    
4. **Обращаться по имени сервиса:**  
    Все Pod'ы в одном namespace могут обращаться по имени, типа: `http://my-service`.
    

---

## 🧠 Частые ошибки и ловушки

|Ошибка|Почему происходит|
|:--|:--|
|Service не находит Pod'ы|Selector в Service не совпадает с label'ами Pod'а|
|Нет доступа к сервису|Забыл открыть порты или неправильно настроил `targetPort`|
|LoadBalancer не работает|Кластер не в облаке (например, голый kubeadm)|

---

## ✨ Очень кратко:

> Service в Kubernetes — это как **DNS + балансировщик + маршрутизатор** одновременно.

Он "перехватывает" запросы и отправляет их правильным живым Pod'ам без твоего участия.
