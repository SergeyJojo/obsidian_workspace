# 📦 Как устроен `values.yaml` в Helm чартах

Файл `values.yaml` — это **набор всех переменных**, которые может использовать Helm-шаблон для настройки деплоя.  
Именно сюда **заливаются параметры без изменения самих шаблонов**.

Пример реального `values.yaml`:

```yaml
replicaCount: 3

image:
  repository: myregistry.com/myapp
  tag: v1.0.0
  pullPolicy: IfNotPresent

service:
  type: ClusterIP
  port: 80

resources:
  requests:
    cpu: "100m"
    memory: "128Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"

env:
  - name: ENV
    value: "production"
  - name: DEBUG
    value: "false"

ingress:
  enabled: true
  className: nginx
  hosts:
    - host: myapp.example.com
      paths:
        - path: /
          pathType: Prefix

persistence:
  enabled: true
  storageClass: standard
  accessModes:
    - ReadWriteOnce
  size: 1Gi

autoscaling:
  enabled: true
  minReplicas: 2
  maxReplicas: 10
  targetCPUUtilizationPercentage: 80
```

---

# 🧠 Структура `values.yaml` в общем:

|Блок|За что отвечает|
|:--|:--|
|`replicaCount`|Количество подов|
|`image`|Откуда брать образ|
|`service`|Настройки Kubernetes сервиса|
|`resources`|Лимиты ресурсов CPU и памяти|
|`env`|Переменные окружения|
|`ingress`|Проброс наружу через Ingress-контроллер|
|`persistence`|Настройки хранения данных (PV, PVC)|
|`autoscaling`|Автоматическое масштабирование|

---

# 🔥 Как шаблоны Helm используют `values.yaml`

Пример фрагмента шаблона (`deployment.yaml`):

```yaml
spec:
  replicas: {{ .Values.replicaCount }}
  containers:
    - name: {{ .Chart.Name }}
      image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
      resources:
        requests:
          cpu: {{ .Values.resources.requests.cpu }}
          memory: {{ .Values.resources.requests.memory }}
        limits:
          cpu: {{ .Values.resources.limits.cpu }}
          memory: {{ .Values.resources.limits.memory }}
```

То есть шаблоны Helm — это такие **.yaml файлы с Go-шаблонным синтаксисом**, которые при установке подставляют значения из `values.yaml`.

# 🚀 Способы деплоя в Helm и как они меняются

### 1. **Стандартный деплой через Helm Chart**

```bash
helm install myapp ./chart
```

Создаёт релиз в кластере. Использует дефолтный `values.yaml`.

---

### 2. **С установкой кастомных параметров**

```bash
helm install myapp ./chart -f values-prod.yaml
```

- Переопределяем дефолтные значения.
    
- Обычно так деплоят в разные окружения (`dev`, `stage`, `prod`).
    

---

### 3. **Через `--set` параметры на лету**

```bash
helm install myapp ./chart --set replicaCount=5
```

- Прямо в команде меняем отдельные параметры.
    
- Удобно для тестов.
    

---

### 4. **Через `upgrade`**

```bash
helm upgrade myapp ./chart -f values-prod.yaml
```

- Обновляет существующий релиз.
    
- Изменяет только то, что поменялось.
    

---

### 5. **Helmfile или GitOps-подход**

- Большие проекты используют `helmfile` для управления многими чартами.
    
- Или используют GitOps (например, через ArgoCD или Flux), где изменения в репозитории автоматически деплоятся через Helm.
    

---

# 🏗 Как изменяются деплои через Helm в реальной жизни

|Ситуация|Как действуют|
|:--|:--|
|Нужно просто поставить сервис|`helm install`|
|Изменили версию образа|`helm upgrade` с новым `values.yaml`|
|Новый кластер / новое окружение|Новый `values.yaml` под окружение|
|Хотят быстро поэкспериментировать|`--set` прямо в команде|
|Нужно управлять 50+ сервисами|Используют Helmfile или GitOps|

---

# 🎯 Итого:

- `values.yaml` — это **конфигурация всех параметров деплоя**.
    
- Helm позволяет **гибко менять деплой**: через файлы (`values`), через команду (`--set`), через автоматизацию (`helmfile`, ArgoCD).
    
- Ты работаешь с **темплейтами** и **конфигами**, **а не руками редактируешь kubectl yaml'ы** — это **современный стандарт**.
