
В Go есть несколько типов ошибок, которые можно считать критическими или фатальными для программы, и которые не всегда можно или следует перехватывать. Вот список таких ошибок, с пояснением, какие из них нельзя перехватить и какие из них являются фатальными:

### 1. **`panic` (паника)**

**Паника** — это механизм обработки ошибок в Go, который используется для обозначения фатальных, неконтролируемых ситуаций. Когда происходит паника, программа немедленно завершает выполнение текущей горутины, а все отложенные (`defer`) функции выполняются перед тем, как программа будет завершена.

**Почему это критическая ошибка:**

- Если паника не перехватывается через `recover`, программа завершится с ошибкой.
- Обычно используется для ситуаций, которые невозможно или нецелесообразно обработать, например, ошибочные внутренние состояния программы.

**Пример:**

```go
package main

func main() {
    panic("Critical error!") // Паника приводит к завершению программы
}
```

**Можно ли перехватить?**

- Да, с помощью функции `recover`, которая используется внутри отложенной функции `defer`. Однако если паника не перехвачена, программа завершится.

### 2. **Ошибка в системных ресурсах (например, `os.Exit`)**

**`os.Exit`** — это стандартная функция для немедленного завершения программы с заданным кодом выхода. Это фатальная ошибка, если ошибка не была обработана, и приводит к завершению программы.

**Почему это критическая ошибка:**

- Если вызвать `os.Exit()`, программа завершится без выполнения `defer`-функций, что может привести к утечкам ресурсов или другим нежелательным последствиям.

**Пример:**

```go
package main

import "os"

func main() {
    os.Exit(1) // Завершение программы с ошибкой
}
```

**Можно ли перехватить?**

- Нет. Функция `os.Exit` немедленно завершает программу, не давая возможности для перехвата ошибки.

### 3. **Ошибка сегментации (Segmentation Fault)**

Ошибки сегментации происходят, когда программа пытается обратиться к памяти, которая не была выделена или была освобождена. В Go это может произойти, например, при использовании небезопасных операций с указателями через пакет `unsafe`. Это приводит к сбою программы и, как правило, является фатальной ошибкой.

**Почему это критическая ошибка:**

- Это ошибка низкоуровневого программирования, которая связана с некорректным доступом к памяти, и ее невозможно перехватить с помощью Go-стандартных механизмов (например, с помощью `defer` или `recover`).

**Пример (с использованием пакета `unsafe`):**

```go
package main

import "unsafe"

func main() {
    var p *int
    *p = 42 // Ошибка сегментации, потому что указатель p не инициализирован
}
```

**Можно ли перехватить?**

- Нет, ошибки сегментации не могут быть перехвачены средствами Go. Это ошибка на уровне операционной системы, и она приводит к завершению программы.

### 4. **`runtime.Goexit`**

**`runtime.Goexit()`** — это функция, которая завершает выполнение текущей горутины. Она не вызывает панику, а просто завершает работу горутины, в отличие от `panic`.

**Почему это критическая ошибка:**

- Хотя `Goexit` не является ошибкой в классическом понимании, она может быть использована для завершения горутины, что в некоторых случаях может быть неожиданным для логики программы.

**Пример:**

```go
package main

import "runtime"

func main() {
    go func() {
        runtime.Goexit() // Завершение текущей горутины
    }()

    // Программа продолжит выполнение, но горутина завершится
}
```

**Можно ли перехватить?**

- Нет, `runtime.Goexit()` завершает горутину, но не вызывает паники, так что не может быть перехвачено средствами стандартной обработки ошибок.

### 5. **Ошибки, связанные с недостатком памяти (Out of Memory)**

Если программа исчерпала все доступные ресурсы памяти, операционная система может завершить выполнение процесса, отправив сигнал `SIGKILL` или аналогичный. Это происходит, когда программа пытается выделить больше памяти, чем доступно на машине.

**Почему это критическая ошибка:**

- Эта ошибка не может быть перехвачена в Go. Обычно она возникает, когда программа пытается выделить больше памяти, чем позволяет операционная система, или когда происходит ошибка в сборщике мусора.

**Можно ли перехватить?**

- Нет. Когда система исчерпывает память, программа будет завершена, и перехватить эту ошибку невозможно с помощью стандартных средств Go.

### 6. **Ошибка с операционной системой (например, сбой при работе с файловой системой)**

Когда система сталкивается с ошибками на низком уровне, например, при работе с файловой системой, сетью или другими ресурсами операционной системы, такие ошибки могут быть фатальными.

**Почему это критическая ошибка:**

- Если ошибка возникает при взаимодействии с операционной системой (например, ошибки ввода-вывода), она может привести к завершению работы программы, особенно если ошибка не может быть восстановлена.

**Пример:**

```go
package main

import "os"

func main() {
    _, err := os.Open("nonexistent-file.txt")
    if err != nil {
        panic(err) // Если файл не найден, программа завершится с паникой
    }
}
```

**Можно ли перехватить?**

- Да, можно использовать `defer`/`recover` для перехвата паники в случае ошибок операционной системы. Однако саму ошибку не избежать, и это приведет к завершению программы.

### 7. **Ошибки связанные с внешними библиотеками**

Если вы используете сторонние библиотеки и они не реализуют корректное поведение или имеют дефекты (например, в многозадачных приложениях), это может привести к фатальным сбоям, которые нельзя перехватить в Go.

**Почему это критическая ошибка:**

- Некоторые ошибки в сторонних библиотеках могут привести к непредсказуемым последствиям, особенно в многозадачных приложениях. Например, плохая реализация синхронизации или ошибки в выделении памяти.

### Заключение

Фатальные ошибки в Go, такие как `panic`, ошибки сегментации, проблемы с памятью или операционной системой, не всегда можно перехватить. Однако в большинстве случаев Go предоставляет средства для обработки ошибок с помощью `error`, а также позволяет использовать `defer` и `recover` для обработки паники. Ключевое отличие фатальных ошибок от обычных в том, что их невозможно перехватить с помощью стандартных механизмов языка.
