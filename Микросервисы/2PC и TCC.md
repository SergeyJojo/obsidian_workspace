
# Two-Phase Commit (2PC) и Try-Confirm-Cancel (TCC) - протоколы распределенных транзакций

## Two-Phase Commit (2PC) - Двухфазный коммит

### Основная концепция
2PC - это алгоритм координации распределенной транзакции, который гарантирует атомарность (все или ничего) в системах с несколькими участниками.

### Фазы выполнения:

1. **Фаза голосования (Prepare phase)**:
   - Координатор отправляет запрос "prepare" всем участникам
   - Каждый участник выполняет свою часть транзакции, но не фиксирует изменения
   - Участник голосует "Yes" (готов к фиксации) или "No" (не может выполнить)

2. **Фаза выполнения (Commit phase)**:
   - Если все участники проголосовали "Yes":
     * Координатор отправляет "commit"
     * Участники фиксируют изменения
   - Если хотя бы один участник проголосовал "No":
     * Координатор отправляет "rollback"
     * Участники откатывают изменения

### Преимущества:
- Гарантирует атомарность распределенной транзакции
- Относительно прост в понимании и реализации
- Широко поддерживается в СУБД (XA-транзакции)

### Недостатки:
- **Блокировки ресурсов** на время выполнения (проблемы с производительностью)
- **Блокировка при отказе координатора** (участники ждут решения)
- **Синхронное выполнение** (не подходит для высоконагруженных систем)

### Пример сценария (банковский перевод между разными БД):
1. Координатор: "Prepare" → БД1 (списание) и БД2 (зачисление)
2. БД1 и БД2 блокируют средства и отвечают "Yes"
3. Координатор: "Commit" → обе БД фиксируют изменения

## Try-Confirm-Cancel (TCC) - Трехфазная модель

### Основная концепция
TCC - это паттерн для управления распределенными транзакциями, основанный на компенсирующих операциях (сагах).

### Фазы выполнения:

1. **Try (Попытка)**:
   - Резервирование ресурсов
   - Проверка всех условий
   - Подготовка данных без реального изменения состояния

2. **Confirm (Подтверждение)**:
   - Фактическое выполнение операции
   - Использование зарезервированных ресурсов

3. **Cancel (Отмена)**:
   - Компенсирующая операция (откат)
   - Освобождение зарезервированных ресурсов

### Преимущества:
- **Нет долгих блокировок** (ресурсы блокируются только на фазе Try)
- **Более высокая производительность** по сравнению с 2PC
- **Гибкость** - можно реализовать сложную бизнес-логику отката
- **Подходит для микросервисов**

### Недостатки:
- Требует реализации компенсирующих операций
- Сложнее в реализации, чем 2PC
- Нужно проектировать систему с учетом TCC изначально

### Пример сценария (бронирование отеля+авиабилетов):
1. **Try**:
   - Отель: временно блокирует номер
   - Авиакомпания: временно блокирует место
2. **Confirm**:
   - Отель: подтверждает бронь
   - Авиакомпания: подтверждает билет
3. **Cancel** (если один сервис не смог):
   - Отель: разблокирует номер
   - Авиакомпания: разблокирует место

## Сравнение 2PC и TCC

| Критерий               | 2PC                          | TCC                          |
|------------------------|------------------------------|------------------------------|
| **Гарантии**           | Сильная согласованность      | Согласованность в конечном счете |
| **Блокировки**         | Долгие (на время транзакции) | Короткие (только на фазе Try) |
| **Отказоустойчивость** | Проблемы при отказе координатора | Более устойчив к отказам |
| **Производительность** | Низкая                       | Высокая                     |
| **Сложность**          | Проще                        | Сложнее (нужны компенсации) |
| **Использование**      | СУБД, монолиты               | Микросервисы, REST API       |

## Когда что выбирать?

**2PC лучше использовать когда**:
- Требуется строгая согласованность данных
- Система уже использует XA-совместимые СУБД
- Транзакции выполняются быстро

**TCC лучше использовать когда**:
- Система построена на микросервисах
- Операции требуют долгого выполнения
- Нужна высокая доступность и устойчивость к отказам
- Можно реализовать идемпотентные компенсирующие операции

## Реализации в экосистеме:
- **2PC**: XA-интерфейс в СУБД, Atomikos, Narayana
- **TCC**: Apache ServiceComb, Seata, собственные реализации в микросервисных архитектурах

Оба подхода решают проблему распределенных транзакций, но с разными компромиссами между согласованностью, доступностью и производительностью.
