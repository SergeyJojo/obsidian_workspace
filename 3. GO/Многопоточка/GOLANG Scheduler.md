Давайте разберем устройство GMP-модели в Go — это основа планировщика горутин (Goroutine Scheduler), который управляет выполнением параллельных задач в языке программирования Go. GMP расшифровывается как Goroutine (G), Machine (M) и Processor (P), и это ключевая концепция, обеспечивающая легковесную многопоточность в Go. Я объясню основные компоненты, их взаимодействие и как планировщик решает задачи распределения и управления ресурсами, опираясь на предоставленный код и общие принципы работы.

---

Основные концепции GMP

1. Goroutine (G):
    
    - Это легковесная единица выполнения в Go, аналог потока, но управляемая runtime, а не операционной системой.
        
    - G представляет собой задачу, которая должна быть выполнена (например, функцию, запущенную через go func()).
        
    - G хранит свой стек, состояние (например, _Grunning, _Gwaiting) и другую метаинформацию.
        
2. Machine (M):
    
    - Это рабочий поток операционной системы (OS thread), который выполняет код Go.
        
    - M соответствует реальному потоку ОС и используется для запуска горутин.
        
    - Каждый M может быть связан с P (процессором), но может быть заблокирован (например, в системном вызове) без P.
        
3. Processor (P):
    
    - Это абстрактный "процессор" — ресурс, необходимый для выполнения Go-кода.
        
    - P управляет локальной очередью горутин (runq) и связывает M с G.
        
    - Количество P обычно равно количеству доступных CPU ядер (определяется через GOMAXPROCS).
        

Взаимодействие:

- M (поток ОС) должен быть связан с P, чтобы выполнять G (горутины).
    
- Планировщик распределяет готовые к выполнению G по доступным P, которые, в свою очередь, исполняются на M.
    

---

Задача планировщика

Планировщик (scheduler) в Go отвечает за:

- Распределение готовых к выполнению горутин (G) по рабочим потокам (M).
    
- Балансировку между использованием доступного параллелизма (CPU) и экономией ресурсов (парковка ненужных потоков).
    
- Обеспечение высокой производительности и масштабируемости.
    

Основные принципы:

- Децентрализация: Состояние планировщика распределено (например, локальные очереди на каждом P), чтобы избежать узких мест.
    
- Work-Stealing: Если у P заканчиваются задачи, он может "украсть" горутины из очереди другого P.
    
- Спящие потоки (Parking): M, у которых нет работы, паркуются, чтобы не тратить CPU.
    

---

Устройство GMP-модели

Компоненты планировщика:

1. Локальная очередь (Local Run Queue):
    
    - Каждый P имеет свою очередь горутин (runq), где хранятся G, готовые к выполнению.
        
    - Это обеспечивает локальность выполнения и уменьшает конкуренцию.
        
2. Глобальная очередь (Global Run Queue):
    
    - Если локальная очередь переполняется или P не может принять G, горутина отправляется в глобальную очередь.
        
    - Используется для распределения задач между P.
        
3. Spinning Threads:
    
    - M может находиться в состоянии "spinning" — это поток, который ищет работу (в локальных очередях, глобальной очереди или других источниках, например, netpoller), но пока не выполняет G.
        
    - Состояние "spinning" отслеживается через m.spinning и sched.nmspinning.
        
4. Netpoller:
    
    - Специальный механизм для асинхронных операций ввода-вывода (например, сетевых запросов). Если G блокируется в ожидании I/O, M может переключиться на выполнение другой G.
        

Как это работает:

- Когда создается новая G (через go func()), она добавляется в локальную очередь текущего P.
    
- Если локальная очередь заполнена, G отправляется в глобальную очередь.
    
- P управляет выполнением G на связанном M. Если G блокируется (например, в системном вызове), M может "отцепиться" от P и взять другую задачу.
    
- Если у P нет работы, он пытается украсть G у других P или из глобальной очереди.
    

---

Балансировка потоков (Parking/Unparking)

Одна из ключевых задач планировщика — балансировать количество активных M:

- Слишком много потоков: Тратятся ресурсы CPU.
    
- Слишком мало потоков: Не используется весь параллелизм.
    

Подход к парковке/разпарковке:

1. Когда распарковать новый M (функция wakep):
    
    - Есть свободный P (idle P).
        
    - Нет "spinning" потоков (sched.nmspinning == 0).
        
    - В этом случае создается новый M, который сразу становится "spinning" и ищет работу.
        
2. Когда парковать M:
    
    - M становится "spinning", если у него нет локальной работы и он не находит задач в глобальной очереди или netpoller.
        
    - Если "spinning" M не находит работу, он паркуется (переходит в состояние ожидания).
        
3. Переход из "spinning" в "non-spinning":
    
    - Если "spinning" M находит работу, он перестает быть "spinning" и выполняет G.
        
    - Если последний "spinning" M находит работу, он должен распарковать новый M, чтобы избежать недоиспользования CPU.
        

Почему это сложно?

- Децентрализация: Нет единого состояния, чтобы мгновенно понять, сколько потоков нужно.
    
- Гонки: Переход "spinning → non-spinning" может конкурировать с добавлением новой работы, и нужно гарантировать, что новый M будет создан, если работа осталась необработанной.
    

Синхронизация:

- При добавлении работы:
    
    1. Добавляем G в очередь (локальную или глобальную).
        
    2. Барьер памяти (#StoreLoad).
        
    3. Проверяем sched.nmspinning и, если нужно, распарковываем M.
        
- При переходе "spinning → non-spinning":
    
    1. Уменьшаем nmspinning.
        
    2. Барьер памяти.
        
    3. Проверяем очереди на наличие работы.
        

---

Источники работы

Планировщик обрабатывает несколько источников задач:

1. Горутины:
    
    - Новая G становится готовой к выполнению и добавляется в очередь.
        
2. Таймеры:
    
    - Когда таймер срабатывает, создается задача для обработки (например, через netpoller).
        
3. GC (Garbage Collector):
    
    - Приоритетные задачи GC могут активировать спящие M.

Пример из кода

Инициализация runtime:

go

```go
func main() {
    mp := getg().m
    mainStarted = true
    systemstack(func() {
        newm(sysmon, nil, -1) // Запуск системного монитора
    })
    lockOSThread()
    // ... Инициализация
    fn := main_main
    fn()
}
```

- Создается первый M (m0) и G (g0) для выполнения main.
    
- Запускается системный монитор (sysmon) как отдельный M для управления фоновыми задачами.
    

Парковка горутины:

go

```go
func gopark(unlockf func(*g, unsafe.Pointer) bool, lock unsafe.Pointer, reason waitReason, traceReason traceBlockReason, traceskip int) {
    mp := acquirem()
    gp := mp.curg
    mp.waitlock = lock
    mp.waitunlockf = unlockf
    gp.waitreason = reason
    releasem(mp)
    mcall(park_m)
}
```

- G переводится в состояние ожидания, а M может взять другую G.
    

Распарковка:

go

```go
func goready(gp *g, traceskip int) {
    systemstack(func() {
        ready(gp, traceskip, true)
    })
}
```

- G становится готовой, и планировщик добавляет её в очередь.
    

---

Преимущества GMP

1. Легковесность:
    
    - G занимает всего 2 КБ памяти, в отличие от потоков ОС (1-2 МБ).
        
2. Масштабируемость:
    
    - Децентрализация и work-stealing минимизируют конкуренцию.
        
3. Эффективность:
    
    - Балансировка "spinning" и парковки оптимизирует использование CPU.
        

---

Итог

GMP-модель — это сердце планировщика Go, который:

- Управляет G (горутинами) через P (процессоры) на M (потоках ОС).
    
- Использует локальные и глобальные очереди для распределения задач.
    
- Балансирует активные потоки через механизм "spinning" и парковки.
    
- Обеспечивает высокую производительность и масштабируемость.
    

Если хотите углубиться в конкретный аспект (например, work-stealing или как работает sysmon), дайте знать — разберем подробнее!
