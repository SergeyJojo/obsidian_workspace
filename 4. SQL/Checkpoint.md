## 🔹 Что такое checkpoint в PostgreSQL

В PostgreSQL все изменения сначала попадают в **буферный кеш (shared buffers)** и одновременно фиксируются в **WAL (Write-Ahead Log)**.

- WAL пишет синхронно, чтобы при крэше можно было восстановиться.
    
- Буферы можно держать в памяти, но когда они заполняются или приходит время "глобальной фиксации", нужно их выгрузить.
    

👉 **Checkpoint** — это момент, когда PostgreSQL гарантирует, что все dirty pages (страницы с изменениями) в буферном кеше **сброшены на диск** и соответствующие записи WAL уже были записаны и fsync'нуты.  
Это делает WAL "короче" — для восстановления не нужно откатывать журнал слишком далеко назад.

---

## 🔹 Как работает checkpoint пошагово

1. **Триггеры** (что может вызвать checkpoint):
    
    - По времени (`checkpoint_timeout`, например каждые 5 минут).
        
    - По размеру WAL (`max_wal_size` превышен).
        
    - Админская команда (`CHECKPOINT;`).
        
    - Во время shutdown.
        
2. **Процесс**:
    
    - Checkpointer берёт dirty pages из shared buffers.
        
    - Вызывает запись этих страниц на диск.
        
    - Убеждается, что WAL, покрывающий эти изменения, уже сброшен (`fsync`).
        
    - Обновляет `pg_control` — "с какого места WAL можно начать recovery".

## 🔹 Какие системные вызовы используются

PostgreSQL сам не пишет "голыми руками", он полагается на вызовы ОС (через `smgr.c`, `bufmgr.c`).  
Основные вызовы:

- **`write()`** — чтобы передать страницу из буферного кеша PostgreSQL в файловую систему (страница — 8 KB).
    
- **`pwrite()`** (часто используется вместо `write`, чтобы писать сразу по нужному смещению).
    
- **`fdatasync()`** или **`fsync()`** — чтобы гарантировать сброс данных с кэша ОС на диск.
    
    - `fdatasync()` сбрасывает только данные файла, без метаданных.
        
    - `fsync()` может затронуть и метаданные (например, размер файла).
        
- **`sync_file_range()`** (Linux, если включён `wal_sync_method=open_datasync` или подобные) — оптимизация, чтобы делать асинхронные сбросы.
    
- **`msync()`** — если PostgreSQL использует mmap (обычно для некоторых вспомогательных файлов, но не для основного heap/WAL).

## 🔹 Оптимизации и нюансы

- PostgreSQL **не всегда сразу вызывает fsync() для каждой страницы** — он может сгруппировать записи и вызвать fsync только в checkpoint.
    
- Параметр **`synchronous_commit`** управляет тем, ждёт ли backend `fsync` WAL перед ответом клиенту.
    
- Параметр **`full_page_writes`** — влияет на то, сколько пишется в WAL при checkpoint.
    
- **bgwriter** и **checkpointer** стараются равномерно сбрасывать страницы, чтобы не "обрушить" диск в момент checkpoint (см. `checkpoint_completion_target`).
    

---

## 🔹 Итог

- Checkpoint = запись всех dirty страниц из shared buffers в файлы БД.
    
- На уровне ОС это делается через **`pwrite()`** (страницы) и **`fdatasync()/fsync()`** (гарантия записи).
    
- Цель checkpoint — сократить время recovery и ограничить рост WAL.
