
Понимаю, что ты работаешь с Go и хочешь эффективно документировать свои REST API с помощью Swagger. Для этого можно использовать инструменты, такие как **Swaggo/swag** и **go-swagger**, которые позволяют генерировать документацию из комментариев в коде. Ниже я опишу основные теги, которые следует использовать в комментариях, а также лучшие практики для создания качественной документации.

---

## 🏷️ Основные теги для аннотаций в комментариях

### 📌 Общая информация об API

Эти аннотации размещаются в комментариях над функцией `main` или в файле `main.go`:

```go
// @title           Название API
// @version         1.0
// @description     Подробное описание API
// @termsOfService  http://example.com/terms/

// @contact.name   Имя контакта
// @contact.url    http://example.com
// @contact.email  support@example.com

// @license.name  Название лицензии
// @license.url   http://example.com/license

// @host      example.com
// @BasePath  /api/v1
// @schemes   http https
```

### 📌 Аннотации для обработчиков маршрутов

Размещаются непосредственно над функциями-обработчиками маршрутов:([Devtrovert | Phuong Le | Substack](https://blog.devtrovert.com/p/swagger-in-go-why-its-the-genius?utm_source=chatgpt.com "Swagger in Go: A Pragmatic Guide - by Phuong Le - Devtrovert"))

```go
// @Summary      Краткое описание эндпоинта
// @Description  Подробное описание эндпоинта
// @Tags         Категория или группа эндпоинта
// @Accept       Формат входных данных (например, json)
// @Produce      Формат выходных данных (например, json)
// @Param        имя_параметра местоположение тип обязательность "Описание"
// @Success      код_ответа {тип} модель "Описание"
// @Failure      код_ответа {тип} модель "Описание"
// @Router       /путь [метод]
```

**Пример:**

```go
// @Summary      Получить пользователя по ID
// @Description  Возвращает данные пользователя по его идентификатору
// @Tags         users
// @Accept       json
// @Produce      json
// @Param        id path int true "Идентификатор пользователя"
// @Success      200 {object} models.User "Успешный ответ"
// @Failure      400 {object} models.Error "Некорректный запрос"
// @Failure      404 {object} models.Error "Пользователь не найден"
// @Router       /users/{id} [get]
```

### 📌 Аннотации для моделей

Для описания структур данных (моделей) можно использовать теги в комментариях и структурные теги:

```go
// User представляет информацию о пользователе
type User struct {
    ID    int    `json:"id" example:"1"`
    Name  string `json:"name" example:"Иван"`
    Email string `json:"email" example:"ivan@example.com"`
}
```

Также можно использовать специальные теги, такие как `swaggerignore:"true"`, чтобы исключить поле из документации.

## ✅ Лучшие практики при документировании API

1. **Поддерживай актуальность аннотаций**: Обновляй комментарии при изменении логики эндпоинтов.
    
2. **Используй понятные и краткие описания**: `@Summary` должен быть лаконичным, а `@Description` — более подробным.
    
3. **Группируй эндпоинты с помощью `@Tags`**: Это улучшает навигацию в Swagger UI.
    
4. **Указывай примеры данных**: Используй тег `example` в структурных тегах для предоставления примеров значений.
    
5. **Определяй модели для запросов и ответов**: Это обеспечивает ясность структуры данных.
    
6. **Используй `@Param` для описания всех параметров**: Указывай местоположение (`path`, `query`, `header`, `body`), тип и обязательность параметра.
    
7. **Документируй возможные ответы с помощью `@Success` и `@Failure`**: Это помогает понять, какие ответы может возвращать эндпоинт.
    
8. **Организуй документацию с помощью `@Router`**: Указывай путь и метод для каждого эндпоинта.
