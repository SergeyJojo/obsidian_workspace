## **1. Архитектура Go Scheduler: Взаимодействие G, M и P**

### **1.1. Состояния потоков (M)**

Потоки (M) переходят между несколькими состояниями:

1. **Idle (простой):**
    - Поток без привязанного процессора (`P`) ожидает.
2. **Running (исполняется):**
    - Поток привязан к `P` и выполняет горутину.
3. **Syscall (системный вызов):**
    - Поток временно недоступен, так как выполняет блокирующий вызов.
4. **Blocked (заблокирован):**
    - Поток ждёт, пока станет доступным `P`.

---

### **1.2. Как Go ограничивает количество потоков**

- Количество активных потоков регулируется значением `runtime.sched.maxmcount`.
- Если потоку не удаётся найти `P`, он переходит в "спящий" режим:
    
    ```go
    func stopm() {
        m := getg().m
        m.p = nil
        m.nextp = nil
        runtime.freem(m)
    }
    ```
    

---

### **1.3. Пример работы G, M и P**

```plaintext
1. Горутина G1 добавлена в локальную очередь P1.
2. Поток M1 вытягивает G1 из очереди P1 и исполняет её.
3. Если G1 блокируется, M1 переходит на другую горутину G2.
```

## **2. Netpoll: Глубокий разбор**

Netpoll — это система управления асинхронным вводом-выводом в Go, тесно интегрированная с планировщиком. Она позволяет обрабатывать сетевые события без блокировки потоков.

### **2.1. Как работает Netpoll**

1. **Регистрация дескриптора:**
    
    - Дескриптор (`fd`) регистрируется в системе через вызовы `epoll` (Linux), `kqueue` (macOS), `IOCP` (Windows).
    
    ```go
    func netpollopen(fd uintptr, pd *pollDesc) {
        epollCtl(epfd, EPOLL_CTL_ADD, fd, ...)
    }
    ```
    
2. **Ожидание событий:**
    
    - Если горутина блокируется, она переводится в состояние `Gwaiting`, а поток освобождается для других задач.
3. **Обработка событий:**
    
    - Когда дескриптор готов, Netpoll переводит горутину обратно в состояние `Grunnable`.

---

### **2.2. Оптимизации Netpoll**

1. **Edge-Triggered Mode (ET):**
    - Используется для минимизации накладных расходов на события.
2. **Batching событий:**
    - Планировщик обрабатывает несколько событий за один цикл, что уменьшает переключения контекста.

---

### **2.3. Взаимодействие Netpoll и планировщика**

Когда дескриптор готов, Netpoll уведомляет планировщик:

1. Добавляет горутину в глобальную очередь.
2. Вызывает функцию разблокировки:
    
    ```go
    func netpollunblock(gp *g) {
        ready(gp, 3) // Перевод горутины в состояние runnable
    }
    ```

## **3. Прерывания и Preemption**

### **3.1. Вставка точек прерывания**

Компилятор Go вставляет точки прерывания в стратегически важные места:

1. Циклы:
    
    ```go
    for i := 0; i < n; i++ {
        if preemptible() {
            gopreempt()
        }
    }
    ```
    
2. Вызовы функций:
    - При каждом вызове функция проверяется на возможность прерывания.

---

### **3.2. Принудительное прерывание**

Если горутина работает слишком долго:

1. Планировщик меняет флаг `preempt` в структуре `g`:
    
    ```go
    g.preempt = true
    ```
    
2. Когда горутина достигает точки прерывания, вызывается `runtime.gopreempt`.
    

---

### **3.3. Пример реализации**

```go
func preemptone(gp *g) {
    gp.preempt = true
    if gp.status == Grunning {
        signalM(gp.m)
    }
}
```

## **4. Производительность планировщика**

### **4.1. Сложность алгоритма**

1. **Локальные очереди:** O(1) на добавление и удаление.
2. **Глобальная очередь:** O(1) на добавление, O(N) на извлечение.

---

### **4.2. Меры для повышения производительности**

1. **Адаптивное воровство работы:**
    - Если `P` простаивает, оно агрессивно ищет задачи.
2. **Локальные очереди с кешированием:**
    - Горутины кэшируются в локальных `runq` для минимизации конфликтов.

## **5. Разбор исходного кода**

### **5.1. Создание новой горутины**

Когда вы вызываете `go func()`, происходит:

1. Создаётся структура `g`:
    
    ```go
    g := new(g)
    g.fn = fn
    g.stack = allocStack()
    ```
    
2. Горутина добавляется в очередь:
    
    ```go
    runqput(p, g)
    ```
    
3. Поток `M` вытягивает горутину:
    
    ```go
    g := runqget(p)
    ```
    

---

### **5.2. Прерывание выполнения**

Если горутина работает слишком долго:

1. Планировщик устанавливает флаг прерывания:
    
    ```go
    gp.preempt = true
    ```
    
2. Вызов `gopreempt` приостанавливает выполнение:
    
    ```go
    func gopreempt(gp *g) {
        saveState(gp)
        schedule()
    }
    ```

## **1. Где находится горутина до разблокировки?**

Когда горутина блокируется на ожидании файлового дескриптора, она:

1. **Покидает очередь выполнения**:
    
    - Она удаляется из локальной очереди `runq` (связанной с `P`) или глобальной очереди.
    - Статус горутины изменяется на `Gwaiting`.
2. **Привязывается к дескриптору:**
    
    - Горутину связывают с объектом `pollDesc`, который управляет состоянием файлового дескриптора.
    - Это происходит через вызов `runtime.netpollblock`, который регистрирует горутину для ожидания определённого события (например, доступность чтения или записи).

---

## **2. Привязка через `pollDesc`**

`pollDesc` — это структура в `runtime`, которая хранит информацию о состоянии дескриптора и ожидающих горутинах.

Пример упрощённой структуры:

```go
type pollDesc struct {
    fd      int         // Файловый дескриптор
    rg      *g          // Горутина, ожидающая чтения
    wg      *g          // Горутина, ожидающая записи
}
```

Когда горутина блокируется:

1. Её `g` сохраняется в поле `pollDesc`.
2. Дескриптор регистрируется в Netpoll (например, через `epoll_ctl` для Linux).

---

## **3. Что делает Netpoll?**

Netpoll выполняет:

1. Регистрацию дескриптора в системе ввода-вывода ОС (`epoll`, `kqueue` или `IOCP`).
2. Постоянное ожидание событий для зарегистрированных дескрипторов.

Когда дескриптор становится готовым (например, доступен для чтения):

1. Netpoll вызывает `netpollunblock`:
    
    - Извлекает горутину из `pollDesc`.
    - Переводит её из состояния `Gwaiting` в `Grunnable`.
2. Горутина добавляется в глобальную очередь через вызов:
    
    ```go
    ready(gp, 3) // 3 указывает, что горутина разблокирована Netpoll
    ```
    

---

## **4. Полный цикл блокировки и разблокировки**

### **4.1. Блокировка горутины**

Когда горутина ожидает события, например, вызов `net.Conn.Read()`:

1. Горутину помечают как `Gwaiting`.
    
2. Её дескриптор регистрируется через `netpollblock`:
    
    ```go
    func netpollblock(pd *pollDesc, mode int) *g {
        g := getg()
        g.waitreason = "IO wait"
        goparkunlock(&pd.lock, "IO wait", traceEvGoBlockNet)
        return g
    }
    ```
    
3. Поток `M` освобождается для выполнения других горутин.
    

---

### **4.2. Разблокировка горутины**

Когда дескриптор готов:

1. Netpoll возвращает событие из ОС (`epoll_wait` на Linux).
    
2. `netpollunblock` извлекает горутину:
    
    ```go
    func netpollunblock(gp *g) {
        ready(gp, 3)
    }
    ```
    
3. Планировщик добавляет горутину в глобальную очередь или в локальную очередь `P`.
    

---

## **5. Почему используется глобальная очередь?**

- Глобальная очередь служит общим пулом для всех процессоров `P`.
- Если горутина разблокирована после сетевого ввода-вывода, её выполнение может быть передано любому доступному `P`.
- Это помогает равномерно распределять нагрузку.

---

### **6. Резюме**

До разблокировки горутина временно "заморожена":

- Она находится в состоянии `Gwaiting`, привязанная к объекту `pollDesc`, ассоциированному с файловым дескриптором.
- После готовности дескриптора горутина переводится в `Grunnable` и добавляется в глобальную очередь для выполнения.
