Отличный вопрос, Сергей — ты копнул именно туда, где многие PHP-разработчики даже не знают, что под капотом реально **работает два механизма** управления памятью, а не один.  
Разберём подробно, как **GC (Garbage Collector)** Zend Engine решает проблему **циклических ссылок**.

---

## ♻️ Как работает память и ссылки в PHP

Каждая переменная в PHP представлена структурой **`zval`**:

```c
typedef struct _zval_struct {
    zend_value        value;       // само значение
    zend_uint         refcount;    // счётчик ссылок
    zend_uchar        type;        // тип: IS_STRING, IS_ARRAY и т.д.
    zend_uchar        is_ref;      // флаг "явная ссылка"
} zval;
```

---

## 1️⃣ Основной механизм — Reference Counting (RC)

По умолчанию PHP использует **подсчёт ссылок**:

- Когда ты создаёшь переменную:
    
    ```php
    $a = [1, 2, 3];
    ```
    
    → `refcount = 1`.
    
- Когда делаешь копию:
    
    ```php
    $b = $a;
    ```
    
    → `refcount = 2`.
    
- Когда удаляешь переменную (`unset`):  
    → `refcount` уменьшается.  
    Если `refcount == 0`, zval освобождается.
    

🧩 Это работает быстро и эффективно…  
но **ломается при циклических ссылках**.

---

## 2️⃣ Проблема циклов

```php
$a = [];
$a['self'] = &$a;
unset($a);
```

Что происходит:

- `$a` → `refcount = 1`.
    
- `$a['self']` → создаёт ссылку на сам `$a`, т.е. **refcount увеличивается до 2**.
    
- `unset($a)` уменьшает счётчик на 1, но в объекте/массиве осталась внутренняя ссылка → `refcount = 1`.
    
- Значит, память не освобождается: **утечка!**
    

---

## 3️⃣ Zend Garbage Collector (введён в PHP 5.3)

Чтобы решить это, PHP ввёл **вторичный сборщик мусора (GC)**, который:

- работает **поверх reference counting**,
    
- периодически **ищет циклы** объектов/массивов,
    
- и **удаляет их вручную**, даже если `refcount > 0`.
    

---

## 4️⃣ Как GC находит циклы

Когда объект или массив **становится "возможным участником цикла"**, Zend Engine добавляет его в специальный **буфер возможных циклов** (root buffer).

Дальше, при запуске GC (вручную или автоматически), выполняется три прохода:

### 🧮 1. Mark phase

GC делает "снимок" всех элементов из root buffer и:

- помечает все zval’ы, участвующие в цикле,
    
- временно уменьшает их `refcount`.
    

Если после этого `refcount == 0` — значит объект **недостижим снаружи**, но **связан циклически**.

### 🔍 2. Scan phase

GC сканирует отмеченные zval’ы, чтобы определить, действительно ли они образуют **замкнутый цикл**.

### 🧹 3. Collect phase

Все zval’ы, участвующие в таком цикле, **освобождаются из памяти**, даже если у них `refcount > 0`.

---

## 5️⃣ Когда GC срабатывает

Автоматически — когда буфер GC переполняется (по умолчанию 10 000 элементов).

Можно управлять вручную:

```php
gc_collect_cycles(); // принудительный запуск GC
gc_enable();         // включить GC (по умолчанию включен)
gc_disable();        // выключить GC
gc_status();         // статистика по GC
```

---

## 6️⃣ Пример демонстрации

```php
class A {
    public $ref;
}

$a = new A;
$b = new A;

$a->ref = $b;
$b->ref = $a;

unset($a, $b);

echo "Before GC: ", memory_get_usage(), "\n";
gc_collect_cycles();
echo "After GC: ", memory_get_usage(), "\n";
```

📊 До вызова `gc_collect_cycles()` память удерживается — оба объекта ссылаются друг на друга.  
После — GC обнаруживает цикл и очищает память.

---

## 7️⃣ Важно понимать

|Механизм|Когда срабатывает|Против чего эффективен|Производительность|
|---|---|---|---|
|Reference Counting|Всегда при изменении ссылок|Обычные переменные|Очень быстрый|
|Garbage Collector|Периодически / вручную|Циклические ссылки|Медленнее, но безопаснее|

---

## 8️⃣ GC и производительность

GC работает не постоянно — Zend отслеживает **“подозрительные” zval’ы**.  
Чтобы избежать тормозов:

- Он запускается **асинхронно** при накоплении циклов.
    
- Использует **root buffer**, чтобы не сканировать всю память.
    
- Можно вызвать вручную, если код работает с большими объектами (например, в демоне или воркере).
    

---

## 9️⃣ Как избежать избыточных циклов вручную

- Освобождай большие структуры (`unset`, `null`).
    
- Избегай **взаимных ссылок** между объектами, если это не нужно.
    
- Если используешь большие замыкания или коллекции — очищай их явно.
    
- Для короткоживущих скриптов (веб-запросы) — GC почти не нужен (память всё равно очищается при завершении запроса).
    

---

## 10️⃣ Вывод

- PHP использует **reference counting** + **cycle collector**.
    
- GC решает проблему **циклических ссылок** между zval.
    
- Активируется автоматически, но может вызываться вручную.
    
- Утечек из-за циклов в современных версиях PHP (7+) уже почти не бывает.
