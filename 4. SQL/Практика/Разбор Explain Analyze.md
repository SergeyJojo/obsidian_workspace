## 🧠 Что такое `EXPLAIN ANALYZE`?

Это инструмент PostgreSQL, который:

1. **Планирует** запрос (планировщик оценивает, как его лучше выполнить)
    
2. **Выполняет** его (если есть `ANALYZE`)
    
3. Показывает **фактические и прогнозируемые характеристики** выполнения
    

---

## 📐 Базовая структура узла (Node):

```sql
Nested Loop  (cost=0.43..8.50 rows=1 width=4)
             (actual time=0.028..0.045 rows=3 loops=1)
```

| Поле          | Значение                    |
| ------------- | --------------------------- |
| `cost`        | Оценка планировщика         |
| `actual time` | Реальное время выполнения   |
| `rows`        | Оценка числа строк          |
| `actual rows` | Фактическое число строк     |
| `loops`       | Сколько раз узел был вызван |

---

## 🧾 Полный разбор параметров

### 🔹 `cost=START..END` (логические затраты)

- `START` — стоимость инициализации (доступ к первой строке)
    
- `END` — стоимость получения **всех строк**
    
- Измеряется в **абстрактных единицах**, не миллисекундах
    
- Базируется на `random_page_cost`, `cpu_tuple_cost` и других настройках
    

### 🔹 `rows=...` (оценка планировщика)

- Количество строк, которое **ожидает вернуть узел**
    
- Оценивается на основе статистики (`ANALYZE`)
    
- Если `rows` сильно не совпадает с `actual rows` → планировщик ошибается
    

### 🔹 `width=...`

- Прогнозируемый **размер одной строки в байтах**
    
- Используется для оценки I/O
    

### 🔹 `actual time=START..END`

- `START`: время до первой строки
    
- `END`: время до последней строки
    
- В миллисекундах, реально замеряется
    
- Это то, что **ты хочешь минимизировать**
    

### 🔹 `loops=...`

- Сколько раз **выполнялся узел**
    
- Вложенные узлы могут вызываться **многократно**, например при `Nested Loop`
    

### 🔹 `Buffers:`

- Использовались ли данные из кеша или читались с диска
    
- Поля:
    
    - `shared hit` — из shared_buffers
        
    - `shared read` — с диска
        
    - `temp read/write` — в temp-файлах (если не хватает памяти)

## 🧰 Типы узлов (Nodes)

### 🔸 1. `Seq Scan`

- Последовательный проход по таблице
    
- Быстрый на **маленьких** таблицах
    
- Медленный на **больших**, если нет селективности
    
- Признак того, что **нет индекса** или он не используется
    

### 🔸 2. `Index Scan`

- Обходит строки через B-tree индекс
    
- Хорош, если условие — `=`, `<`, `BETWEEN`
    
- Работает с **любым количеством строк**, но требует переходов к таблице (heap fetch)
    

### 🔸 3. `Index Only Scan`

- Читает только индекс
    
- Работает, **если нужные колонки уже есть в индексе**
    
- Быстрее, т.к. не идёт в таблицу
    

### 🔸 4. `Bitmap Index Scan` + `Bitmap Heap Scan`

- Для **не селективных** условий: `IN`, `OR`, большие диапазоны
    
- Сначала строится **bitmap** (массив битов), потом выборка блоков
    
- Удобен, когда **много строк, но не подряд**
    

### 🔸 5. `Nested Loop`

- Простой алгоритм: для каждой строки A ищем подходящие строки в B
    
- Эффективен для **мало строк**, или если есть **индекс**
    
- Может быть **чудовищно медленным**: `loops` растёт до миллионов
    

### 🔸 6. `Hash Join`

- Строит **в памяти хэш-таблицу** по одной из таблиц, и по ней ищет другую
    
- Быстрее Nested Loop при больших объёмах
    

### 🔸 7. `Merge Join`

- Работает на отсортированных данных
    
- Эффективен при `ORDER BY` или предварительной сортировке
    

### 🔸 8. `Aggregate`, `GroupAggregate`, `HashAggregate`

- Используются при `GROUP BY`, `COUNT`, `SUM`, `AVG` и т.п.
    
- `HashAggregate` — быстрее, но требует памяти
    

### 🔸 9. `Sort`

- Сортировка данных
    
- Медленно на больших объёмах, особенно без индекса
    
- Может писать во **временные файлы**, если не хватает `work_mem`

## 📊 Как анализировать план: пошагово

### 🔍 Шаг 1: Найди **верхний узел** — это итог запроса

- Смотри `actual time`, `actual rows`
    
- Сколько реально ушло времени на весь запрос
    

### 🔍 Шаг 2: Пройди вниз по вложенным узлам

- Найди **самый медленный шаг** — у кого `actual time` × `loops` максимальны
    
- Смотри `buffers`, были ли `read` с диска
    

### 🔍 Шаг 3: Сравни `rows` vs `actual rows`

- Если ошибка в 10×, 100× — статистика устарела или плохой план
    
- Запусти `ANALYZE` или `VACUUM ANALYZE`
    

### 🔍 Шаг 4: Найди узлы типа `Seq Scan`, `Sort`, `Nested Loop`

- Это самые часто проблемные шаги

## 🧪 Пример разбора

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE customer_id = 123;
```

```
Index Scan using idx_orders_customer_id on orders
  (cost=0.29..8.50 rows=10 width=100)
  (actual time=0.025..0.031 rows=5 loops=1)
  Buffers: shared hit=3
```

- Используется индекс → ✅
    
- `rows=10`, `actual rows=5` → ошибка умеренная
    
- Всё из кэша → `shared hit=3`, `read=0` → супер быстро

## ⚠️ Антипаттерны и проблемы

| Симптом                       | Возможная причина             | Как исправить                           |
| ----------------------------- | ----------------------------- | --------------------------------------- |
| `Seq Scan` на большой таблице | Нет индекса или плохой фильтр | Создать индекс                          |
| `Nested Loop` с loops > 10k   | Соединение без индекса        | Добавить индекс, поменять JOIN-тип      |
| `Sort` с большим временем     | Нет индекса под `ORDER BY`    | Добавить индекс, увеличить `work_mem`   |
| `rows` ≠ `actual rows` ×100   | Устаревшие статистики         | `ANALYZE таблица`, настроить autovacuum |
| `temp read/write`             | Пишем во временные файлы      | Увеличить `work_mem`                    |

## ✅ Мини-чеклист при анализе:

1. **Какой узел самый дорогой по времени?**
    
2. **Есть ли `Seq Scan`, `Nested Loop`, `Sort`?**
    
3. **Где `loops` > 1000?**
    
4. **Сильно ли `rows` ≠ actual rows?**
    
5. **Как читаются данные — из кеша или с диска?**
    
6. **Используется ли нужный индекс?**
    
7. **Весь план: сколько занимает `total runtime`?**
