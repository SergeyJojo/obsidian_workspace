
### **Организация сети в Kubernetes и роль Ingress-контроллеров**

---

## **1. Как устроена сеть в Kubernetes?**
Kubernetes (k8s) создает **виртуальную сеть** между подами (pods), нодами (nodes) и сервисами. Основные компоненты:

### **1.1. Pod Network**
- Каждый под получает **уникальный IP** из внутренней сети кластера.
- Поды могут общаться друг с другом **напрямую**, даже если находятся на разных нодах.
- Реализуется через **CNI-плагины** (Calico, Flannel, Cilium и др.).

### **1.2. Service Network**
- **Сервисы (Services)** — абстракция для доступа к группе подов.
- Типы сервисов:
  - **ClusterIP** (доступ только внутри кластера).
  - **NodePort** (открывает порт на нодах).
  - **LoadBalancer** (облачный балансировщик, например, в AWS/GCP).
  - **ExternalName** (CNAME-запись для внешнего сервиса).

### **1.3. DNS в Kubernetes**
- Встроенный **CoreDNS** (или kube-dns) резолвит имена сервисов:
  - `service-name.namespace.svc.cluster.local`.

---

## **2. Ingress-контроллеры: зачем они нужны?**
### **2.1. Проблема без Ingress**
- Каждый сервис с типом `LoadBalancer` создает **отдельный облачный балансировщик** (дорого!).
- Нет единой точки входа для HTTP/HTTPS-трафика.
- Невозможно маршрутизировать запросы по доменам или путям.

### **2.2. Что дает Ingress?**
- **Единая точка входа** для внешнего трафика.
- **Маршрутизация на уровне L7** (HTTP/HTTPS):
  - По домену (`app1.example.com`, `app2.example.com`).
  - По URL-пути (`/api`, `/static`).
- **Поддержка TLS** (SSL-терминация).
- **Балансировка нагрузки** между сервисами.

### **2.3. Как это работает?**
1. Пользователь делает запрос на `https://app.example.com`.
2. DNS направляет трафик на **Ingress-контроллер** (например, Nginx).
3. Ingress-контроллер смотрит в **Ingress-ресурс** и перенаправляет запрос в нужный сервис.

---

## **3. Популярные Ingress-контроллеры**
| Контроллер              | Особенности                                      |
|-------------------------|--------------------------------------------------|
| **Nginx Ingress**       | Самый популярный, гибкость конфигов.            |
| **Traefik**             | Автоматическое обнаружение сервисов, простота.  |
| **HAProxy Ingress**     | Высокая производительность.                     |
| **Istio IngressGateway**| Часть сервис-меша Istio (для сложных сценариев).|

## **4. Пример: Настройка Nginx Ingress**
### **4.1. Установка Ingress-контроллера**
```bash
helm repo add ingress-nginx https://kubernetes.github.io/ingress-nginx
helm install ingress-nginx ingress-nginx/ingress-nginx
```

### **4.2. Создание Ingress-ресурса**
```yaml
# ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service:
            name: api-service
            port:
              number: 80
      - path: /
        pathType: Prefix
        backend:
          service:
            name: frontend-service
            port:
              number: 80
  tls:
  - hosts:
    - app.example.com
    secretName: tls-secret  # Сертификат TLS
```

Применяем:
```bash
kubectl apply -f ingress.yaml
```

## **5. Зачем еще нужны Ingress-контроллеры?**
- **Canary-развертывания** — постепенный rollout новой версии.
- **Аутентификация** (OAuth, JWT через аннотации).
- **Кеширование** (например, для статики).
- **Ограничение скорости** (rate limiting).

---

## **6. Альтернативы Ingress**
- **Service Mesh (Istio, Linkerd)** — более сложные сценарии (mTLS, трафик-менеджмент).
- **API Gateways (Kong, Apigee)** — для API-менеджмента.

---

## **Итог**
- **Сеть в Kubernetes** обеспечивает связность подов и сервисов через CNI и DNS.
- **Ingress-контроллеры** нужны для:
  - Упрощения доступа извне.
  - Гибкой маршрутизации HTTP(S)-трафика.
  - Централизованного управления TLS и балансировкой.

Для старта лучше всего подойдет **Nginx Ingress** — он надежный и хорошо документирован. 🚀
