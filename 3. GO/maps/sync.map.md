F Давайте подробно разберем внутреннее устройство sync.Map в Go, основываясь на ее реализации в стандартной библиотеке (src/sync/map.go). Я опишу все компоненты, их назначение и взаимодействие, чтобы вы получили полное представление о том, из чего она состоит "на самом деле". Код взят из версии Go 1.22 (последняя стабильная на момент моего знания), но принципы применимы ко всем версиям, начиная с введения sync.Map в Go 1.9.

---

Общая концепция sync.Map

sync.Map — это потокобезопасная реализация словаря, оптимизированная для сценариев, где:

- Чтение происходит значительно чаще, чем запись.
    
- Многим горутинам нужно одновременно обращаться к данным.
    

Для этого она использует двухуровневую структуру:

- "Чистые" данные (read): Хранятся в атомарно доступном поле для быстрого чтения без блокировок.
    
- "Грязные" данные (dirty): Хранят изменения и новые записи, доступ к которым требует мьютекса.
    

---

Внутренние структуры sync.Map

1. Основная структура Map

go

```go
type Map struct {
    mu     sync.Mutex    // Мьютекс для защиты dirty
    read   atomic.Value  // Атомарное поле для "чистых" данных (тип readOnly)
    dirty  map[interface{}]*entry // "Грязная" карта для измененных данных
    misses int           // Счетчик промахов при чтении из read
}
```

- mu sync.Mutex:
    
    - Защищает поле dirty от конкурентного доступа при записи, удалении или синхронизации.
        
    - Используется только тогда, когда нужно изменить dirty или скопировать данные из dirty в read.
        
- read atomic.Value:
    
    - Хранит структуру типа readOnly (описана ниже).
        
    - atomic.Value позволяет атомарно читать и обновлять данные без блокировок, что делает чтение из read очень быстрым и безопасным для конкуренции.
        
    - Это ключевая оптимизация для сценариев с частым чтением.
        
- dirty map[interface{}]*entry:
    
    - Обычная карта Go, которая хранит указатели на структуры entry (см. ниже).
        
    - Содержит новые записи, измененные значения или данные, которые еще не синхронизированы с read.
        
    - Может быть nil, если все данные уже находятся в read и нет новых изменений.
        
- misses int:
    
    - Счетчик "промахов" при попытке чтения из read.
        
    - Если промахов становится слишком много (например, ключ есть только в dirty), это триггерит копирование dirty в read.
        

---

2. Структура readOnly

go

```go
type readOnly struct {
    m       map[interface{}]*entry // Карта "чистых" данных
    amended bool                  // Флаг, указывающий, есть ли данные в dirty
}
```

- m map[interface{}]*entry:
    
    - Карта, содержащая "чистые" данные, доступные для чтения.
        
    - Ключи — это interface{}, значения — указатели на entry.
        
    - Это подмножество всех данных в sync.Map, которое не требует блокировок для доступа.
        
- amended bool:
    
    - Флаг, показывающий, содержит ли dirty данные, отсутствующие в read.
        
    - Если amended == true, то при чтении или итерации нужно проверять dirty.
        

readOnly хранится в atomic.Value поля read, что позволяет атомарно обновлять его целиком (например, при синхронизации с dirty).

---

3. Структура entry

go

```go
type entry struct {
    p atomic.Pointer[any] // Указатель на значение (interface{})
}
```

- p atomic.Pointer[any]:
    
    - Атомарный указатель на значение, хранящееся в карте (тип interface{} в старых версиях, any в Go 1.18+).
        
    - Использует atomic.Pointer (ранее atomic.Value) для безопасного конкурентного доступа к значению.
        
- Специальные значения p:
    
    - nil: Запись удалена (soft-deleted), но еще не вытеснена из памяти.
        
    - unsafe.Pointer(&expunged): Специальный маркер (expunged), указывающий, что запись была "вытеснена" (expunged) из read и теперь существует только в dirty.
        
    - Указатель на interface{}: Актуальное значение, доступное для чтения.
        

entry позволяет атомарно обновлять или проверять значение без необходимости блокировать всю карту.

---

4. Специальный маркер expunged

go

```go
var expunged = unsafe.Pointer(new(any))
```

- expunged — это глобальный уникальный указатель, используемый для обозначения записей, которые были удалены из read и ожидают полной очистки или переноса в dirty.
    
- Это оптимизация для отложенного удаления (lazy deletion), чтобы избежать немедленной перестройки read.
    

---

Как это все связано?

Состояние sync.Map

- read содержит "стабильные" данные, которые можно читать без блокировок.
    
- dirty содержит "новые" или "измененные" данные, которые еще не синхронизированы с read.
    
- Когда запись добавляется или изменяется:
    
    - Она сначала попадает в dirty.
        
    - Если dirty становится достаточно большим (или misses превышает порог), данные из dirty копируются в read, а dirty сбрасывается.
        
- Удаление помечает запись как nil или expunged в read, а полная очистка происходит при синхронизации.
    

Пример состояния

Предположим, у нас есть sync.Map:

go

```go
m := &sync.Map{}
m.Store("a", 1)
m.Store("b", 2)
m.Delete("a")
m.Store("c", 3)
```

Возможное внутреннее состояние:

- read:
    
    go
    
    ```go
    readOnly{
        m: map[interface{}]*entry{
            "a": &entry{p: nil},      // Удалено
            "b": &entry{p: &2},       // Значение 2
        },
        amended: true,
    }
    ```
    
- dirty:
    
    go
    
    ```go
    map[interface{}]*entry{
        "b": &entry{p: &2},       // Копия из read
        "c": &entry{p: &3},       // Новое значение
    }
    ```
    
- misses: Увеличивается при попытке чтения "c" из read.
    

---

Как работают ключевые операции?

1. Store (запись)

- Проверяет read на наличие ключа.
    
- Если ключ есть и не expunged, обновляет значение атомарно через entry.p.
    
- Если ключа нет или он expunged:
    
    - Берет mu.Lock().
        
    - Создает dirty, если его нет, копируя не-expunged записи из read.
        
    - Добавляет новую запись в dirty.
        
    - Устанавливает read.amended = true.
        

2. Load (чтение)

- Читает read через atomic.Load.
    
- Если ключ есть и entry.p != nil и не expunged, возвращает значение.
    
- Если ключа нет или он expunged:
    
    - Берет mu.Lock().
        
    - Читает из dirty.
        
    - Увеличивает misses.
        
    - Если misses превышает порог, копирует dirty в read.
        

3. Delete (удаление)

- Проверяет read.
    
- Если ключ есть и не expunged, атомарно устанавливает entry.p = nil.
    
- Если нужно удалить из dirty, берет mu.Lock() и удаляет запись.
    

4. Range (итерация)

- Читает read.
    
- Итерируется по read.m, пропуская nil и expunged.
    
- Если read.amended, берет mu.Lock() и итерируется по dirty, добавляя только новые ключи.
    

---

Оптимизации и особенности

1. Атомарность:
    
    - read и entry.p используют атомарные операции (atomic.Value, atomic.Pointer), минимизируя блокировки.
        
2. Ленивое удаление:
    
    - Записи в read сначала помечаются как nil, а затем как expunged при необходимости, что откладывает полную очистку.
        
3. Синхронизация:
    
    - Когда misses достигает len(dirty), dirty копируется в read, а dirty обнуляется. Это минимизирует работу с мьютексом.
        
4. Память:
    
    - Указатели entry позволяют избежать дублирования значений между read и dirty.
        

---

Итог

sync.Map состоит из:

- mu sync.Mutex: Для защиты dirty.
    
- read atomic.Value: Хранит readOnly с картой "чистых" данных и флагом amended.
    
- dirty map[interface{}]*entry: Обычная карта для "грязных" данных.
    
- misses int: Счетчик промахов для триггера синхронизации.
    
- entry: Структура с атомарным указателем на значение (p).
    

Это двухуровневая структура, где read оптимизирован для чтения, а dirty — для записи, с ленивым переносом данных между ними. Если хотите углубиться в конкретную операцию (например, как Load обрабатывает expunged), дайте знать!
